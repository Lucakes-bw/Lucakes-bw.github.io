> **本文目标**：会用 sysbench 压测 MySQL；能读懂吞吐量和延迟（平均值、95% 分位）；理解并发数对吞吐量和延迟的影响；理解缓冲池大小和命中率对性能的影响；理解组提交；知道调优的方法和最重要的几个参数。
>
> **前置知识**：第 3 章的缓冲池和索引；第 4 章的 redo 日志和刷盘设置。
>
> **实验环境**：MySQL 8.4.13 容器（172.17.0.4），sysbench 1.0.20 在另一个容器中运行，两者在同一台 2 个 CPU 核、2 GB 内存的虚拟机中，网络往返的时间极短。所以本文的绝对数字只代表这台机器，重要的是它们之间的**相对关系**。

## 1. 为什么要压测

- **容量**：上线前知道这台数据库每秒能处理多少请求，业务增长到什么程度需要扩容；
- **调优的依据**：改了一个参数、加了一个索引，到底快了多少，要用相同的负载前后对比，而不是凭感觉；
- **找到瓶颈**：压力加大时，先耗尽的是 CPU、内存、磁盘，还是锁。

## 2. sysbench

sysbench 是最常用的数据库压测工具，内置了几种模拟 OLTP（在线事务处理）的负载：

| 测试 | 每个事务做什么 |
|---|---|
| `oltp_point_select` | 1 次按主键查询 |
| `oltp_read_only` | 14 次查询（点查、范围查询、排序、求和等） |
| `oltp_write_only` | 1 次更新索引列、1 次更新非索引列、1 次删除、1 次插入 |
| `oltp_read_write` | 上面两者的组合，共 18 次查询 |

先准备数据：8 个表，每个 20 万行。

```bash
sysbench oltp_read_write --db-driver=mysql --mysql-host=172.17.0.4 --mysql-user=sb --mysql-password=… \
    --mysql-db=sbtest --tables=8 --table-size=200000 prepare
```

```sql
CREATE TABLE `sbtest1` (
  `id` int NOT NULL AUTO_INCREMENT,
  `k` int NOT NULL DEFAULT '0',
  `c` char(120) NOT NULL DEFAULT '',
  `pad` char(60) NOT NULL DEFAULT '',
  PRIMARY KEY (`id`),
  KEY `k_1` (`k`)
)
```

160 万行，数据加索引共 188 MB，比默认的缓冲池（128 MB）大。然后运行，例如 4 个线程跑 15 秒：

```bash
sysbench oltp_point_select … --threads=4 --time=15 --rand-type=uniform run
```

```
SQL statistics:
    queries performed:
        read:                            909095
        …
    transactions:                        909095 (181786.08 per sec.)
    queries:                             909095 (181786.08 per sec.)
    ignored errors:                      0      (0.00 per sec.)
Latency (ms):
         min:                                    0.01
         avg:                                    0.01
         max:                                    2.20
         95th percentile:                        0.01
```

（这是 2 个线程、5 秒的一次输出。`--rand-type=uniform` 让每一行被访问的概率相同，默认的分布会集中访问少数的行。）关注两类指标：

- **吞吐量**：每秒完成的事务数（TPS）和查询数（QPS）；
- **延迟**：每个事务用了多长时间。平均值会掩盖少数很慢的请求，所以还要看**分位数**：95% 分位 5 毫秒，表示 95% 的事务在 5 毫秒内完成，其余 5% 更慢。用户感受到的往往是那些慢的请求。

每秒 18 万次查询，比通常见到的数字高得多。为了确认它是真实的，又跑了一次同样的测试，比较服务器自己的计数：这一次 sysbench 报告了 908205 次查询，服务器的 `Questions` 计数增加了 908211，只差 6 次（sysbench 初始化时自己执行的几条语句）。这么高是因为客户端和服务器在同一台虚拟机中，往返几乎不花时间，而按主键查一个缓存中的行只需要几微秒。

为了把一次压测变成一行摘要，写了一个小脚本 `sb.sh`，从 sysbench 的输出中取出事务数、查询数、平均延迟和 95% 分位的延迟。下面的结果都是它的输出。

## 3. 并发数

缓冲池设为 512 MB（足以放下全部数据），先运行一次预热，再把线程数从 1 加到 64：

```
oltp_point_select 线程   1：  29350.73 事务/秒  平均    0.03 毫秒  95%    0.04 毫秒
oltp_point_select 线程   2： 172158.93 事务/秒  平均    0.01 毫秒  95%    0.01 毫秒
oltp_point_select 线程   4： 172946.43 事务/秒  平均    0.02 毫秒  95%    0.04 毫秒
oltp_point_select 线程   8： 158851.16 事务/秒  平均    0.05 毫秒  95%    0.08 毫秒
oltp_point_select 线程  16： 161763.29 事务/秒  平均    0.10 毫秒  95%    0.21 毫秒
oltp_point_select 线程  32： 153415.59 事务/秒  平均    0.21 毫秒  95%    0.50 毫秒
oltp_point_select 线程  64： 140231.38 事务/秒  平均    0.46 毫秒  95%    1.18 毫秒
```

- 1 个线程只有 2.9 万，2 个线程跳到了 17 万，远不止翻倍。我的推测（没有进一步测量）是：只有一个线程时，客户端和服务器轮流工作，每次都要等对方被唤醒，CPU 大部分时间在空闲和唤醒之间切换；2 个线程时两个 CPU 核一直有事可做；
- 线程数超过 CPU 核数（2 个）以后，吞吐量不再增加，反而缓慢下降：更多的线程只是在排队，还增加了切换的开销；
- **延迟随线程数一路上升**：64 个线程时平均 0.46 毫秒，是 4 个线程时的 20 多倍。每个请求都要等前面的请求处理完。

读写混合的负载也是同样的规律：

```
oltp_read_write  线程   1：   1237.11 事务/秒  平均    0.81 毫秒  95%    0.81 毫秒
oltp_read_write  线程   2：   1798.93 事务/秒  平均    1.11 毫秒  95%    1.39 毫秒
oltp_read_write  线程   4：   1631.03 事务/秒  平均    2.45 毫秒  95%    4.82 毫秒
oltp_read_write  线程   8：   1846.45 事务/秒  平均    4.33 毫秒  95%    7.98 毫秒
oltp_read_write  线程  16：   2100.35 事务/秒  平均    7.61 毫秒  95%   12.75 毫秒
oltp_read_write  线程  32：   2021.03 事务/秒  平均   15.82 毫秒  95%   56.84 毫秒
```

吞吐量在 2 个线程后基本持平（每秒约 2000 个事务，即约 4 万次查询），延迟却从 0.8 毫秒涨到了 15.8 毫秒，95% 分位更是涨到了 57 毫秒。

所以「同时连接的客户端越多越好」是错的。超过系统的处理能力后，增加并发只会增加延迟。这和计算机网络专栏《同时服务多个客户端》中看到的现象一样。应用程序通常用**连接池**限制同时访问数据库的连接数，把多出来的请求挡在数据库之外排队，而不是让数据库里挤满了互相争抢的线程。

## 4. 缓冲池

第 3 章说过，缓冲池缓存数据页，命中时不需要读磁盘。在 4 个线程的点查负载下，改变缓冲池的大小（`innodb_buffer_pool_size` 可以在运行时修改），每次先预热，再测量，同时统计缓冲池的命中率（1 - 物理读 / 逻辑读）：

```
缓冲池 128 MB：  71993.13 事务/秒  平均 0.06 毫秒  95% 0.11 毫秒  命中率 81.81%  磁盘读 724996 页
缓冲池 256 MB：  92076.49 事务/秒  平均 0.04 毫秒  95% 0.09 毫秒  命中率 91.93%  磁盘读 366954 页
缓冲池 512 MB： 172323.06 事务/秒  平均 0.02 毫秒  95% 0.04 毫秒  命中率 100.00%  磁盘读 0 页
```

（本来还想测 64 MB，但设置后实际得到的是 128 MB：缓冲池的大小必须是 `innodb_buffer_pool_chunk_size`（默认 128 MB）的整数倍，会被向上取整。）

- 数据 188 MB，缓冲池 128 MB 时，约 18% 的请求要读磁盘，吞吐量只有全部命中时的 42%；
- 256 MB 已经比数据大了，命中率却只有 92%：缓冲池中还有其他的页（数据字典、undo 等），而且均匀随机地访问 160 万行，10 秒的预热还不足以把所有的页都读进来；
- 512 MB 时全部命中，一次磁盘读也没有。

这里的「磁盘读」大部分其实读的是虚拟机的操作系统页缓存，并没有真正访问磁盘，所以代价不算大。在真实的服务器上，一次磁盘读要 0.1 毫秒（固态硬盘）到 10 毫秒（机械硬盘），命中率每下降一点，性能都会明显下降。

**缓冲池是 MySQL 最重要的参数。** 专用的数据库服务器上，通常设为物理内存的 50%～75%，剩下的留给操作系统、连接和其他的内存需求。目标是让**经常访问的数据**（热数据）都在缓冲池中，不一定是全部数据。

## 5. 写入和刷盘

第 4 章用插入 1 万行比较过刷盘设置。用 sysbench 的写负载再比较一次（第三组是把设置改回默认后又测了一遍）：

```
--- innodb_flush_log_at_trx_commit=1 sync_binlog=1
oltp_write_only  线程   1：   2343.84 事务/秒  平均    0.43 毫秒  95%    0.49 毫秒
oltp_write_only  线程   4：   4414.59 事务/秒  平均    0.91 毫秒  95%    1.23 毫秒
oltp_write_only  线程  16：   7253.66 事务/秒  平均    2.20 毫秒  95%    4.41 毫秒
--- innodb_flush_log_at_trx_commit=2 sync_binlog=0
oltp_write_only  线程   1：   3677.62 事务/秒  平均    0.27 毫秒  95%    0.40 毫秒
oltp_write_only  线程   4：  10193.24 事务/秒  平均    0.39 毫秒  95%    1.12 毫秒
oltp_write_only  线程  16：  10790.46 事务/秒  平均    1.48 毫秒  95%    3.62 毫秒
--- innodb_flush_log_at_trx_commit=1 sync_binlog=1
oltp_write_only  线程   1：   1134.23 事务/秒  平均    0.88 毫秒  95%    2.57 毫秒
oltp_write_only  线程   4：   2866.53 事务/秒  平均    1.39 毫秒  95%    3.36 毫秒
oltp_write_only  线程  16：   5641.34 事务/秒  平均    2.83 毫秒  95%    6.21 毫秒
```

- 不在提交时 `fsync`，吞吐量提高到 1.5～2.3 倍（代价见第 4 章：机器断电可能丢失约 1 秒的数据）；
- 同样的默认设置，第三组比第一组低了不少。紧接在快的那组之后测量，前一组产生的大量脏页还在后台写回磁盘，和压测争抢磁盘。**同一个测试要重复几次**，注意前后的测试会互相影响，只测一次的数字不可靠；
- 默认设置下，线程越多，吞吐量提高得越明显（1 个线程 2344，16 个线程 7254）。这是因为**组提交**。

### 5.1 组提交

统计默认设置下 redo 日志 `fsync` 的次数（`Innodb_os_log_fsyncs`）：

```
线程 1：2458.04 事务/秒，10 秒约 24580 个事务，redo 日志 fsync 28525 次，平均每次 fsync 提交 0.86 个事务
线程 16：7513.74 事务/秒，10 秒约 75137 个事务，redo 日志 fsync 31316 次，平均每次 fsync 提交 2.40 个事务
```

1 个线程时，每个事务都要单独 `fsync` 一次（后台线程还会额外 `fsync`，所以比事务数还多）。16 个线程时，`fsync` 的次数几乎没变（每秒约 3000 次，这就是这块磁盘 `fsync` 的速度上限），但平均每次 `fsync` 提交了 2.4 个事务：一个事务等待 `fsync` 时，其他事务也写好了日志，下一次 `fsync` 把它们一起写到磁盘上。并发越高，每次能「搭车」的事务越多。这就是**组提交**（group commit），它让「每次提交都 `fsync`」的安全设置在高并发下也能有不错的吞吐量。

## 6. 调优的方法

1. **先找到真正慢的地方**：第 3 章的慢查询日志和 `performance_schema`。大多数性能问题来自几条写得不好、缺少索引的查询，而不是参数；
2. **一次只改一个地方**，在相同的数据和负载上前后对比，每个测试重复几次；
3. **看资源**：压测时观察 CPU（`top`）、磁盘（`iostat`）、内存，以及 MySQL 的状态（缓冲池命中率、锁等待、复制延迟），找出先耗尽的资源；
4. **压测的数据和负载要接近真实**：数据量、数据的分布（热点）、读写的比例、查询的种类。100 行的表上什么都快。

## 7. 最重要的几个参数

| 参数 | 作用 | 建议 |
|---|---|---|
| `innodb_buffer_pool_size` | 缓冲池大小 | 专用服务器上物理内存的 50%～75% |
| `innodb_redo_log_capacity` | redo 日志大小 | 写入多时加大，避免检查点追不上（第 4 章看到过这个警告） |
| `innodb_flush_log_at_trx_commit` | 提交时 redo 日志是否 `fsync` | 默认 1；能接受断电丢 1 秒的数据时用 2 |
| `sync_binlog` | 提交时 binlog 是否 `fsync` | 默认 1；有主从复制时保持 1 |
| `max_connections` | 最大连接数 | 用连接池控制实际的并发，不要靠调大它 |
| `long_query_time` | 慢查询的阈值 | 例如 0.5 秒，配合慢查询日志使用 |
| `innodb_io_capacity` | 后台刷脏页的速度 | 按磁盘的能力设置，固态硬盘可以设到几千 |

MySQL 8.0 起，设置 `innodb_dedicated_server = ON` 会根据机器的内存自动设置缓冲池和 redo 日志的大小，适合专用的数据库服务器。

## 8. 常见错误

- **只看平均延迟**：少数很慢的请求被平均掉了，要看 95%、99% 分位；
- **只测一次**：前一次测试留下的脏页、缓存的状态都会影响下一次（第 5 节的第三组）；
- **在小数据上压测**：数据全在缓冲池中，测不出真实的磁盘读取；
- **以为并发越高越好**：超过处理能力后只增加延迟；
- **一上来就调参数**：先看慢查询和索引；
- **为了压测的数字关掉持久性**：`innodb_flush_log_at_trx_commit = 0` 的数字很好看，但第 4 章看到了它的代价。

## 9. 小结

- sysbench 模拟 OLTP 负载，看吞吐量（TPS、QPS）和延迟（平均值、95% 分位）
- 并发：超过 CPU 核数后吞吐量不再增加，延迟一路上升；用连接池限制并发
- 缓冲池：128 MB 到 512 MB，命中率从 82% 到 100%，吞吐量从 7.2 万到 17.2 万；它是最重要的参数
- 刷盘设置改为 2 和 0，写入的吞吐量提高到 1.5～2.3 倍；组提交让多个事务共享一次 `fsync`，16 个线程时每次 `fsync` 提交 2.4 个事务
- 调优：先找慢查询，一次改一处，重复测量，数据和负载要接近真实

到这里，数据库专栏就结束了。从第 1 章的 SQL，到第 2 章的表设计，第 3 章打开 `.ibd` 文件看到了页和 B+ 树，第 4 章用两个会话重现了各种并发问题、用 `kill -9` 验证了持久性，第 5 章在程序中使用数据库、备份恢复、主从复制和压测。每一个结论都在真实的 MySQL 中测过。下次遇到一条慢查询、一次死锁、一个丢失的更新，你知道该从哪里查起了。

## 10. 练习

1. 第 4 节中，缓冲池设为 64 MB，实际是多少？为什么？
2. 一个系统的数据库有 500 GB，服务器内存 64 GB，缓冲池应该设多大？能保证命中率很高吗？
3. 第 5.1 节中，如果把线程数增加到 64，你预计每次 `fsync` 提交的事务数会怎样变化？吞吐量呢？

<details>
<summary>点击查看答案</summary>

1. 实际是 128 MB。缓冲池按块（chunk）分配，大小必须是 `innodb_buffer_pool_chunk_size × innodb_buffer_pool_instances` 的整数倍，这台服务器上块的大小是 128 MB（`SELECT @@innodb_buffer_pool_chunk_size` 得到 134217728），64 MB 被向上取整成了 128 MB。要使用更小的缓冲池，需要在启动时把块调小。
2. 大约 40～48 GB（物理内存的 60%～75%），留出内存给操作系统和连接。缓冲池只有数据的十分之一，能不能有高命中率，取决于**访问模式**：大多数业务的访问是集中的（最近的订单、活跃的用户），热数据可能只有几 GB，命中率仍然可以很高；如果访问是均匀随机的（像第 4 节的 `--rand-type=uniform`），命中率大约只有 10%，就需要更多内存或者更快的磁盘。要用接近真实的负载压测，并观察实际的命中率。
3. 线程越多，同一时刻在等待 `fsync` 的事务越多，每次 `fsync` 能捎带的事务也越多，平均数会继续增加。但吞吐量不一定继续增加：第 3 节看到，超过 CPU 核数以后，线程主要在排队，CPU、锁（同一行或同一个页上的竞争）可能成为新的瓶颈，延迟会明显上升。实际的结果要压测才能知道，这正是压测的意义。

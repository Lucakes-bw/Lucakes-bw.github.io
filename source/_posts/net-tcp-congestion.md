> **本文目标**：理解接收窗口和流量控制，理解零窗口和窗口探测；理解拥塞控制要解决的问题；理解慢启动、拥塞避免、快速恢复，以及 Reno 和 CUBIC 的区别；会用 `ss -ti` 观察拥塞窗口，会用 iperf3 测量吞吐量。
>
> **前置知识**：上一篇的滑动窗口和重传；第 2.1 篇 UDP 没有流量控制的实验。
>
> **实验环境**：Ubuntu 24.04 容器，Linux 内核 6.8，iperf3 3.16。网络是上一篇的 c —— r —— s，延迟、带宽限制都加在路由器 r 上。

## 1. 两种「太快」

发送方可能发得太快，有两种情况：

1. **接收方处理不过来**：接收方的程序读得慢，接收缓冲区满了。解决它的是**流量控制**，靠的是接收方告诉发送方「我还能收多少」；
2. **网络承受不了**：路径上某个路由器的出口带宽有限，包在它的队列中越积越多，最后被丢弃。解决它的是**拥塞控制**，发送方要根据丢包、延迟等迹象，自己判断网络能承受多快。

TCP 的发送方实际能发送的数据量，取二者中较小的那个：

```
发送窗口 = min(接收窗口 rwnd, 拥塞窗口 cwnd)
```

## 2. 流量控制：接收窗口

TCP 头部中的**窗口**字段，就是接收方告诉发送方的**接收窗口**：接收缓冲区中还有多少空间。上一篇看到的 `win 502`，乘以窗口扩大因子 128，就是 64256 字节。发送方保证已发出但未被确认的数据不超过这个值。

### 2.1 零窗口

重复第 2.1 篇 UDP 的那个实验：让 s 上的接收程序暂停读取，c 发送 20 MB 的数据：

```bash
#!/bin/bash
# zerowin.sh：接收方暂停读取，观察窗口变成 0
cd /lab
ip netns exec r tc qdisc change dev eth1 root netem delay 20ms
head -c 20000000 /dev/zero > 20m.bin
ip netns exec s tcpdump -i eth0 -nn -U -s 128 -w zw.pcap tcp 2>/dev/null & T=$!
ip netns exec s nc -l 8000 > /dev/null & N=$!; sleep 0.5
kill -STOP $N                                   # 接收方暂停，不再读取
ip netns exec c nc -N 10.0.2.2 8000 < 20m.bin & C=$!
sleep 1.5
echo "--- 1.5 秒后，c 和 s 的连接："
ip netns exec c ss -tnm "dport = :8000" | tail -2
ip netns exec s ss -tnm "sport = :8000" | grep -v LISTEN | tail -2
sleep 6
echo "--- 恢复读取"; kill -CONT $N
wait $C; echo "c 发送完毕"
sleep 0.5; kill $T; sleep 0.5
```

1.5 秒后，双方的套接字状态（`ss -tnm`，`-m` 显示内存）：

```
ESTAB 0      352480      10.0.1.2:44922     10.0.2.2:8000
	 skmem:(r0,rb131072,t0,tb522240,f1504,w363040,o0,bl0,d0)
ESTAB 122656 0           10.0.2.2:8000     10.0.1.2:44922
	 skmem:(r128416,rb131072,t0,tb87040,f2656,w0,o0,bl0,d3)
```

- s（第二行）的**接收队列**中有 122656 字节没有被读取，接收缓冲区（`rb131072`）几乎满了；
- c（第一行）的**发送队列**中积压了 352480 字节，发不出去。nc 的 `write` 会阻塞，于是 nc 也停下来，不再从文件中读取。

在 s 上抓包，s 发出的确认中，窗口逐渐缩小：

```
IP 10.0.2.2.8000 > 10.0.1.2.44922: Flags [.], ack 121633, win 8, ...
IP 10.0.1.2.44922 > 10.0.2.2.8000: Flags [P.], seq 121633:122657, ack 1, win 502, ... length 1024
IP 10.0.2.2.8000 > 10.0.1.2.44922: Flags [.], ack 122657, win 0, ...
```

窗口剩下 8（× 128 = 1024 字节）时，c 正好发送了 1024 字节把它填满；之后 s 通告**窗口为 0**：「一个字节也不能再发了」。

窗口为 0 时，发送方停止发送。但如果之后 s 开放窗口的那个通告丢失了，双方就会永远等下去。所以发送方会定期发送**零窗口探测**，询问窗口是否打开了。统计 c 发出的探测：

```
窗口为 0 的时刻（相对）：0
探测   0.27 秒，间隔 0.27
探测   0.78 秒，间隔 0.51
探测   1.77 秒，间隔 0.99
探测   3.76 秒，间隔 1.99
窗口重新打开：6.93 秒
```

探测的间隔也是指数退避的。s 恢复读取后，立即发出了窗口更新（tshark 标记为 `TCP Window Update`），窗口从 0 迅速增大到一百多万字节（Linux 会根据连接的情况自动调整接收缓冲区的大小），c 继续发送，最终 20 MB 全部送达。

| | UDP（第 2.1 篇） | TCP |
|---|---|---|
| 接收方暂停读取 | 缓冲区满后，4907 个数据报被丢弃 | 窗口降为 0，发送方停下来等待 |
| 发送方知道吗 | 不知道 | 知道，并且 `write` 阻塞 |
| 恢复后 | 丢掉的就没了 | 一个字节都不少 |

**流量控制的效果是：慢的一方决定了整体的速度**，而不会丢失数据。网络编程中经常遇到的「`write` 卡住了」，往往就是对方没有在读。

## 3. 拥塞控制

### 3.1 拥塞是什么

假设 c 和 s 之间的瓶颈是 r 的出口，带宽 50 Mbit/s。如果 c 以 100 Mbit/s 的速度发送，每秒有 50 Mbit 的数据进入 r 的队列，队列很快就满了，之后的包全部被丢弃。丢包导致重传，重传又占用带宽……当很多连接同时这样做时，网络中充满了重传的包，真正送达的数据反而越来越少，这就是**拥塞**。1986 年，互联网就发生过这样的「拥塞崩溃」，吞吐量下降到正常时的千分之一，此后 TCP 才加入了拥塞控制。

问题在于，发送方不知道路径的带宽是多少，也不知道有多少别的连接在和它共享。TCP 的办法是**试探**：维护一个**拥塞窗口**（cwnd），不断地增大它，直到出现丢包，就说明超过了网络的承受能力，于是减小它。

### 3.2 观察拥塞窗口

在 r 上把发往 s 的方向设为：延迟 50 ms、带宽 50 Mbit/s、队列最多 280 个包：

```bash
ip netns exec r tc qdisc change dev eth1 root netem delay 50ms rate 50mbit limit 280
```

往返时间约 54 ms。50 Mbit/s × 0.054 秒 ≈ 330 KB ≈ 230 个 1448 字节的段，这叫**带宽时延积**（BDP），是「填满」这条路径所需要的在途数据量。队列上限 280 个包包括了正在被延迟的包，所以在途的数据超过约 280 段时，就会开始丢包。

用 iperf3 发送 10 秒，同时大约每 20 毫秒用 `ss -ti` 读取一次 c 的 cwnd：

```bash
#!/bin/bash
# cwnd.sh 拥塞控制算法 秒数：c 向 s 发送数据，大约每 20 毫秒记录一次 c 的 cwnd
cd /lab
ip netns exec s iperf3 -s -1 -D -p 5201 > /dev/null; sleep 0.5
ip netns exec c iperf3 -c 10.0.2.2 -p 5201 -t $2 -C $1 -J > iperf-$1.json & P=$!
: > cwnd-$1.txt
START=$(date +%s.%N)
while kill -0 $P 2>/dev/null; do
    T=$(python3 -c "import time;print(round(time.time()-$START,2))")
    C=$(ip netns exec c ss -tin "dport = :5201" | grep -o "cwnd:[0-9]*" | cut -d: -f2 | sort -n | tail -1)   # 取最大的，即数据连接
    [ -n "$C" ] && echo "$T $C" >> cwnd-$1.txt
    sleep 0.01
done
```

`-C` 指定拥塞控制算法。这个内核中可用的算法：

```bash
cat /proc/sys/net/ipv4/tcp_available_congestion_control
```

```
reno cubic
```

分别用 CUBIC（Linux 的默认算法）和 Reno 运行一次：

```

cwnd 从 10 开始（Linux 的初始拥塞窗口是 10 段），每过一个往返时间（约 54 毫秒）**翻一倍**：10、20、40、80、160。这个阶段叫**慢启动**，名字有点误导，它其实增长得很快（指数增长），「慢」是相对于一开始就全速发送而言的。前 0.3 秒 cwnd 一直是 10，那是 iperf3 在建立连接、交换参数。

慢启动一直持续到第一次丢包，或者 cwnd 达到慢启动阈值（ssthresh）。指数增长会冲得过头：Reno 这次在慢启动中 cwnd 最高冲到了 558，远超过路径能容纳的约 280，造成了大量的丢包，这也是 Reno 的重传次数（284）远多于 CUBIC（17）的一个原因。

### 3.4 Reno：加性增、乘性减

Reno 的曲线是规整的锯齿（每 0.25 秒取一个样本）：

```
1.00:140 1.25:145 1.50:150 1.75:155 2.00:160 ... 8.50:277 8.75:280 9.01:142 9.26:147
```

- **拥塞避免**：慢启动结束后，cwnd 每个往返时间只增加 1 段（线性增长）。0.25 秒约是 4.6 个往返时间，样本中每 0.25 秒增加 4～5，和这个规则一致；
- **快速恢复**：通过重复确认发现丢包时，cwnd **减半**（280 → 140、280 → 142），然后继续线性增长。如果是超时重传，则认为网络状况很差，cwnd 直接降到 1，重新慢启动。

这种「每次加一个、出事就减半」的规则叫 **AIMD**（加性增、乘性减）。它有一个很好的性质：多个连接共享同一个瓶颈时，它们的速度会逐渐趋于均等，所以是公平的。

### 3.5 CUBIC

CUBIC 的样本：

```
2.50:262 2.75:268 3.00:272 3.25:276 3.50:280 3.75:198 4.00:204 ... 6.76:238 7.00:238 7.25:239 7.50:239 7.75:239 8.00:239 8.26:240 8.51:242 8.76:244 9.00:247
```

和 Reno 的不同：

- 丢包时只减到原来的 **70%**（280 → 198），而不是一半，带宽损失更小；
- 之后的增长不是一条直线，而是一条三次曲线：先快速回升，接近上次丢包时的窗口（约 239）时**放慢**，在那附近停留一段时间（7.00～8.00 秒几乎不变），然后再加速向上试探。它的增长只取决于距离上次丢包过去了多少时间，而不取决于往返时间，所以在高带宽、长延迟的网络上比 Reno 恢复得快得多。

结果：CUBIC 的吞吐量 46.6 Mbit/s，接近 50 Mbit/s 的带宽，只重传了 17 段；Reno 41.8 Mbit/s，重传了 284 段，每次减半后要花好几秒才能线性地爬回来，期间链路没有被填满（每秒的吞吐量中有两秒只有 34.6 Mbit/s）。

### 3.6 BBR

Google 提出的 **BBR** 换了一种思路：它不等到丢包才减速，而是持续测量路径的带宽和最小往返时间，按照估计出的带宽时延积来控制发送量，在有随机丢包的网络（比如无线网络）上表现更好。这台机器的内核没有加载 BBR 的模块（可用的只有 reno 和 cubic），所以没有实测。在支持的系统上，可以用 `sysctl -w net.ipv4.tcp_congestion_control=bbr` 切换。

## 4. 常见误区

1. **以为发送速度只取决于带宽**：实际的发送量受接收窗口和拥塞窗口共同限制，还取决于往返时间。同样的窗口，往返时间越长，速度越慢。
2. **以为丢包一定是网络出了故障**：对 TCP 来说，适度的丢包是正常的，它正是靠丢包来探测网络的容量。
3. **以为慢启动很慢**：它是指数增长，每个往返时间翻倍。
4. **接收方的程序读得慢，却去优化网络**：用 `ss -tn` 看接收队列（Recv-Q），如果一直很大，瓶颈在接收方的程序。
5. **以为路由器的缓冲区越大越好**：缓冲区太大会让包在队列中排很久，延迟变得很高（缓冲区膨胀，bufferbloat），TCP 却迟迟收不到丢包的信号。

## 5. 小结

- 发送窗口 = min(接收窗口, 拥塞窗口)；流量控制保护接收方，拥塞控制保护网络
- 接收方通过窗口字段通告剩余的缓冲区；实测接收方暂停时窗口降为 0，发送方停止并发送零窗口探测（间隔 0.27、0.51、0.99、1.99 秒），恢复后一个字节都没有丢
- 慢启动：cwnd 从 10 开始，每个往返时间翻倍（实测 10、20、40、80、160）
- Reno：拥塞避免时每个往返时间加 1，丢包时减半，形成锯齿
- CUBIC：丢包时减到 70%，按三次曲线增长，在上次丢包的窗口附近放慢；实测 46.6 Mbit/s，Reno 41.8 Mbit/s
- 带宽时延积决定了填满一条路径需要多大的窗口；`ss -ti` 可以看到每个连接的 cwnd、rtt、重传等信息

## 6. 练习

1. 一条路径的带宽是 100 Mbit/s，往返时间是 100 ms。要充分利用带宽，窗口至少要多大？如果没有窗口扩大选项（窗口最大 65535 字节），最多能达到多少速度？
2. 用 `ss -ti` 查看一个正在传输数据的连接，输出中的 `rto`、`rtt`、`cwnd`、`ssthresh`、`retrans` 分别表示什么？
3. 为什么超时重传时 cwnd 降到 1，而快速重传时只减半？

1. 带宽时延积 = 100 Mbit/s × 0.1 s = 10 Mbit = **1.25 MB**，窗口至少要这么大，才能在等待第一个确认回来之前一直发送。如果窗口最大只有 65535 字节，每个往返时间最多发送 65535 字节，速度最多是 65535 × 8 / 0.1 ≈ **5.2 Mbit/s**，只有带宽的 5%。这就是 TCP 需要窗口扩大选项（第 2.2 篇握手中的 `wscale`）的原因。

   ```
   rto:252 rtt:51.255/0.195 mss:1448 cwnd:204 ssthresh:197 bytes_retrans:24616 retrans:0/17 minrtt:50.304

   - `ssthresh:197`：慢启动阈值，上次丢包时设定的。cwnd 低于它时慢启动，高于它时拥塞避免。cwnd 204 刚刚超过 197，说明连接正处于丢包后的拥塞避免阶段；

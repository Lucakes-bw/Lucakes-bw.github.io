> **本文目标**：理解 B+ 树的结构，以及它为什么适合放在磁盘上；理解聚簇索引（主键索引）和二级索引的区别；理解回表和覆盖索引；会估算一次查询要读多少个页。
>
> **前置知识**：上一篇《InnoDB 的存储结构》；数据结构专栏的二叉搜索树和平衡树（《AVL 树》）。
>
> **实验环境**：MySQL 8.4.13（Docker），缓冲池 128 MB。测试表 `t` 和上一篇相同：100 万行，主键 `id` 从 1 到 1000000，每行约 140 字节；`k` 是 1～1000002 之间互不相同的整数（`k = id × 7919 mod 1000003`），和 `id` 的顺序无关。

## 1. 为什么是 B+ 树

数据结构专栏讲过，在有序的数据中查找，二叉搜索树（平衡时）需要比较 log₂n 次。100 万个数，log₂(1000000) ≈ 20，比逐个比较的 100 万次少得多。

但数据库的数据在磁盘上。如果二叉树的每个节点是一个页，找一行就要读 20 个页。从固态硬盘随机读一页大约 0.1 毫秒，机械硬盘大约 10 毫秒，20 次就是 2 毫秒到 200 毫秒，而在内存中比较 20 次只需要不到 1 微秒。**读页的次数**才是关键。

既然每次读磁盘都要读一整页（16 KB），那就让每个节点尽量大，在一个节点中放尽可能多的键，每个节点有成百上千个孩子。树的每一层能把范围缩小到几百、几千分之一，几层就够了。这就是 **B+ 树**：

- 数据（完整的行）只放在最底层的**叶子节点**中；
- 上层的节点只放「键 + 子节点的位置」，用来指路，所以一个节点能放很多键，树很矮；
- 叶子节点按键的顺序连成链表，范围查询找到起点后，顺着链表往下读就行了。

上一篇已经看到了这棵树：100 万行的表，叶子页 9260 个，第 1 层 9 个页（平均每页 1029 条记录），根页 1 个。每个非叶子页能放一千多个「主键 + 页号」，叶子页能放 108 行，3 层能放的行数大约是：

```
1029 × 1029 × 108 ≈ 1.1 亿
```

也就是说，这个表即使有上亿行，按主键查一行也只要读 3 个页（再多才会增加到 4 层）。下面的演示用一棵很小的树（每个叶子页只有 3 行）展示查找的过程：

## 2. 实测：查一行读几个页

MySQL 会把读过的页缓存在内存中的**缓冲池**（buffer pool）里，再次用到时就不必读磁盘了。为了看到真实的磁盘读取，要清空缓冲池：关闭启动时自动加载上次缓存内容的功能，然后重启数据库。

MySQL 提供两个计数器：

- `Innodb_buffer_pool_read_requests`：**逻辑读**，向缓冲池请求一个页的次数，无论它是否在内存中；
- `Innodb_buffer_pool_reads`：**物理读**，缓冲池中没有、不得不从磁盘读的次数。

写一个脚本，执行每条查询前后读取这两个计数器，算出这条查询引起了多少次读取：

```bash reads.sh
#!/bin/bash
# 依次执行每条查询，显示它引起的磁盘页读取（Innodb_buffer_pool_reads 的增量）和逻辑读（read_requests 的增量）
r() { mysql -N -e "SELECT VARIABLE_VALUE FROM performance_schema.global_status WHERE VARIABLE_NAME = '$1'"; }
for q in "$@"; do
  a=$(r Innodb_buffer_pool_reads); b=$(r Innodb_buffer_pool_read_requests)
  out=$(mysql -N idx -e "$q" | head -3 | tr '\t\n' ' ')
  c=$(r Innodb_buffer_pool_reads); d=$(r Innodb_buffer_pool_read_requests)
  echo "磁盘读 $((c - a)) 页，逻辑读 $((d - b)) 次  ← $q  →  $out"
done
```

（实验环境中只有这个脚本在访问数据库，所以全局计数器的增量就是这条查询引起的。）重启后依次执行：

```
磁盘读 4 页，逻辑读 71 次  ← SELECT name FROM t WHERE id = 500000  →  user_0500000
磁盘读 0 页，逻辑读 3 次  ← SELECT name FROM t WHERE id = 500001  →  user_0500001
磁盘读 2 页，逻辑读 4 次  ← SELECT name FROM t WHERE id = 900000  →  user_0900000
```

- 第一次查询从磁盘读了 4 页：根页、第 1 层的一个页、叶子页，再加上打开这个表时读的 1 页。逻辑读的 71 次中，大部分是打开表时读取数据字典；
- 查 500001：它和 500000 在同一个叶子页中，3 个页都已经在缓冲池里了。**逻辑读正好 3 次**，就是树的 3 层，没有读磁盘；
- 查 900000：根页已经缓存，但它在另一个第 1 层的页下、另一个叶子页中，所以从磁盘读了 2 页。

按主键查一行，读的页数就等于树的层数。

## 3. 聚簇索引

InnoDB 的表数据本身就是按主键组织的一棵 B+ 树，叶子页中存的就是完整的行，这叫**聚簇索引**（clustered index）。主键索引就是表本身：

- 每个表都有聚簇索引。没有定义主键时，InnoDB 用第一个不允许为 `NULL` 的唯一索引；连这也没有，就自动生成一个隐藏的 6 字节行号作为主键；
- 行在叶子页中按主键排序，所以按主键的范围查询、按主键排序都很快，顺着叶子页的链表读就可以；
- 主键的选择会影响整个表的存储：上一篇看到，随机的主键让页只装满了 70%。

```
磁盘读 177 页，逻辑读 692 次  ← SELECT SUM(LENGTH(name)) FROM t WHERE id BETWEEN 1 AND 50000  →  600000
```

主键在 1 到 50000 之间的 5 万行，存放在连续的约 463 个叶子页中（每页 108 行），找到起点后沿链表读下去，只有 692 次逻辑读。

## 4. 二级索引

在 `k` 列上建一个索引：

```sql
CREATE INDEX idx_k ON t (k);
```

100 万行，用了 0.4 秒。这样建的索引叫**二级索引**（secondary index），它是另一棵 B+ 树：按 `k` 排序，叶子中存的不是完整的行，而是 **(k, 主键)**。用上一篇的脚本从根页出发，逐层遍历这棵树（根页的页号可以从 `information_schema.innodb_indexes` 中查到）：

```
== PRIMARY
层级 2：     1 页，共        9 条记录
层级 1：     9 页，共     9260 条记录
层级 0：  9260 页，共  1000000 条记录
== idx_k（根页 46）
层级 1：     1 页，共      832 条记录
层级 0：   832 页，共  1000000 条记录
```

MySQL 自己的统计（`mysql.innodb_index_stats` 中的 `n_leaf_pages`）也是 PRIMARY 9260 个叶子页、idx_k 832 个，和文件中数出来的一致。二级索引的每条记录只有 `k` 和 `id` 两个 4 字节的整数加上记录头，一个叶子页能放约 1200 条，所以 100 万条只要 832 页，2 层就够了，整个索引约 15 MB，而表本身约 145 MB。

### 4.1 回表

通过二级索引查一行：

```sql
SELECT name FROM t WHERE k = 500000;
```

1. 在 `idx_k` 中查找 `k = 500000`，在叶子中得到它的主键 `id = 511998`；
2. 拿着这个主键，到聚簇索引中再查一次，才得到 `name`。

第 2 步叫**回表**。二级索引的叶子中存的是主键而不是行在文件中的位置，因为行的位置会随着页分裂而改变，主键却不变；代价是每次都要再走一遍聚簇索引。

### 4.2 覆盖索引

如果查询需要的列在二级索引中都有，就不必回表。`idx_k` 中有 `k` 和 `id`：

```sql
SELECT id FROM t WHERE k = 500000;     -- 二级索引中就有 id，不用回表
SELECT name FROM t WHERE k = 500000;   -- name 只在完整的行中，要回表
```

这叫**覆盖索引**：索引「覆盖」了查询需要的所有列。只查一行时，差别是多读 3 个页；查很多行时，差别就大了。`k` 在 1 到 50000 之间的 5 万行，对应的 `id` 散布在整个表中：

```
磁盘读 0 页，逻辑读 61 次  ← SELECT SUM(k) FROM t WHERE k BETWEEN 1 AND 50000  →  1250025000
磁盘读 871 页，逻辑读 166413 次  ← SELECT SUM(LENGTH(name)) FROM t WHERE k BETWEEN 1 AND 50000  →  600000
磁盘读 2448 页，逻辑读 161659 次  ← SELECT SUM(LENGTH(name)) FROM t WHERE k BETWEEN 1 AND 50000  →  600000
```

（第一条之前，`idx_k` 的这 42 个叶子页已经被读进了缓冲池。后两条是同一条查询连续执行了两次。）

- 只用 `k`：在 `idx_k` 中找到起点，沿着叶子读完 5 万条，约 42 个叶子页，**逻辑读 61 次**，耗时显示为 0.00 秒；
- 要用 `name`：5 万条记录，每条都要回表走一遍聚簇索引的 3 层，**逻辑读 16 万多次**，耗时约 0.08 秒。

更糟的是磁盘读。这 5 万行散布在整个表的 9260 个叶子页中，而表有约 145 MB，比 128 MB 的缓冲池还大，放不下所有的页。第二次执行时，上一次读进来的页已经有很多被挤出去了，又从磁盘读了 2448 页。如果是机械硬盘，每次随机读约 10 毫秒，2448 次就是 24 秒。

回表的代价取决于回表的行数。查询要返回的行很多时，回表可能比直接扫描整个表还慢，这时优化器会放弃索引（下一篇会看到）。这也是 `SELECT *` 的另一个代价：只要选了索引中没有的列，就无法使用覆盖索引。

### 4.3 二级索引中的主键

每个二级索引的叶子中都存着主键。主键越长，所有的二级索引就越大。同样的 10 万行，分别用 `INT` 和 `CHAR(36)` 的 UUID 作主键，各在 `k` 上建一个索引：

```
+------------+------------+--------------+
| table_name | index_name | n_leaf_pages |
+------------+------------+--------------+
| t_int      | PRIMARY    |          175 |
| t_int      | idx_k      |          128 |
| t_uuid     | PRIMARY    |          393 |
| t_uuid     | idx_k      |          503 |
+------------+------------+--------------+
```

`idx_k` 本身只有一个 4 字节的 `k`，换成 UUID 主键后，每条记录要多存 36 字节的主键，叶子页从 128 个增加到 503 个，接近 4 倍。表上有几个二级索引，就要多付几次这样的代价。主键应该**短**，并且**递增**。

## 5. 索引的代价

索引让查询变快，但不是免费的：

- **空间**：每个索引都是一棵完整的 B+ 树。`idx_k` 约占 15 MB；一个包含字符串列的索引会大得多；
- **写入变慢**：插入一行，要在聚簇索引中插入，还要在每个二级索引中各插入一条；修改被索引的列，要在索引中删除旧的记录、插入新的记录；
- **二级索引的插入是随机的**：主键递增时，聚簇索引总是在最右边追加，但 `k` 的值是随机的，`idx_k` 的插入会落到各个叶子页中，引起页分裂。（InnoDB 用「插入缓冲」把对不在缓冲池中的二级索引页的修改先攒起来，以后再合并，减少随机读写。）

所以索引要按查询的需要建，不是越多越好。下一篇用 `EXPLAIN` 看查询是否用上了索引，第 3.4 篇讨论什么样的查询能用上索引。

## 6. 常见错误

- **以为索引存的是行的地址**：InnoDB 的二级索引存的是主键，查其他列要回表；
- **`SELECT *`**：用不上覆盖索引，回表的行多时非常慢；
- **用长的、随机的值作主键**：所有的二级索引都跟着变大，插入时页分裂；
- **建很多用不上的索引**：占空间，拖慢写入；
- **只看逻辑上的「找到一行」**：真正的代价是读了多少个页、其中多少要读磁盘。

## 7. 小结

- B+ 树的节点是页，上层只存「键 + 子页号」，一个页能放上千个，树很矮：100 万行 3 层，估算 1 亿行也只要 3 层
- 叶子页按键排序并且连成链表，适合范围查询和排序
- 实测：缓冲池为空时，按主键查一行从磁盘读 3 页（加上打开表的 1 页）；缓存后逻辑读正好 3 次
- 聚簇索引的叶子是完整的行，主键就是表本身；二级索引的叶子是（索引列，主键）
- 通过二级索引查其他的列要回表；索引包含所有需要的列时不用回表（覆盖索引）。实测 5 万行：覆盖 61 次逻辑读，回表 16 万多次
- 主键越长，二级索引越大：UUID 主键让 idx_k 大了近 4 倍

## 8. 练习

1. 如果用二叉搜索树存 100 万行，每个节点一个页，查一行最少要读多少个页？如果是一棵每个节点有 100 个孩子的树呢？
2. 表 `t` 有主键 `id` 和二级索引 `idx_k`。下面哪些查询不需要回表？
   - `SELECT id, k FROM t WHERE k = 10`
   - `SELECT COUNT(*) FROM t WHERE k > 900000`
   - `SELECT * FROM t WHERE k = 10`
   - `SELECT k FROM t WHERE id = 10`
3. 这个表一页 108 行、非叶子页一页约 1029 条记录。如果表有 2 亿行，树有几层？按主键查一行要读几个页？

1. 平衡的二叉搜索树，高度至少是 ⌈log₂(1000001)⌉ = 20，大部分行都在最下面几层，查一行要读将近 20 个页。每个节点有 100 个孩子的树，100³ = 100 万，3 层就够了。B+ 树把一个节点做成一页，每页放上千个键，把读页的次数降到了 3、4 次。

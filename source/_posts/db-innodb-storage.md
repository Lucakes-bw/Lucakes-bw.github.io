## 1. 为什么要了解存储结构

第 1 章只把数据库当作一个黑盒：发出 SQL，拿回结果。要回答下面这些问题，就必须打开它看一看：

- 为什么在 100 万行中按主键查一行，几乎和在 10 行中查一样快？
- 为什么建议用自增整数作主键，而不是 UUID？
- 为什么 `SELECT *` 比只选需要的列慢？
- 索引到底是什么，为什么有时候用不上？

这一章从最底层开始：数据在文件中是怎样存放的。

## 2. 表空间和页

MySQL 默认的存储引擎是 **InnoDB**。每个表的数据和索引都放在数据目录中的一个文件里，叫作**表空间**（tablespace），扩展名是 `.ibd`。

InnoDB 读写磁盘的最小单位是**页**（page），默认 16 KB。即使只读一行，也要把这一行所在的整个页读进内存；修改一行，最终也是把整个页写回磁盘。所以表空间文件就是一个个 16 KB 的页依次排列，第 n 页从文件的第 n × 16384 字节开始。

### 2.1 解析 .ibd 文件

每一页的开头都有 38 字节的**文件头**（FIL header），其中有这一页的编号、前一页和后一页的编号、页的类型。INDEX 类型的页（存放表中的数据和索引）在文件头之后还有页头，记录这一页的层级、记录数和所属的索引。写一个脚本把它们读出来：

```python ibd.py
#!/usr/bin/env python3
"""ibd.py：读一个 InnoDB 表空间文件（.ibd），列出每一页的类型；INDEX 页再显示层级、记录数和索引编号"""
import struct, sys
from collections import Counter

PAGE = 16384
TYPES = {0: 'ALLOCATED（未使用）', 2: 'UNDO_LOG', 3: 'INODE', 5: 'IBUF_BITMAP', 7: 'TRX_SYS',
         8: 'FSP_HDR（文件头）', 9: 'XDES', 10: 'BLOB', 17853: 'SDI（表结构）', 17855: 'INDEX（索引页）'}

def pages(path):
    with open(path, 'rb') as f:
        no = 0
        while True:
            p = f.read(PAGE)
            if len(p) < PAGE:
                return
            yield no, p
            no += 1

def index_info(p):
    n_recs, = struct.unpack('>H', p[54:56])
    level, = struct.unpack('>H', p[64:66])
    index_id, = struct.unpack('>Q', p[66:74])
    return n_recs, level, index_id

def main():
    path, mode = sys.argv[1], (sys.argv[2] if len(sys.argv) > 2 else 'list')
    stats = Counter()
    for no, p in pages(path):
        page_no, prev, nxt = struct.unpack('>III', p[4:16])
        ptype, = struct.unpack('>H', p[24:26])
        name = TYPES.get(ptype, str(ptype))
        if ptype == 17855:
            n_recs, level, index_id = index_info(p)
            stats[(index_id, level)] += 1
            stats[('recs', index_id, level)] += n_recs
            if mode == 'list':
                pv = '-' if prev == 0xFFFFFFFF else prev
                nx = '-' if nxt == 0xFFFFFFFF else nxt
                print(f'第 {no:>3} 页  {name}  索引 {index_id}  层级 {level}  记录数 {n_recs:>3}  上一页 {pv}  下一页 {nx}')
        else:
            stats[name] += 1
            if mode == 'list':
                print(f'第 {no:>3} 页  {name}')
    if mode == 'summary':
        for k in sorted((k for k in stats if isinstance(k, tuple) and k[0] != 'recs'), key=lambda k: (k[0], -k[1])):
            print(f'索引 {k[0]}  层级 {k[1]}：{stats[k]:>6} 页，共 {stats[("recs",) + k]:>8} 条记录')
        for k in stats:
            if isinstance(k, str):
                print(f'{k}：{stats[k]} 页')

main()
```

InnoDB 文件中的整数都是**大端序**，所以用 `struct.unpack('>…')` 读取。

数据库运行时，修改过的页可能还在内存中，没有写回文件。复制文件前先执行 `FLUSH TABLES 表名 FOR EXPORT`，它把这个表所有修改过的页写回磁盘，并在这个会话结束前禁止修改这个表，这时复制出的文件才是完整一致的。（这只用于实验观察，备份要用 5.2 篇的方法。）

### 2.2 空表

建一个测试表：

```sql
CREATE TABLE t (
    id   INT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    k    INT UNSIGNED NOT NULL,
    name VARCHAR(20) NOT NULL,
    note CHAR(100) NOT NULL DEFAULT ''
);
```

还没有插入任何数据，解析它的文件：

```
文件大小：114688 字节，7 页
第   0 页  FSP_HDR（文件头）
第   1 页  IBUF_BITMAP
第   2 页  INODE
第   3 页  SDI（表结构）
第   4 页  INDEX（索引页）  索引 318  层级 0  记录数   0  上一页 -  下一页 -
第   5 页  ALLOCATED（未使用）
第   6 页  ALLOCATED（未使用）
```

这就是第 1 章中「3 行数据的表也有 112 KB」的原因：

- 第 0 页记录整个表空间的信息，以及哪些页已经使用；
- 第 1 页是插入缓冲的位图，第 2 页记录「段」（下面会说）的信息；
- 第 3 页存放表的定义（列名、类型等），MySQL 8.0 起表结构就保存在表空间中；
- 第 4 页是主键索引的**根页**，现在是空的。表中的数据就从这一页开始存放；
- 第 5、6 页预先分配，还没有使用。

文件变大时，InnoDB 起初每次多分配几页，文件超过一定大小后，就按**区**（extent）分配：一个区是连续的 64 页，即 1 MB。连续分配的好处是，按顺序读一个表时，相邻的页在磁盘上也大多是相邻的。

## 3. 一行数据长什么样

插入一行，再看第 4 页中的字节：

```sql
INSERT INTO t (k, name, note) VALUES (12345, 'lucky', 'hi');
```

用 `od` 显示第 4 页从第 94 字节开始的内容（文件中的偏移量是 4 × 16384 + 94 = 65630）：

```
0065630    01  00  02  00  1c  69  6e  66  69  6d  75  6d  00  02  00  0b
0065646    00  00  73  75  70  72  65  6d  75  6d  64  05  00  00  10  ff
0065662    f1  00  00  00  01  00  00  00  00  3c  b0  81  00  00  01  10
0065678    01  10  00  00  30  39  6c  75  63  6b  79  68  69  20  20  20
0065694    20  20  20  20  20  20  20  20  20  20  20  20  20  20  20  20
*
0065774    20  20  20  20  20  20  20  20  20  20  20  20  20  20  20  00
```

（`*` 表示省略了和上一行相同的若干行。）逐段拆开：

| 页内偏移 | 字节 | 含义 |
|---|---|---|
| 94～98 | `01 00 02 00 1c` | infimum 记录的头部，最后两字节 `00 1c` = 28：下一条记录在 99 + 28 = 127 |
| 99～106 | `69 6e 66 …` | `infimum`，页中「最小」的虚拟记录 |
| 107～111 | `02 00 0b 00 00` | supremum 记录的头部 |
| 112～119 | `73 75 70 72 …` | `supremum`，页中「最大」的虚拟记录 |
| 120 | `64` | 变长列 `note` 的长度：100 |
| 121 | `05` | 变长列 `name` 的长度：5 |
| 122～126 | `00 00 10 ff f1` | 这一行的头部，最后两字节 `ff f1` = -15：下一条记录在 127 - 15 = 112，即 supremum |
| 127～130 | `00 00 00 01` | `id` = 1 |
| 131～136 | `00 00 00 00 3c b0` | 隐藏列 `DB_TRX_ID`：插入这一行的事务编号 |
| 137～143 | `81 00 00 01 10 01 10` | 隐藏列 `DB_ROLL_PTR`：回滚指针，指向 undo 日志 |
| 144～147 | `00 00 30 39` | `k` = 0x3039 = 12345 |
| 148～152 | `6c 75 63 6b 79` | `name` = `lucky` |
| 153～252 | `68 69 20 20 …` | `note` = `hi`，后面补了 98 个空格 |

几点值得注意：

- **每一行都比你定义的列多出不少字节。** 5 字节的记录头，加上两个隐藏列：6 字节的事务编号和 7 字节的回滚指针。它们是事务和多版本并发控制的基础（4.2 篇）。这里定义的四列共 4 + 4 + 5 + 100 = 113 字节，实际占了 113 + 2 + 5 + 13 = 133 字节；
- **变长列的长度存在记录头前面，并且是倒序的**（先 `note` 再 `name`）。所有列都是 `NOT NULL`，所以没有记录哪些列为 `NULL` 的位图；
- **`CHAR(100)` 真的占了 100 字节**，`hi` 只有 2 字节，剩下的用空格补齐。下一节会看到这对一页能放多少行的影响；
- **页中的记录用单向链表连起来**，按主键从小到大的顺序：infimum → 第 1 行 → supremum。每条记录的头部保存「到下一条记录的距离」。插入一行时，只需要把它挂进链表的合适位置，不必移动其他的行。

链表只能从头往后找，一页有一百多条记录时，逐条比较太慢。所以页的末尾还有一个**页目录**：每隔 4～8 条记录取一条作为「槽」，记录它的位置。在页中查找一个主键时，先在槽中二分查找，确定在哪一组，再在组内沿链表找几步。

## 4. 页满了会怎样

### 4.1 一页能放多少行

继续插入，每次插一行，看第 4 页的记录数（同样的表结构，`name` 是 `user_0000001` 这样的 12 个字符，`note` 是 `x`）：

```
101 行：L0:101
102 行：L0:102
...
108 行：L0:108
109 行：L1:2 L0:54 L0:55
```

（`L0:108` 表示一个层级为 0 的页，有 108 条记录。）这个表一页最多放 108 行。每行约 140 字节，108 行是 15 KB 左右：InnoDB 不会把页完全装满，而是留出大约 1/16 的空间，供以后修改这些行（例如把变长的列改长）时使用，避免一修改就要分裂。

### 4.2 页分裂

第 109 行插入时，第 4 页放不下了，发生了**页分裂**：

```
第   4 页  INDEX（索引页）  索引 318  层级 1  记录数   2  上一页 -  下一页 -
第   5 页  INDEX（索引页）  索引 318  层级 0  记录数  54  上一页 -  下一页 6
第   6 页  INDEX（索引页）  索引 318  层级 0  记录数  55  上一页 5  下一页 -
```

- 原来的 109 行被分到两个新页（第 5、6 页）中，各一半；
- 第 4 页没有消失，而是变成了**层级 1**的页，只有 2 条记录：分别指向第 5 页和第 6 页，记录的是「第 5 页从哪个主键开始」「第 6 页从哪个主键开始」；
- 第 5、6 页通过「上一页」「下一页」连成了双向链表。

层级为 0 的页叫**叶子页**，存放完整的行；层级更高的页只存放「主键 + 子页的页号」，用来指路。这就是一棵树：第 4 页是根，第 5、6 页是叶子。根页的页号始终不变，所以 InnoDB 只需要记住根在第 4 页，就能找到整棵树。

再插入到 200 行：

```
第   4 页  INDEX（索引页）  索引 318  层级 1  记录数   3  上一页 -  下一页 -
第   5 页  INDEX（索引页）  索引 318  层级 0  记录数  54  上一页 -  下一页 6
第   6 页  INDEX（索引页）  索引 318  层级 0  记录数 108  上一页 5  下一页 7
第   7 页  INDEX（索引页）  索引 318  层级 0  记录数  38  上一页 6  下一页 -
```

第 6 页被装到了 108 行，然后新开了第 7 页，并没有再对半分。InnoDB 发现插入一直发生在最右边（主键递增），就不再对半分裂，而是让左边的页保持装满，直接在右边开一个新页。这对自增主键非常友好：除了第一次分裂的第 5 页，每个叶子页都是满的。

### 4.3 100 万行

插入 100 万行（约 1.4 秒），文件变成了 156 MB。按层级统计所有的 INDEX 页：

```
文件大小：163577856 字节，9984 页
索引 321  层级 2：     1 页，共        9 条记录
索引 321  层级 1：     9 页，共     9260 条记录
索引 321  层级 0：  9260 页，共  1000000 条记录
ALLOCATED（未使用）：710 页
```

（索引的编号变了，是因为重新建了表。）100 万行是一棵 3 层的树：

- 9260 个叶子页，平均每页 108 行；
- 9 个第 1 层的页，每页约 1029 条记录，每条指向一个叶子页；
- 1 个根页，9 条记录，每条指向一个第 1 层的页。

从根出发，按主键找一行，只要读 3 个页：在根页中找到该去哪个第 1 层的页，在第 1 层的页中找到该去哪个叶子页，在叶子页中找到这一行。下一篇详细讨论这棵 B+ 树。

## 5. 小结

- InnoDB 的表存放在 `.ibd` 表空间文件中，由 16 KB 的页组成；页是读写磁盘的最小单位
- 空表也有 7 页：文件头、位图、段信息、表结构、一个空的根页
- 每一行除了定义的列，还有 5 字节的记录头和两个隐藏列（6 字节的事务编号、7 字节的回滚指针）；变长列的长度倒序存在记录头前面；`CHAR(n)` 会补齐到 n 字节
- 页中的记录用链表按主键排序，页目录支持二分查找
- 页满时分裂，根页变成上一层；叶子页存放完整的行，非叶子页存放「主键 + 子页号」，叶子页之间是双向链表
- 实测：这个表一页 108 行，100 万行是 3 层的树，按主键查找只读 3 个页

   ```
   索引 324  层级 2：     1 页，共        2 条记录
   索引 324  层级 1：     2 页，共     1320 条记录
   索引 324  层级 0：  1320 页，共   100000 条记录
   ```

   随机插入时，新的行会插到已经满了的页的中间，页只能对半分裂，分裂出的两个页都只有一半满，之后可能再也填不满。结果叶子页从 927 个增加到 1320 个，平均每页只有 76 行（装满了约 70%），文件大了 45%，树还多了一层。此外，每次分裂都要移动一半的数据、修改上层的页，插入本身也更慢。UUID 这样的随机值作主键就是这种情况，所以 InnoDB 推荐使用递增的主键（第 2 章《范式与表设计》第 5 节）。
3. 把符号位取反：1 存成 `80 00 00 01`，-1（补码 `ff ff ff ff`）存成 `7f ff ff ff`，0 存成 `80 00 00 00`。这样按字节从左到右比较，-1 < 0 < 1，和数值的大小顺序一致。InnoDB 对有符号整数正是这样存储的，于是比较主键时可以直接比较字节，不用关心类型。

> **本文目标**：知道「换乘」为什么不能简单地当成边的权重；学会把问题建模成一张新的图（状态图）；在状态图上实现堆优化的 Dijkstra，并还原路线；体会 O(V²) 和 O((V + E) log V) 在一万个车站时的差别。
>
> **前置知识**：《最短路径》（Dijkstra）、《堆与优先队列》。需要先完成[里程碑 2](/posts/ds-project-metro-m2/)。

## 1. 要做什么

这个里程碑增加两个命令。

**`fastest <起点> <终点>`：用时最少的路线**

```
metro> fastest 植物园 西站
植物园 → 西站：坐 7 站，换乘 2 次，用时 31 分钟（乘车 21 分钟，换乘 10 分钟）
  3号线：植物园 → 体育馆，2 站，7 分钟
  2号线：体育馆 → 南湖，3 站，7 分钟
  4号线：南湖 → 西站，2 站，7 分钟
```

和里程碑 2 的 `stops 植物园 西站` 比一比：那条路线只坐 6 站，但换乘 3 次，用时 32 分钟；这条多坐了 1 站，少换 1 次，31 分钟。

用时 = 乘车时间 + 换乘次数 × `TRANSFER_MINUTES`（5 分钟）。刚在起点上车不算换乘。

**`from <站名>`：从一个车站出发，到其他每个车站最少要多久**

```
metro> from 西山
从 西山 出发到各站的最短用时（换乘一次 5 分钟）：
  果园 3 分钟
  动物园 5 分钟
  人民广场 8 分钟
  市政府 10 分钟
  植物园 11 分钟
  ……
  港口 23 分钟
  西站 27 分钟
```

按用时从少到多排列，用时相同的按车站编号排列（这一步由 `main.c` 完成）。到达不了的车站显示「无法到达」，排在最后。

要实现的是 `route.c` 中的两个函数：

```c
int routeFastest(const Metro* m, int from, int to, Route* r);   // 返回值和 routeFewestStops 相同
int routeAllTimes(const Metro* m, int from, int* minutes);      // minutes[s]：到车站 s 的最短用时，到不了是 -1；返回 0
```

用时最少的路线也可能不止一条。比如从南湖到会展中心，「2号线 → 1号线 → 3号线」和「4号线 → 3号线」都是 17 分钟。这时返回哪一条都算对，**测试中只使用最短路线只有一条的起点和终点**。

## 2. 把换乘放进图里

### 2.1 直接在车站图上做 Dijkstra，会错在哪里

最直接的想法是：图还是里程碑 1 建好的那张，每个车站是一个顶点，用 Dijkstra 求最短时间；松弛一条边时，如果这条边的线路和「到达这个车站时坐的线路」不同，就多加 5 分钟。

这个想法很自然，但它是**错的**。看从港口到老街的例子：

<div class="dsviz" data-viz="metro-trap"></div>

圆圈里的数字是到达这个车站时坐的线路，下面是站名和 dist。这个算法得出 20 分钟，而正确答案是 16 分钟：

```
港口 → 老街：坐 4 站，换乘 1 次，用时 16 分钟（乘车 11 分钟，换乘 5 分钟）
  4号线：港口 → 东湖，1 站，2 分钟
  3号线：东湖 → 老街，3 站，9 分钟
```

问题出在市政府。到市政府有两种方法：

- 4号线到东门，换 1号线：2 + 3 + 5 + 3 = **13** 分钟，到达时在 1号线上；
- 4号线到东湖，换 3号线：2 + 5 + 4 + 3 = **14** 分钟，到达时在 3号线上。

每个车站只能记一个 dist，算法留下了更小的 13，扔掉了 14。可是老街在 3号线上：坐 1号线来的，还要再换乘一次，13 + 5 + 2 = 20；坐 3号线来的，不用换乘，14 + 2 = 16。**先到达的不一定更好，还要看是在哪条线上到达的。**

Dijkstra 正确的前提是：一个顶点的最短距离确定以后，从它出发的边的代价和「是怎么到达它的」无关。这里换乘的 5 分钟恰恰取决于是怎么到达的，前提不成立了。在示例城的 462 对车站中，这种做法算错了 62 对。

### 2.2 状态图：把「在哪条线上」也变成顶点的一部分

既然「在哪条线上」会影响后面的代价，就把它放进顶点里：新图的每个顶点是一个**状态**（车站，线路），表示「人在这个车站，在这条线路的站台上」。

- 只有一条线路经过的车站，只有一个状态，比如（港口，4号线）；
- 换乘站有几条线路经过，就有几个状态，比如东湖有（东湖，3号线）和（东湖，4号线）两个。

状态之间有两种边：

| 边 | 从 | 到 | 代价 |
|---|---|---|---|
| 坐一站 | （s，L） | （t，L），s 和 t 在线路 L 上相邻 | 这个区间的分钟数 |
| 换乘 | （s，L1） | （s，L2），同一个车站的另一条线路 | `TRANSFER_MINUTES` |

换乘变成了一条普通的边，权重固定是 5 分钟，和「是怎么到达的」无关，Dijkstra 的前提又成立了。

示例城有 22 个车站，其中 7 个换乘站各有 2 条线路，所以一共 22 + 7 = 29 个状态；坐一站的边有 25 条（就是 25 个区间），换乘的边有 7 条。

起点和终点怎么办？起点车站的**每一个**状态代价都是 0（在起点可以直接选择坐哪条线，不算换乘）；终点车站的任何一个状态，最先被确定的那个就是答案。

下面是同一个例子在状态图上的运行过程。换乘站被拆成了两个圆圈，圆圈里是线路，标着「换5」的边是换乘：

<div class="dsviz" data-viz="metro-states"></div>

（东湖，3号线）和（东湖，4号线）、（市政府，1号线）和（市政府，3号线）现在各有各的代价：在市政府，1号线的那个是 13，3号线的那个是 14，两个都保留了下来，最后从 14 走到老街，得到 16。

### 2.3 从状态的答案回到车站的答案

- `routeFastest`：终点的状态第一次从堆中取出时停下，沿着前驱还原路线。前驱链上的一步，要么是坐一站（车站变了），要么是换乘（车站没变）。只有车站变了的那些步，才是 `Route` 中的一站。
- `routeAllTimes`：不提前停下，求出到所有状态的最短用时。一个车站的答案是它的几个状态中最小的那个。

### 3.1 给状态编号

Dijkstra 需要 `dist[v]` 这样的数组，所以状态也要有整数编号。参考实现让每个车站的状态编号连在一起：

```c
typedef struct {
    int* first;         // 车站 s 的状态是 first[s] .. first[s+1]-1
    int* station;       // station[v]：状态 v 在哪个车站
    int* line;          // line[v]：状态 v 在哪条线路上
    int n;              // 状态的个数
} States;
```

示例城中，西山（车站 0）只有一个状态 0；果园（车站 1）有两个状态 1、2，分别是 1号线和 3号线；动物园（车站 2）是状态 3……

建立的方法：依次看每个车站的邻接表，每出现一条新的线路，就增加一个状态。里程碑 1 中说过，同一条线路的边在邻接表中是挨着的，所以只要和前一条边比较线路就能去重，`main.c` 中的 `stationLines` 就是这样做的。

要从（车站，线路）找到状态编号，在 `first[s]` 到 `first[s+1]-1` 之间顺序查找就可以了，一个车站最多只有几条线路。

<details>
<summary>提示：为什么不用 s * nlines + line 作为编号</summary>

这样编号最简单，不需要 `first` 数组，也不用查找。但大部分（车站，线路）组合根本不存在：示例城有 22 × 4 = 88 个编号，只用到 29 个。一个有 500 个车站、20 条线路的城市，要 10000 个编号，而实际的状态只有六七百个。每次查询都要初始化这么大的 `dist` 数组，就浪费了。

</details>

状态图的边**不需要真的建出来**。处理状态（s，L）时，「坐一站」的边就是 s 的邻接表中线路为 L 的那几条，「换乘」的边就是 s 的其他几个状态，现场算出来就行。

### 3.2 堆

用《堆与优先队列》中的二叉堆（最小堆），元素是（用时，状态）。

和《最短路径》一文一样，更新了一个状态的 dist 以后，**不去修改堆中原来的元素**，而是把新的（用时，状态）再放进堆里。同一个状态可能在堆中出现好几次，取出时如果发现它已经确定过了，就跳过。这种做法叫**懒删除**，比实现「减小某个元素的键值」简单得多，堆的大小最多是边的条数。

堆的数组要能扩容，因为事先不知道会放进多少个元素。

### 3.3 Dijkstra

```c
// 从车站 from 的所有状态出发，算出到每个状态的最短用时 dist 和前驱 prev。
// to >= 0 时，第一次从堆中取出车站 to 的状态就停下，返回这个状态；否则算完所有状态，返回 -1。
static int dijkstra(const Metro* m, const States* g, int from, int to, int* dist, int* prev);
```

步骤和 2.2 节的演示完全相同：

1. 所有状态的 dist 设为「无穷大」（`INT_MAX`），prev 设为 -1；起点车站的每个状态 dist 设为 0，放进堆；
2. 从堆中取出用时最小的状态 v。已经确定过就跳过；否则标记为确定。如果 v 在终点，停下；
3. 沿着 v 的线路坐一站，以及在 v 的车站换乘，用 `dist[v] + 代价` 去更新对方的 dist，更新成功就记下前驱并入堆。

<details>
<summary>提示：为什么要在「取出」时判断终点，而不是「放进」时</summary>

放进堆的时候，这个代价还不一定是最终的。比如上面的例子中，（老街，3号线）第一次被放进堆时代价是 16，但如果还有别的路更快，后面还会被更新。只有从堆中**取出**时，它才是所有剩下的状态中最小的，不可能再被更新。

</details>

<details>
<summary>提示：INT_MAX 加上分钟数会溢出</summary>

用 `INT_MAX` 表示无穷大时，不要对它做加法。参考实现只从已经确定的状态出发去更新别的状态，确定的状态的 dist 一定不是无穷大，所以不会溢出。如果你在别的地方用 `dist[v] + w` 和别的值比较，要先确认 `dist[v]` 不是 `INT_MAX`，否则 `-fsanitize=undefined` 会报告 `signed integer overflow`。

</details>

### 3.4 还原路线

终点状态 `target` 找到以后，沿着 `prev` 往回走到起点的某个状态（它的 `prev` 是 -1）。和里程碑 2 一样，先数出车站的个数，再从后往前填：

- `prev[v]` 和 v 在同一个车站：这是一次换乘，跳过；
- 不在同一个车站：这是坐了一站，`stations[i]` 是 v 的车站，`lines[i]` 是 v 的线路。

## 5. 常见错误

1. **在车站图上做 Dijkstra，再根据「到达时的线路」加换乘时间**。2.1 节已经说明了为什么错，测试 `02-fastest-state` 会失败。
2. **在起点也算了一次换乘**。只把起点的一个状态（比如第一条线路）设为 0，其他状态要通过「换乘」边才能到达，从起点坐其他线路时就多算了 5 分钟。
3. **把换乘边连到了别的车站**。换乘边只连接同一个车站的不同状态。
4. **放进堆时就判断终点**。见 3.3 节的提示：如果后面还能找到更快到达终点的路线，结果就错了。
5. **没有跳过过时的元素**。结果通常还是对的，但同一个状态会被处理很多次，大数据测试可能超时。
6. **还原路线时把换乘也算成了一站**。`main.c` 会报告某两站「不相邻」：一个车站和它自己显然不相邻。
7. **每次查询都没有释放状态图和堆**。`from` 和 `top`（里程碑 5）会对每个车站各调用一次，泄漏会很快累积起来。

## 6. 思考题

1. 现实中，不同车站的换乘时间并不相同：有的换乘站是同站台换乘，1 分钟就够了；有的要走很长的通道。如果要支持每个车站、每对线路都有自己的换乘时间，数据格式和状态图要怎么改？
2. 有的乘客嫌换乘麻烦，愿意多坐几分钟车来少换一次。比如「换乘一次相当于多坐 10 分钟」，但显示的用时仍然是真实的时间。怎么实现？
3. 状态图的思路不只能用在地铁上。想一想：开车导航时，「左转比右转多等 30 秒」这种规则，要怎么放进图里？

<details>
<summary>点击查看答案</summary>

1. 可以在数据文件中增加一种行，比如 `TRANSFER 东湖 3号线 4号线 3`，表示在东湖从 3号线换到 4号线要 3 分钟（可以规定两个方向相同，也可以分开写）。没有写的，使用默认值 `TRANSFER_MINUTES`。状态图的结构完全不用变，只是换乘边的权重不再是常数，要查一张表。由于每个换乘站的线路很少，可以在 `States` 中为每个车站保存一个 k × k 的小矩阵。

2. 用两种「代价」：Dijkstra 比较的是「乘车时间 + 换乘次数 × 10」，而显示给用户的是「乘车时间 + 换乘次数 × 5」。也就是说，换乘边在 Dijkstra 中的权重是 10，但还原出路线以后，`main.c` 仍然按 5 分钟来计算用时。这和下一个里程碑的做法有相通之处：决定「哪条路线最好」的权重，不一定就是显示给用户的那个数。

3. 把「在哪个路口，从哪个方向来」作为状态：顶点是有向的道路（从路口 A 开到路口 B 的这一段），从一段道路转到下一段道路就是一条边，边的权重包括转弯的等待时间。这在图论中叫作**线图**（line graph），和地铁的状态图是同一个思路：当代价取决于「是怎么来的」，就把「怎么来的」放进顶点。

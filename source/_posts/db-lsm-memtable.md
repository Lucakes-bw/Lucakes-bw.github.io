> **本文目标**：理解内存表为什么必须是有序的；会用跳表实现内存表的插入、覆盖和查找；理解删除为什么要写墓碑，墓碑什么时候才能真正消失；理解内存表的大小怎样计算、写满以后落盘的步骤和顺序；知道同步落盘会让写入卡顿，真正的引擎怎样避免。
>
> **前置知识**：本章第 1 篇；《数据结构》专栏的《跳表》。
>
> **实验环境**：同第 1 篇。

## 1. 为什么要有序

内存表只需要支持查找的话，哈希表最快。但内存表写满以后要整个写成一个 SSTable，而 SSTable 是**按键排好序**的文件（第 3 篇）：有序，才能在文件中二分查找，才能在合并时像归并排序那样顺序地合并多个文件，才能支持范围查询。所以内存表本身就要有序，落盘时按顺序遍历一遍，直接写出去。

平衡树（红黑树）和跳表都可以。LevelDB、RocksDB 默认用跳表：实现简单，而且容易做成多个线程同时读、一个线程写都不需要加锁的版本。lsm-kv 的跳表和《跳表》一文中的基本相同，每升一层的概率是 1/4，最多 16 层：

```c
typedef struct Node {
    char* key;
    char* val;
    uint32_t klen, vlen;  // vlen == TOMBSTONE 表示删除
    int height;
    struct Node* next[];  // 每一层的后继
} Node;
```

键是任意的字节串，按字节比较（`memcmp`，短的在前）。

## 2. 同一个键写多次

插入时先像查找一样从高层往低层走，记下每一层的前驱；如果最底层的下一个节点就是这个键，**直接覆盖它的值**，不插入新节点：

```c
static void memPut(Mem* m, const char* k, uint32_t kl, const char* v, uint32_t vl)
{
    Node* update[SKIP_MAX];
    Node* x = m->head;
    for (int i = m->height - 1; i >= 0; i--) {
        while (x->next[i] && keyCmp(x->next[i]->key, x->next[i]->klen, k, kl) < 0) x = x->next[i];
        update[i] = x;
    }
    Node* hit = x->next[0];
    if (hit && keyCmp(hit->key, hit->klen, k, kl) == 0) {
        // 已经有这个键：替换值，内存表的大小加上新值、减去旧值
        ...
        return;
    }
    // 没有：随机决定高度，插入新节点
    ...
}
```

所以一个键在内存表中被改了一万次，落盘时也只写出最后一个值。频繁更新的「热点」键在内存表中就被合并掉了，这是 LSM 树的写入比想象中便宜的原因之一。

## 3. 删除：墓碑

内存表中的键，可能在更早的 SSTable 中也有旧值。如果删除时只是从内存表中摘掉节点，查找时内存表中找不到，就会继续往下查，找到那个旧值，**已经删除的数据又出现了**。

所以删除也是一次写入：写一条特殊的记录，值的长度为 `0xFFFFFFFF`，叫**墓碑**（tombstone），意思是「这个键在这里被删除了」：

```c
int lsmDelete(Lsm* db, const char* key, uint32_t klen) { return writeRecord(db, key, klen, NULL, TOMBSTONE); }
```

它和普通的写入一样进日志、进内存表、落盘到 SSTable。查找时，从新到旧，**先遇到墓碑就返回「不存在」**，不再往下查：

```c
Node* n = memFind(db->mem, key, klen);
if (n) {
    if (n->vlen == TOMBSTONE) return 0;   // 被删除了
    ...
}
```

墓碑本身也占空间。它什么时候能真正消失？只有合并到**最底层**，确定更深的地方不再有这个键的旧值时，才能丢掉（第 5 篇）。所以 LSM 树中大量删除的数据，要过一段时间才会真正释放空间；大量删除之后的扫描还会经过一大片墓碑，变慢。这是使用 RocksDB、Cassandra 时常见的问题。

第 1 篇的随机测试中，20% 的操作是删除，最后在第 2 层留下了 14308 条数据，和数组中记录的期望完全一致，说明墓碑正确地遮住了旧值。

## 4. 内存表有多大

`memtableBytes`（默认 4 MB）限制内存表的大小。计算大小时，不只算键和值，还要算节点本身：

```c
m->bytes += kl + vbytes + sizeof(Node) + sizeof(Node*) * (size_t)h;
```

`sizeof(Node)` 是 32 字节（两个指针、三个整数和对齐），每一层的后继指针 8 字节，平均高度约 1.33 层。一条 16 字节的键、100 字节的值，在内存表中约占 116 + 32 + 11 ≈ 159 字节，再加上 `malloc` 自己的开销（《malloc 是怎样分配内存的》）。实测 200 万次随机写入一共落盘了 75 次，平均每次约 2.7 万条，和 4 MB ÷ 159 字节 ≈ 2.6 万条对得上：**管理开销约 43 字节，占内存表的四分之一以上**。

如果只算键和值，内存表实际占用的内存会比设置的大很多；RocksDB 用一个专门的内存池（arena）分配节点，按池的大小计算，更准确，也避免了很多次小的 `malloc`。

## 5. 写满了：落盘

内存表写满以后：

```c
static void flushMemtable(Lsm* db)
{
    // 1. 按顺序遍历跳表，写成一个 L0 的 SSTable，fsync
    Builder b;
    builderStart(&b, db);
    for (Node* n = db->mem->head->next[0]; n; n = n->next[0]) builderAdd(&b, n->key, n->klen, n->val, n->vlen);
    Table* t = builderFinish(&b, 1);
    levelAppend(&db->levels[0], t);

    // 2. 换一个新的日志文件号，写清单
    uint64_t oldWal = db->walNumber;
    db->walNumber = db->nextFile++;
    writeManifest(db);

    // 3. 清单写好以后，旧的日志才可以删除
    close(db->walFd);
    unlink(旧日志);
    walOpen(db, 1);

    // 4. 换一个空的内存表，检查要不要合并
    memFree(db->mem);
    db->mem = memNew();
    maybeCompact(db);
}
```

顺序是关键：

1. SSTable 先写完并 `fsync`，这时它已经安全了，但清单中还没有它；如果此刻崩溃，下次打开时清单中没有这个文件、旧日志还在，从日志重放即可，多出来的文件只是一个没人引用的垃圾；
2. 清单记录了新文件和新日志以后，旧日志中的数据都已经在 SSTable 中了；
3. 这时才能删除旧日志。如果顺序反过来，先删日志再写清单，中间崩溃，这批数据就既不在日志中、也不在任何被引用的文件中，彻底丢失。

200 万次随机写入的结果（16 字节的键、100 字节的值，写入的数据共 221.3 MB）：

```
写入的数据 221.3 MB；WAL 244.1 MB，落盘 238.7 MB，……
落盘 75 次
```

日志比数据多了 10%（每条 12 字节的头），落盘写出的 SSTable 比数据多了 8%（每条 8 字节的头，加上索引和布隆过滤器）。平均每个 L0 文件 3.2 MB。

## 6. 落盘会让写入卡一下

lsm-kv 的落盘是**同步**的：触发落盘的那一次 `lsmPut`，要等 3 MB 多的文件写完、`fsync` 完才返回。按顺序写入 200 万条（这时没有合并，见第 5 篇），统计每次写入的耗时：

```
2000000 次，1.36 秒，每秒 1474406 次
超过 10 ms 的写 1 次，一共 0.01 秒；最慢的一次 14 ms
```

绝大多数写入不到 1 微秒，最慢的一次 14 毫秒，就是碰上了落盘。对于一个延迟敏感的服务，每隔几万次写入就卡 14 毫秒，是不能接受的。

真正的引擎会把写满的内存表**冻结**成只读的「不可变内存表」，立刻换一个新的内存表接收写入，由后台线程把不可变内存表写成 SSTable。查找时要多查一个不可变内存表。只有后台落盘跟不上、不可变内存表积累太多时，才让写入等待。lsm-kv 为了代码简单没有这样做，合并也是同步的，第 5 篇会看到合并造成的卡顿严重得多。

## 7. 常见错误

1. **用无序的哈希表做内存表**。落盘时还要排序，也无法支持范围查询。
2. **删除时直接从内存表中摘掉节点**。更早的文件中的旧值会重新出现。
3. **以为写了墓碑空间就释放了**。墓碑要合并到最底层才消失，在那之前反而多占了空间。
4. **只按键和值的大小计算内存表**。节点和分配器的开销可能占到四分之一以上。
5. **落盘时先删日志、再写清单**。中间崩溃就丢数据。

## 8. 小结

- 内存表必须有序，落盘时顺序写出就是一个有序的 SSTable；lsm-kv 用跳表；
- 同一个键的多次写入在内存表中合并成一条；
- 删除写的是墓碑，查找时先遇到墓碑就返回不存在；墓碑要合并到最底层才能丢掉；
- 内存表的大小要算上节点开销：每条 116 字节的数据约占 159 字节，4 MB 约 2.6 万条，实测 75 次落盘、平均每次 2.7 万条；
- 落盘的顺序：写 SSTable 并 `fsync` → 写清单 → 删除旧日志；
- 同步落盘让写入卡顿，最慢的一次 14 毫秒；真正的引擎用不可变内存表和后台线程。

## 9. 练习

1. 一个键先写入、落盘到 L0，然后被删除（墓碑在内存表中）。这时内存表也落盘了。查这个键会怎样？
2. 为什么墓碑不能在落盘到 L0 时就丢掉？
3. 把 `memtableBytes` 从 4 MB 调到 64 MB，对写入、读取、恢复各有什么影响？

<details>
<summary>点击查看答案</summary>

1. 现在 L0 有两个文件：新的那个中有墓碑，旧的那个中有值。查找时 L0 的文件从新到旧查，先在新文件中遇到墓碑，返回「不存在」，不会读到旧文件中的值。

2. 墓碑的作用是遮住更旧的数据。落盘到 L0 时，更早的 L0 文件和下面各层中都可能有这个键的旧值，丢掉墓碑，旧值就会重新出现。只有合并到某一层，而这一层以下都没有数据了（这个键不可能还有旧值），墓碑才能丢掉。

3. 写入：落盘次数变为原来的 1/16，每个 L0 文件更大，合并的次数也减少，同一个键的重复写入在内存表中合并得更多，写放大降低；但每次落盘写 64 MB，同步落盘时卡顿更长。读取：内存表中能命中的数据更多；L0 文件更大，但个数一样。恢复：日志最多有 64 MB，重新打开时要重放更多的记录，启动更慢；崩溃时内存中丢失的（需要重放的）数据更多。内存占用也相应增加。

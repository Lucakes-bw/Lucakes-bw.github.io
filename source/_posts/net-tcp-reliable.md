> **本文目标**：理解 TCP 怎样用序号、确认和重传实现可靠传输；理解滑动窗口；理解累积确认、重复确认和 SACK；理解快速重传和超时重传的区别；会用 `nstat` 和 tshark 分析丢包和重传。
>
> **前置知识**：上一篇的序号和确认号；第 2.1 篇的 netem。
>
> **实验环境**：Ubuntu 24.04 容器，Linux 内核 6.8，tshark 4.2。

## 1. 可靠传输要解决的问题

上一篇讲过，TCP 给每个字节编号。有了编号，可靠传输的基本思路很简单：

- 接收方收到数据后回复**确认**（ACK），确认号表示「这之前的字节都收到了」；
- 发送方发出的数据，在被确认之前都保留着；一段时间没有被确认，就**重传**；
- 接收方根据序号把数据按顺序排好，丢弃重复的数据。

如果每发一段就停下来等确认（停等协议），效率会很低：在一个往返时间为 20 ms 的网络上，每秒最多只能发 50 段。所以 TCP 允许连续发送多段而不必等待确认，这就是**滑动窗口**。

## 2. 滑动窗口

发送方维护一个**窗口**：窗口内的数据可以发送，不必等待确认；窗口左边是已经被确认的，右边是暂时不能发的。收到确认后，窗口左边界向右移动（「滑动」），新的数据进入窗口，可以继续发送。

TCP 的确认是**累积确认**：确认号 N 表示 N 之前的所有字节都收到了。如果中间缺了一段，即使后面的段都到了，确认号也只能停在缺口处，接收方会对后面到达的每一段重复发送同样的确认号，这叫**重复确认**（dup ACK）。为了让发送方知道缺口之后的数据已经收到了，接收方还会在 **SACK**（选择确认）选项中列出它们（上一篇握手时协商的 `sackOK`）。

发送方收到 3 个重复确认，就认为缺口处的段丢失了，**不等超时**，立即重发它，这叫**快速重传**。下面的演示中，10 个报文段中有一段会在途中丢失，可以改变窗口的大小，看看窗口为 3 时会发生什么：

## 3. 搭建实验：先踩一个坑

### 3.1 netem 应该加在哪里

第一次实验时，我把 netem 的 2% 丢包像 2.1 篇的 UDP 实验那样加在了客户端 c 自己的网卡上，传送 1 MB 的文件。c 上的计数器显示重传了 25 段，但在服务器 s 上抓包，**一个 SACK 都没有**，tshark 也没有发现任何丢失的段：s 从来没有看到过缺口。

原因是：netem 在发送方的网卡队列中丢弃一个包时，发送方的 TCP 能直接得知这个包没发出去，于是立即重发，丢包根本没有发生在网络中。这和真实的网络不同：真实的丢包发生在途中的路由器上，发送方只能通过对方的确认来推断。所以本篇改用一个三台机器的网络，把丢包和延迟加在中间的路由器 r 上：

```bash
#!/bin/bash
# tri.sh：c —— r —— s，丢包和延迟加在中间的路由器 r 上
set -e
for n in c r s; do ip netns add $n; ip netns exec $n ip link set lo up; done
link() {
    ip link add tmpa type veth peer name tmpb
    ip link set tmpa netns $1; ip netns exec $1 ip link set tmpa name $2
    ip link set tmpb netns $4; ip netns exec $4 ip link set tmpb name $5
    ip netns exec $1 ip addr add $3 dev $2; ip netns exec $4 ip addr add $6 dev $5
    ip netns exec $1 ip link set $2 up;     ip netns exec $4 ip link set $5 up
}
link c eth0 10.0.1.2/24  r eth0 10.0.1.1/24
link r eth1 10.0.2.1/24  s eth0 10.0.2.2/24
ip netns exec c ip route add default via 10.0.1.1
ip netns exec s ip route add default via 10.0.2.1
for x in "c eth0" "r eth0" "r eth1" "s eth0"; do      # 关闭分段卸载，让每个包都是真实的大小
    set -- $x; ip netns exec $1 ethtool -K $2 tso off gso off gro off
done
```

### 3.2 分段卸载

脚本的最后关闭了网卡的**分段卸载**（TSO、GSO、GRO）。另一个坑是：最初在 c、s 之间直接传送 1 MB，只抓到了 161 个包，而 1 MB 至少要分成 691 段。为了提高效率，Linux 会把多段数据合成一个最大 64 KB 的「超级包」交给网卡，由网卡（或者在发出前的最后一刻）再切成 1448 字节的段；接收时也会把多个段合并（GRO）。虚拟网卡 veth 上，这些超级包会原样传到对方，于是 netem 丢弃的是整个超级包，抓包看到的也是超级包。关闭之后，每个包都是真实的大小，抓到了 1005 个包。

真实的网卡上，分段卸载是在网卡的硬件中完成的，网线上传送的仍然是正常大小的帧，所以平时不需要关闭它。但在本机抓包时，tcpdump 看到的是卸载之前的超级包，会出现 `length 30000` 这样超过 MTU 的「包」，不要被它吓到。

## 4. 2% 的丢包

在 r 上把发往 s 的方向（eth1）设为延迟 20 ms、丢包 2%，c 向 s 传送一个 1 MB 的随机文件，在 s 上抓包。传送的脚本：

```bash
#!/bin/bash
# xfer.sh 文件 抓包文件：c 把文件发给 s，在 s 上抓包，输出用时和 c 的重传计数
cd /lab; X() { ip netns exec "$@"; }
ip netns exec s tcpdump -i eth0 -nn -U -s 128 -w $2 tcp 2>/dev/null & T=$!
ip netns exec s bash -c "nc -l 8000 > recv.bin" & N=$!; sleep 1
X c nstat -n
START=$(date +%s.%N); X c nc -N 10.0.2.2 8000 < $1; wait $N
python3 -c "import time; print(\"传输用时\", round(time.time()-$START,2), \"秒\")"
cmp $1 recv.bin && echo "接收的文件和原文件相同"
X c nstat | grep -E "TcpOutSegs|TcpRetransSegs|TCPFastRetrans|TCPTimeouts|TCPLossProbes|TCPSackRecovery |TCPDSACK"
sleep 0.5; kill $T; sleep 0.5
```

（后台运行的命令要直接写 `ip netns exec ... &`，`$!` 才是 tcpdump 本身的 PID。我最初用一个 shell 函数包装它，`$!` 成了子 shell 的 PID，`kill` 之后 tcpdump 还在运行，留下了一堆孤儿进程（《进程：fork、exec、wait》）。）

```bash
ip netns exec r tc qdisc add dev eth1 root netem delay 20ms loss 2%
./xfer.sh 1m.bin loss.pcap
```

```

接收的文件和原文件相同
TcpOutSegs                      694                0.0
TcpRetransSegs                  8                  0.0
TcpExtTCPSackRecovery           4                  0.0
TcpExtTCPFastRetrans            7                  0.0
TcpExtTCPTimeouts               1                  0.0
TcpExtTCPDSACKRecv              1                  0.0
TcpExtTCPDSACKIgnoredNoUndo     1                  0.0
TcpExtTCPDSACKRecvSegs          1                  0.0
```

- 文件完整无误：`cmp` 比较收到的文件和原文件，完全相同；
- c 一共发出 694 段，重传了 8 段，其中 7 段是**快速重传**，1 次是**超时重传**（`TCPTimeouts`）；
- `TCPDSACKRecv` 表示有 1 次重传其实是多余的：原来那段并没有丢，只是来晚了，接收方用 D-SACK（重复 SACK）告诉发送方「这段我收到两次了」；
- 用时 **1.72 秒**。同样的文件，只有 20 ms 延迟、没有丢包时，3 次分别用了 0.5、0.32、0.21 秒。

丢包是随机的，每次的结果都不一样。在 2% 丢包下又传送了 7 次：

```
传输用时 0.36 秒 TcpRetransSegs 8  TcpExtTCPFastRetrans 8
传输用时 1.38 秒 TcpRetransSegs 16 TcpExtTCPFastRetrans 16
传输用时 1.07 秒 TcpRetransSegs 14 TcpExtTCPFastRetrans 13 TcpExtTCPTimeouts 1
传输用时 1.44 秒 TcpRetransSegs 12 TcpExtTCPFastRetrans 12
传输用时 1.03 秒 TcpRetransSegs 11 TcpExtTCPFastRetrans 11
传输用时 0.84 秒 TcpRetransSegs 12 TcpExtTCPFastRetrans 12
传输用时 0.74 秒 TcpRetransSegs 13 TcpExtTCPFastRetrans 13
```

8 次中有 2 次发生了超时重传，用时在 0.36～1.72 秒之间，大多在 1 秒左右，比没有丢包时慢了几倍。重传的只是 8～16 段，占不到 2.5%，多出来的时间主要不是花在重传上：第 2.4 篇会讲到，TCP 把丢包当作网络拥塞的信号，每次丢包都会主动降低发送速度。

tshark 能自动分析 TCP 的丢包和重传。统计 s 上抓到的包：

```bash
for f in tcp.analysis.lost_segment tcp.analysis.retransmission tcp.analysis.fast_retransmission tcp.analysis.duplicate_ack tcp.analysis.out_of_order; do
    echo "$f: $(tshark -r loss.pcap -Y $f | wc -l)"
done
```

```
tcp.analysis.lost_segment: 6
tcp.analysis.retransmission: 3
tcp.analysis.fast_retransmission: 2
tcp.analysis.duplicate_ack: 11
tcp.analysis.out_of_order: 5
```

在接收方看来，有 6 处出现了缺口（`lost_segment`，表示之前缺了数据），收到了 3+2 个被 tshark 识别为重传的段、5 个「乱序」的段（重传的段到达时，它的序号比已经收到的小，tshark 也会把一部分标为乱序），s 发出了 11 个重复确认。在接收方抓的包和发送方的计数器不会完全对应，但趋势是一致的。

## 5. 一次完整的快速重传

找到第一个缺口，看它前后的包（只保留了时间的秒以下部分）：

```
252481 IP 10.0.1.2.42186 > 10.0.2.2.8000: Flags [.], seq 40545:41993, ...
252484 IP 10.0.1.2.42186 > 10.0.2.2.8000: Flags [P.], seq 41993:43441, ...
252493 IP 10.0.2.2.8000 > 10.0.1.2.42186: Flags [.], ack 43441, ...
281210 IP 10.0.1.2.42186 > 10.0.2.2.8000: Flags [.], seq 46337:47785, ...
281246 IP 10.0.2.2.8000 > 10.0.1.2.42186: Flags [.], ack 43441, ... sack 1 {46337:47785}
281250 IP 10.0.1.2.42186 > 10.0.2.2.8000: Flags [.], seq 47785:49233, ...
281256 IP 10.0.2.2.8000 > 10.0.1.2.42186: Flags [.], ack 43441, ... sack 1 {46337:49233}
281257 IP 10.0.1.2.42186 > 10.0.2.2.8000: Flags [P.], seq 49233:50681, ...
281260 IP 10.0.2.2.8000 > 10.0.1.2.42186: Flags [.], ack 43441, ... sack 1 {46337:50681}
281261 IP 10.0.1.2.42186 > 10.0.2.2.8000: Flags [.], seq 43441:44889, ...
281279 IP 10.0.2.2.8000 > 10.0.1.2.42186: Flags [.], ack 44889, ... sack 1 {46337:50681}
281280 IP 10.0.1.2.42186 > 10.0.2.2.8000: Flags [P.], seq 44889:46337, ...
281286 IP 10.0.2.2.8000 > 10.0.1.2.42186: Flags [.], ack 50681, ...
```

1. s 确认到 43441，一切正常；
2. 下一个到达的是 **46337**：43441～46336 这两段（各 1448 字节）在 r 上被丢掉了；
3. s 回复 `ack 43441`，并用 `sack {46337:47785}` 说明后面那段收到了。之后每到一段，都回复同样的 `ack 43441`，SACK 的范围不断扩大：`{46337:49233}`、`{46337:50681}`。这是 3 个**重复确认**；
4. c 收到第 3 个重复确认后立即重发 43441 开始的段。从 SACK 中它还知道 44889 那段也没有到，所以接着重发它，而不会重发 46337 之后那些已经到达的段；
5. 两段重传都到达后，s 的确认号从 43441 **一下子跳到 50681**，跳过了 7240 字节：缺口补上了，之前缓存着的乱序数据一起被确认。

从发现缺口（281210）到补上（281280）只用了 70 微秒，不需要等待任何计时器。没有 SACK 的话，c 只能知道 43441 丢了，不知道 44889 也丢了，要再等一轮重复确认才能发现。

## 6. 超时重传

快速重传需要后面还有数据在传送，才能产生重复确认。如果丢的是最后一段，或者网络完全中断了，就只能靠**超时**：每发出一段，发送方都启动一个**重传计时器**，超时（RTO）还没有收到确认，就重传。

实验：c 每隔 0.5 秒向 s 发送一行文字，中途在 r 上把丢包率设为 100%，6 秒后恢复。在 r 的入口（eth0）抓 c 发出的包：

```bash
( for i in $(seq 1 20); do echo "message $i"; sleep 0.5; done ) | ip netns exec c nc -N 10.0.2.2 8000 &
sleep 2.2; ip netns exec r tc qdisc change dev eth1 root netem loss 100%      # 07:38:22.040 断开
sleep 6;   ip netns exec r tc qdisc change dev eth1 root netem delay 20ms     # 07:38:28.055 恢复
```

c 发出的数据（只保留了时间和序号）：

| 时间 | 序号 | 说明 |
|---|---|---|
| 07:38:19.850 ～ 21.844 | 0:10 ～ 40:50 | 每 0.5 秒一条，正常 |
| 07:38:22.351 | 50:60 | 第 6 条，此时网络已断开 |
| 22.583 | 50:60 | 重传，间隔 0.23 秒 |
| 22.815 | 50:60 | 重传，间隔 0.23 秒 |
| 23.270 | 50:60 | 重传，间隔 0.46 秒 |
| 24.221 | 50:60 | 重传，间隔 0.95 秒 |
| 26.077 | 50:60 | 重传，间隔 1.86 秒 |
| 29.722 | 50:60 | 重传，间隔 3.64 秒，网络已恢复，成功 |
| 29.750 | 60:211 | 积压的第 7～20 条，合在一起发出 |

- **RTO 从约 0.23 秒开始**：Linux 的 RTO 最小是 200 毫秒，再加上根据往返时间（这里约 20 ms）估算出的余量；
- 前两次重传间隔相同，之后**每次翻倍**（指数退避），和上一篇 SYN 的重发一样，目的是在网络拥塞时不再雪上加霜；
- 网络在 28.055 就恢复了，但下一次重传要等到 29.722，**白白等了 1.7 秒**。指数退避的代价是：中断时间越长，恢复后还要多等一段时间；
- 断网期间写入的 14 行（`message 7` 到 `message 20`，共 151 字节）积压在发送缓冲区中，恢复后合在一个段中发出。TCP 是字节流，应用写入的次数和发出的段数不必对应（第 2.5 篇）。

如果一直不恢复，重传的次数达到上限（`net.ipv4.tcp_retries2`，默认 15，大约 15 分钟）后，连接会被放弃，应用得到 `Connection timed out` 错误。

**快速重传和超时重传的对比**：

| | 快速重传 | 超时重传 |
|---|---|---|
| 触发条件 | 3 个重复确认（或 SACK 显示有缺口） | 重传计时器到期 |
| 等待时间 | 约一个往返时间 | 至少 200 ms，并且翻倍增长 |
| 适用情况 | 丢了一段，后面还有数据在传 | 丢的是最后几段、网络中断、窗口太小 |
| 实测（1 MB，2% 丢包） | 7 次 | 1 次 |

## 7. 常见误区

1. **以为 TCP 能保证数据被对方的程序处理了**：TCP 只保证数据到了对方的内核。程序崩溃、没有读取，都不在 TCP 的保证范围内，应用层要有自己的确认（比如 HTTP 的响应）。
2. **以为丢包率 2% 只会让速度降低 2%**：实测用时通常是没有丢包时的几倍。
3. **在发送方本机用 netem 模拟丢包来测试 TCP**：TCP 能直接看到本地的丢弃，测不出真实的效果。要放在中间的设备上。
4. **抓包时被超过 MTU 的「包」迷惑**：那是分段卸载之前的超级包。
5. **以为重传的间隔是固定的**：超时重传按指数增长，网络恢复后可能还要等一段时间。

## 8. 小结

- TCP 用序号、确认和重传实现可靠传输；滑动窗口允许连续发送多段而不必等待确认
- 确认是累积的；有缺口时接收方发送重复确认，并用 SACK 告诉发送方缺口之后收到了什么
- 3 个重复确认触发快速重传，不等超时；实测两段丢失后，两次重传就补上了缺口，确认号跳过了 7240 字节
- 没有足够的后续数据或网络中断时，靠超时重传：实测 RTO 从约 0.23 秒开始，每次翻倍
- 实测 2% 丢包：1 MB 文件每次都完整送达，重传 8～16 段，用时 0.36～1.72 秒，没有丢包时是 0.21～0.5 秒
- 测试 TCP 时，丢包要加在中间的路由器上；抓包时注意分段卸载产生的超级包

## 9. 练习

1. 发送方的窗口是 4 段，发送了第 1～4 段，第 2 段丢失了。接收方会发出哪些确认？发送方能否通过快速重传恢复？
2. 把 r 上的丢包率改成 10%，再传送 1 MB，用时和重传次数会怎样变化？
3. 为什么快速重传的阈值是 3 个重复确认，而不是 1 个？

1. 第 1 段到达后确认 2；第 3、4 段到达时，第 2 段还没到，各回复一次「确认 2」，并带上 SACK。这只有 **2 个**重复确认。如果第 4 段之后发送方还有数据，并且窗口允许发送第 5 段（收到「确认 2」后窗口左边界到了 2，窗口是 2～5），第 5 段到达时会产生第 3 个重复确认，可以快速重传；如果第 4 段就是最后一段，就只能等超时（演示中窗口为 3 时就是这种情况）。Linux 实际还有 RACK、TLP（尾部丢失探测）等机制，能在这种情况下比普通的超时更早地发现丢包，对应的计数器是 `TCPLossProbes` 等（第 4 节的实验中它们恰好没有出现）。

2. 丢包率 10% 时实测：

   文件仍然完整，但用时变成了 7.36 秒，重传了 69 段，进入了 41 次丢包恢复。丢包率从 2% 变成 10%，用时却增加了好几倍：频繁的丢包让 TCP 一直保持着很低的发送速度。

3. 网络中的包可能**乱序**到达：后发的段先到了，接收方也会发出重复确认，但前面的段并没有丢，稍后就会到。如果收到 1 个重复确认就重传，乱序时就会产生很多不必要的重传。等到 3 个，说明缺口之后已经有 3 段到达了，前面那段很可能是真的丢了。第 4 节中出现的 D-SACK，就是一次「以为丢了、其实只是晚到」的多余重传。

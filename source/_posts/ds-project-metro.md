## 1. 为什么要做项目

前面每一篇文章都只讲一种数据结构，例子也是为它专门设计的：讲哈希表就只有哈希表，讲 Dijkstra 就给一个现成的图。真正写程序时，情况正好反过来：先有一个问题，要自己判断用什么结构，几种结构还要配合起来。

比如「从西山到港口怎么坐最快」这个问题：

- 用户输入的是**站名**，而图算法需要的是**编号**。站名到编号的转换，用**哈希表**；
- 车站和区间组成一张**图**，用**邻接表**存储；
- 每个区间的时间不同，最快的路线要用 **Dijkstra**，Dijkstra 又需要**堆**；
- 换乘要花时间，所以「在同一个车站换一条线」也要表示在图里，这需要对图的建模多想一步。

这个项目就是让你把这些自己想一遍、写一遍。每一步都有测试，所以不是「看懂了」就算完成，而是**测试全部通过**才算完成。

## 2. 示例城的地铁

项目使用一座虚构的城市——示例城。先来看看它的地铁线路图：

<div class="dsviz metro-map" data-metro="map"></div>

线路图是可以操作的：点一个车站、一条线路或者下面的一种走法，相关的部分会高亮，其他部分会变淡，下方会显示对应的信息。在手机上可以左右滑动查看完整的线路图。

### 2.1 怎么看这张图

- **线路**：每种颜色是一条线路，示例城一共有 4 条：红色的 1 号线东西走向，绿色的 2 号线南北走向，蓝色的 3 号线和橙色的 4 号线斜着穿过城市。
- **车站**：线路上的每个圆圈是一个车站，一共 22 个。
- **换乘站**：粗白圈表示有两条线路经过的车站，在这里可以从一条线换到另一条线。示例城有 7 个换乘站：果园、人民广场、市政府、东门、体育馆、南湖、东湖。
- **区间**：相邻两站之间的一段叫作一个**区间**，一共 25 个。勾选「显示区间时间」，每个区间上会显示列车开过这一段要几分钟。

现在点一下**人民广场**，下方会显示：

```
metro> station 人民广场
人民广场：1号线、2号线（换乘站）
  1号线：动物园 3 分钟、市政府 2 分钟
  2号线：文化宫 3 分钟、南湖 2 分钟
```

这就是里程碑 1 完成后，你的程序对 `station 人民广场` 这条命令的输出：它在哪几条线路上，每条线路上的前后两站是哪个、要开几分钟。点一下线路按钮，看到的是 `line` 命令的输出。

把整张图写成文字，就是下面这张表。程序读入的数据文件，记录的也正是这些内容：

| 线路 | 车站（括号中是到下一站的分钟数） |
|---|---|
| 1号线 | 西山 (3) 果园 (2) 动物园 (3) 人民广场 (2) 市政府 (3) 东门 (2) 科技园 (4) 机场 |
| 2号线 | 北站 (3) 体育馆 (2) 文化宫 (3) 人民广场 (2) 南湖 (3) 大学城 (4) 南站 |
| 3号线 | 植物园 (3) 果园 (4) 体育馆 (3) 老街 (2) 市政府 (3) 会展中心 (4) 东湖 |
| 4号线 | 西站 (4) 花园路 (3) 南湖 (2) 博物馆 (3) 东门 (3) 东湖 (2) 港口 |

注意，数据文件中**没有**车站的坐标。线路图上的位置只是为了画得好看，程序只知道「哪两个车站相邻、开过去要几分钟」。程序也不能把这些线路写死在代码里，换一个数据文件，就能查询另一座城市。

### 2.2 从地铁图到「图」

点线路图上方的「**抽象成图**」，同样的数据换一种画法：

- 每个车站变成一个**顶点**，圆圈里的数字是它的**编号**。编号按车站在数据文件中第一次出现的顺序分配：1 号线的西山是 0，果园是 1……机场是 7；接着是 2 号线上新出现的北站 8、体育馆 9……一直到 4 号线的港口 21。
- 每个区间变成一条**边**，边上的数字是**权重**，也就是区间的分钟数。地铁可以双向行驶，所以这是一张**无向图**。
- 颜色没有了，但每条边仍然要记住自己属于哪条线路：后面计算换乘时，要知道每一段坐的是哪条线。

这张图有 22 个顶点、25 条边，平均每个顶点只连着 2 条多一点的边，是一张很**稀疏**的图，所以用**邻接表**存储（为什么不用邻接矩阵，见[图的表示与遍历](/posts/ds-graph/)）。在「抽象成图」中点一个顶点，比如果园，可以看到它的邻接表：

```
# 顶点 1 的邻接表：(0, 1号线, 3) → (2, 1号线, 2) → (14, 3号线, 3) → (9, 3号线, 4)
```

每一项是（相邻顶点的编号，线路，分钟数）：果园在 1 号线上和西山（0）、动物园（2）相邻，在 3 号线上和植物园（14）、体育馆（9）相邻。里程碑 1 要做的，就是读取数据文件，建立起这样的邻接表。

### 2.3 同一个问题，不同的答案

回到「地铁图」，依次点「西山 → 港口」的 4 种走法：

| 走法 | 怎么坐 | 坐几站 | 用时 | 换乘 |
|---|---|---|---|---|
| A | 1号线到东门，换 4号线 | 7 | 18 分钟 | 1 次 |
| B | 1号线到市政府，换 3号线到东湖，换 4号线 | 7 | 19 分钟 | 2 次 |
| C | 1号线到果园，换 3号线到东湖，换 4号线 | 7 | 21 分钟 | 2 次 |
| D | 1号线到人民广场，换 2号线到南湖，换 4号线 | 8 | 20 分钟 | 2 次 |

（用时只算了列车运行的时间。）

从西山到港口，最少要坐 7 站，但坐 7 站的走法有好几种，用时并不相同。走法 D 比 C 多坐了一站，反而快了 1 分钟。现实中换乘还要走通道、等车，每换乘一次都要多花几分钟；把这些时间也算进去，各种走法的快慢可能又不一样了。

所以，「最好的路线」取决于你看重什么：站数最少、时间最短，还是换乘最少。这就是里程碑 2、3、4 要分别解决的三个问题。

## 3. 五个里程碑

| 里程碑 | 完成后可以 | 主要用到 |
|---|---|---|
| 1. 读取数据，建立地铁图 | 统计线路和车站；按顺序列出一条线路；查看车站所在的线路和相邻的车站 | [哈希表](/posts/ds-hash-table/)、[图的邻接表](/posts/ds-graph/)、[顺序表](/posts/ds-seqlist/) |
| 2. 站数最少的路线 | 找出经过车站最少的路线 | [队列](/posts/ds-queue/)、[BFS](/posts/ds-graph/) |
| 3. 时间最短的路线 | 找出用时最少的路线，换乘要额外花时间 | [Dijkstra](/posts/ds-shortest-path/)、[堆](/posts/ds-heap/) |
| 4. 换乘最少的路线 | 优先换乘少，换乘次数相同时再比时间 | 对图重新建模、Dijkstra 的变形 |
| 5. 搜索与排行 | 输入站名的开头列出所有匹配的车站；列出连接线路最多的车站 | [排序](/posts/ds-quick-merge/)、[二分查找](/posts/ds-binary-search/)、[Top K](/posts/ds-heap/) |

每个里程碑都在前一个的基础上增加功能，并且有自己的测试。运行某个里程碑的测试时，前面所有里程碑的测试也会一起运行，这样可以防止加新功能时改坏了已经做好的部分。

这几个里程碑是按难度排列的。里程碑 2 只要做一次 BFS；里程碑 3 开始，「换乘」会让问题变得有意思：同一个车站，从 1 号线换到 3 号线要走一段通道，这段时间怎么放进图里？里程碑 4 又会发现，「换乘最少」和「时间最短」不能用同一种权重来表示。

## 4. 怎样验证做对了

每个里程碑都从三个方面检查：

1. **自动测试**。`tests/run.sh` 会编译你的代码，把一组命令输入给程序，逐字比较程序的输出和期望的输出。数据文件中的各种格式错误也有对应的测试。
2. **内存检查**。测试时用 `-fsanitize=address,undefined` 编译，数组越界、使用已经释放的内存、整数溢出都会被当作失败；在 Linux 上还会检查内存泄漏。**输出正确但有内存错误，也算没有通过。**
3. **自查清单**。每个里程碑最后有几个问题，比如「为什么站名要先转换成编号，而不是直接在图里保存站名」。测试只能检查结果，这些问题检查的是你是否真的理解了自己的设计。

## 5. 准备环境

### 5.1 下载起始代码

下载 [ds-metro.zip](/downloads/ds-metro.zip)，解压后的目录是：

```
ds-metro/
├── Makefile
├── README.md
├── data/
│   └── metro.txt          示例城的线路数据
├── src/
│   ├── main.c             命令行界面，已经写好
│   ├── metro.h  metro.c   地铁图：读取数据、建图、查询（要你实现）
│   └── hashmap.h  hashmap.c   哈希表（要你实现）
└── tests/
    ├── run.sh             测试脚本
    └── m1/                里程碑 1 的测试用例
```

`main.c` 负责读取命令、按固定的格式输出结果，已经写好了，一般不需要修改。你要实现的是 `metro.c` 和 `hashmap.c` 中标了 `TODO` 的部分。头文件中的结构体和函数声明是 `main.c` 和测试依赖的接口，**不要修改它们**；你可以在 `.c` 文件中随意增加自己的 `static` 函数。

### 5.2 编译和测试

需要 `gcc` 或 `clang`、`make` 和 `bash`。项目在 Ubuntu 24.04（gcc 13）和 macOS（Apple clang）上测试过；Windows 请使用 WSL。

```bash
cd ds-metro
make                    # 编译出 build/metro
tests/run.sh m1         # 运行里程碑 1 的测试
```

起始代码可以编译，但什么都还没有实现，所以测试几乎全部失败：

```
== 里程碑 1 ==
[失败] 哈希表：插入、查找和更新
      hmGet("人民广场") 应该是 3，实际是 -1
      hmGet("果园") 应该是 1，实际是 -1
      ……
[失败] 01-stats  stats：统计线路、车站、区间、换乘站
      退出码应该是 0，实际是 1
      数据错误：metroLoad 还没有实现
……
[通过] 33-no-file  数据文件不存在

通过 1/26
```

（唯一通过的一项是「数据文件不存在」，这部分起始代码已经写好了。）

每一项失败都会说明原因：哪个函数返回了什么，或者输出的哪一行和期望的不同。加上 `-v` 可以看到完整的差异：

```bash
tests/run.sh -v m1
```

测试还分成了几组，比如 `tests/run.sh m1 hash` 只运行哈希表的测试。每个里程碑的文章会告诉你，做完哪一部分该运行哪一组。

所有测试用例都是普通的文本文件，放在 `tests/m1/cases/` 中：`.in` 是输入的命令，`.out` 是期望的输出，`.err` 是期望的错误信息，`.args` 是使用的数据文件。测试失败时，可以直接打开对应的文件，或者手动运行同样的命令：

```bash
./build/metro data/metro.txt < tests/m1/cases/05-station-transfer.in
```

### 5.3 交互地使用

在终端中直接运行时，程序会显示提示符，可以一条一条地输入命令：

```bash
make run
```

## 6. 建议的做法

1. **先读完里程碑的要求再写代码**。特别是输出格式和错误信息，测试会逐字比较。
2. **一小步一小步地写，随时运行测试**。比如里程碑 1，先写哈希表，跑一次测试，看到前 3 项通过了，再去写读取数据的部分。
3. **卡住了先看提示**。每个里程碑的实现部分都有折叠起来的提示，先试着自己想 10 分钟，再展开。
4. **全部通过以后，再看参考实现**。对比一下自己的设计和参考实现有什么不同，各有什么好处。参考实现在每个里程碑的最后给出链接。

准备好了就开始[里程碑 1：读取数据，建立地铁图](/posts/ds-project-metro-m1/)。

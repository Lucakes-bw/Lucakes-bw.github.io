> **本文目标**：知道哈希表为什么做不了前缀搜索；用排序和二分查找实现前缀搜索，理解「以某个前缀开头的字符串在排好序以后一定挨在一起」；用大小为 K 的堆选出前 K 名；回顾整个项目。
>
> **前置知识**：《快速排序与归并排序》、《二分查找》、《堆与优先队列》（Top K）。需要先完成[里程碑 4](/posts/ds-project-metro-m4/)（排行要用到里程碑 3 的 `routeAllTimes`）。

## 1. 要做什么

**`search <站名的开头>`：列出站名以它开头的所有车站**

```
metro> search 东
东湖、东门（2 个）
metro> search 人民广场
人民广场（1 个）
metro> search 天
没有以 天 开头的车站
```

匹配的车站按站名的 `strcmp` 顺序排列。

**`top <个数>`：到其他车站平均用时最短的 K 个车站**

```
metro> top 3
到其他车站平均用时最短的 3 个车站：
  1. 人民广场  平均 7.9 分钟
  2. 市政府  平均 9.0 分钟
  3. 南湖  平均 9.2 分钟
```

「平均用时」是从这个车站出发，到其他每个车站的最短用时（里程碑 3 的 `from` 命令算出的那些数）的平均值。人民广场排第一并不意外：它在 1号线和 2号线的交叉点上，正好位于城市的中心。

如果有到达不了的车站，平均值只算能到达的那些，并且**能到达的车站多的排在前面**；能到达的一样多时，平均用时短的在前；再一样，车站编号小的在前。

要实现的是 `search.c` 中的 4 个函数：

```c
typedef struct {
    int* order;         // 车站编号，按站名从小到大（strcmp 的顺序）排列
    int n;
} NameIndex;

void nameIndexBuild(NameIndex* ix, const Metro* m);
void nameIndexFree(NameIndex* ix);
int nameIndexPrefix(const NameIndex* ix, const Metro* m, const char* prefix, int* first);
int rankCentral(const Metro* m, int k, int* out);
```

`main.c` 在读取数据以后调用一次 `nameIndexBuild`，之后每次 `search` 都调用 `nameIndexPrefix`；程序结束前调用 `nameIndexFree`。

## 2. 前缀搜索

### 2.1 哈希表为什么不行

按站名查找，里程碑 1 已经有了 `stationIndex` 这个哈希表，平均 O(1)。但它只能回答「有没有一个叫『东门』的车站」，回答不了「有哪些车站以『东』开头」。

哈希函数的目的就是把相近的键**打散**：「东门」和「东湖」只差一个字，哈希值却毫无关系，落在不同的桶里。要找所有以「东」开头的站名，只能把整个哈希表遍历一遍，逐个检查，O(n)。

### 2.2 排好序以后，它们挨在一起

把所有站名按 `strcmp` 的顺序排好：

```
0 东湖   1 东门   2 人民广场   3 会展中心   4 体育馆   5 动物园   6 北站   7 南湖
8 南站   9 博物馆  10 大学城  11 市政府   12 文化宫   13 机场   14 果园   15 植物园
16 港口  17 科技园  18 老街   19 花园路   20 西山   21 西站
```

以「南」开头的南湖、南站排在一起，以「西」开头的西山、西站也排在一起。这不是巧合：`strcmp` 从第一个字节开始逐个比较，所以前 len 个字节相同的字符串，在排好序的序列中一定是**连续的一段**。在它前面的，前 len 个字节都比前缀小；在它后面的，前 len 个字节都比前缀大。

于是前缀搜索变成了两次二分查找：

1. 找**第一个**「前 len 个字节 ≥ 前缀」的位置，这是这一段的开头；
2. 找**第一个**「前 len 个字节 > 前缀」的位置，这是这一段的结尾（不包括）。

两者相减就是匹配的个数。比较「前 len 个字节」用 `strncmp(name, prefix, len)`，len 是前缀的字节数。这就是《二分查找》中的 lower bound 和 upper bound，只是比较的方法换成了 `strncmp`。

可以换成「南」「人民」「会展中心站」试试。

### 2.3 中文站名是怎么排序的

上面的顺序看起来有点奇怪：「东湖」排在「北站」前面，不是按拼音排的。`strcmp` 比较的是字节，站名是 UTF-8 编码的，而 UTF-8 的字节顺序和 Unicode 编号的顺序相同。「东」是 U+4E1C，「北」是 U+5317，所以「东」在前。Unicode 中汉字大致是按部首和笔画排列的，和拼音没有关系。

对前缀搜索来说，用什么顺序都可以，只要**排序和二分查找用同一种比较方法**。如果要按拼音显示，需要一张汉字到拼音的对照表，这已经超出了这个项目的范围。

还有一个细节：按字节比较时，「东」的 UTF-8 编码是 `E4 B8 9C` 三个字节，单独一个字节 `E4` 也是「东湖」的前缀。命令行中输入的总是完整的字，不会出现这种情况，但单元测试会检查它：你的实现应该按字节比较，不需要特别处理中文。

## 3. 排行：Top K

### 3.1 先算出每个车站的排序依据

对每个车站 s，调用一次里程碑 3 的 `routeAllTimes(m, s, minutes)`，得到它到其他所有车站的最短用时，再统计两个数：能到达的车站个数 `reach`，以及到这些车站的时间总和 `total`。比较两个车站时：

1. `reach` 大的在前；
2. `reach` 相同，`total` 小的在前（`reach` 相同，比较总和和比较平均值是一样的，而且不用除法，没有浮点误差）；
3. 都相同，编号小的在前。

示例城有 22 个车站，就要做 22 次 Dijkstra。车站很多时这会很慢：一万个车站的棋盘要做一万次，每次处理两万个状态，所以 `top` 的测试只用小数据。

### 3.2 只要前 K 名，不用全部排序

有了每个车站的排序依据，最简单的做法是把 n 个车站全部排序，取前 K 个，O(n log n)。

《堆与优先队列》中讲过更好的方法：维护一个大小为 K 的堆，**堆顶是目前选出的 K 个中最差的那个**。依次看每个车站：

- 堆还没满，直接放进去；
- 堆满了，如果它比堆顶好，就替换堆顶，再下沉；否则丢掉。

所有车站看完，堆中就是最好的 K 个。最后依次弹出堆顶（最差的），从 `out` 的末尾往前放，就排好了序。总的时间复杂度是 O(n log K)。

在这个项目里，n 只有几十，Top K 和全部排序看不出差别，真正的时间都花在 n 次 Dijkstra 上了。但是当 n 很大、K 很小（比如从一百万个商品中选出销量前 10 名）时，O(n log K) 和 O(n log n) 的差别就很明显，而且堆只占 K 个元素的空间。

### 4.1 按站名排序

`nameIndexBuild` 把 0 到 n-1 放进 `order`，然后按 `m->stations[order[i]].name` 排序。注意排序的是**车站编号**，比较的是编号对应的**站名**。

可以用标准库的 `qsort`，但它的比较函数只有两个参数，拿不到 `Metro`，只能通过全局变量传进去（`main.c` 中给 `from` 命令排序时就是这样做的）。参考实现自己写了一个归并排序，把 `Metro` 作为参数传下去：

```c
// 归并排序：按站名排列车站编号，tmp 是和 a 一样长的辅助数组
static void mergeSort(int* a, int* tmp, int n, const Metro* m);
```

不管用哪种方法，都要是 O(n log n) 的。单元测试会给 20 万个站名排序，插入排序、选择排序这些 O(n²) 的方法，3 秒内完不成。

### 4.2 前缀查找

按 2.2 节的方法写两次二分查找。返回匹配的个数，`*first` 设为第一个匹配的下标。

<details>
<summary>提示：二分查找的区间和循环条件</summary>

用左闭右开的区间 [lo, hi)，答案一定在 [lo, hi] 中：

```c
int lo = 0, hi = ix->n;
while (lo < hi) {
    int mid = lo + (hi - lo) / 2;
    if (strncmp(名字[mid], prefix, len) < 0) lo = mid + 1;   // mid 太小，答案在右边
    else hi = mid;                                          // mid 可能就是答案
}
// lo == hi，就是第一个 >= prefix 的位置，可能等于 n（所有站名都比前缀小）
```

第二次只要把 `< 0` 换成 `<= 0`，并且可以从第一次的结果开始找，不用从 0 开始。

</details>

有几种边界情况，单元测试都会检查：

- 前缀比所有站名都小，或者都大：返回 0；
- 前缀就是一个完整的站名，比如「东门」：返回 1；
- 前缀比任何站名都长，比如「东门站」：返回 0；
- 空字符串：所有站名都匹配（`strncmp` 比较 0 个字节时总是返回 0）；
- 没有车站（n = 0）：返回 0，不能越界。

### 4.3 排行

按 3.1 节和 3.2 节写 `rankCentral`：

1. `k` 大于车站的个数时，取车站的个数；
2. 分配一个长度为 `nstations` 的 `minutes` 数组，对每个车站调用 `routeAllTimes`，算出 `reach` 和 `total`；
3. 用一个大小为 k 的堆选出最好的 k 个；
4. 依次弹出，从后往前写到 `out` 中，返回写入的个数。

<details>
<summary>提示：「最差的在堆顶」的比较函数</summary>

先写一个函数，判断 a 是否应该排在 b 前面：

```c
static int better(const Rank* a, const Rank* b)
{
    if (a->reach != b->reach) return a->reach > b->reach;
    if (a->total != b->total) return a->total < b->total;
    return a->station < b->station;
}
```

堆顶要放最差的，所以在堆中，「父节点比孩子更差」才是正确的顺序：上浮时，如果父节点比自己**好**，就交换；下沉时，选两个孩子中**更差**的那个，如果它比自己差，就交换。

</details>

## 6. 常见错误

1. **排序时交换了站名，而不是车站编号**。`order` 中存的是编号，排序时比较编号对应的站名，交换的是编号。不要去动 `m->stations`：车站的编号就是它在数组中的下标，图中所有的边都依赖这个编号。
2. **二分查找用的是 `strcmp` 而不是 `strncmp`**。「东」比「东门」小，`strcmp` 找到的第一个 > 前缀的位置就是「东湖」，结果是 0 个。
3. **前缀查找时漏掉了 n = 0**。`hi = n - 1` 这种闭区间的写法，在 n = 0 时 hi 是 -1，稍不注意就会越界。
4. **Top K 的堆比较方向反了**。堆顶变成了最好的那个，新来的车站总是比它差，结果只保留了最先看到的 k 个。
5. **`routeAllTimes` 每次调用都泄漏了状态图**。`top` 会对每个车站调用一次，在 Linux 上测试会报告泄漏。

## 7. 思考题

1. **Trie（字典树）** 是专门为前缀搜索设计的结构：每条边是一个字符，从根到某个节点的路径就是一个前缀，以这个前缀开头的所有字符串都在这个节点的子树中。和「排序 + 二分查找」相比，它有什么优点和缺点？
2. 如果用户输入的是站名中间的字，比如「广场」，想找到「人民广场」，排序加二分查找还能用吗？
3. `top` 现在要做 n 次 Dijkstra。如果车站很多，但只关心大概的排名，有什么办法可以少算一些？

<details>
<summary>点击查看答案</summary>

1. 优点：查找的时间只和前缀的长度有关，和站名的个数无关；插入新站名不需要重新排序。缺点：每个节点要保存指向子节点的指针，内存比一个排好序的数组多得多，尤其是中文这种字符集很大的情况（按字节建 Trie，每个汉字要走 3 层）。站名在程序运行期间不会变化，查询也不多，排好序的数组更简单，也更省内存。

2. 不能。排序只能让「开头相同」的字符串挨在一起，开头不同的「人民广场」和「中心广场」会排得很远。中间匹配最简单的做法是遍历所有站名，用 `strstr` 检查，O(n)，对一个城市的车站来说完全够用。站名非常多时，可以给每个站名的所有**后缀**建索引（后缀数组），「包含广场」就变成了「某个后缀以广场开头」，又回到了前缀搜索。

3. 一种办法是**抽样**：随机选几十个车站作为终点，只计算到这些车站的平均用时，作为近似的排序依据。由于地铁是双向的，从 A 到 B 和从 B 到 A 的最短用时相同，所以「到这几十个车站的用时」只要从这几十个车站各出发一次就能算出来，Dijkstra 的次数从 n 次降到了几十次。另一种办法是**缓存**：数据文件读进来以后不会再变，`top` 的结果只需要算一次，存起来，以后的 `top` 命令直接取前 K 个。

</details>

## 9. 回顾整个项目

五个里程碑一共写了大约 700 行 C 代码，用到的数据结构和算法：

| 里程碑 | 问题 | 数据结构和算法 | 为什么选它 |
|---|---|---|---|
| 1 | 站名 → 编号 | 哈希表（链地址法） | 读取数据和每条命令都要按名字查找，平均 O(1) |
| 1 | 车站和区间 | 邻接表（动态数组） | 地铁图非常稀疏；建好以后只读不改 |
| 2 | 站数最少 | BFS、队列、前驱数组 | 所有边的权重相同 |
| 3 | 时间最短 | 状态图、Dijkstra、二叉堆 | 换乘的代价取决于「怎么到达的」，要放进顶点 |
| 4 | 换乘最少 | 同上，代价是二元组 | 字典序也满足 Dijkstra 的要求 |
| 5 | 前缀搜索 | 归并排序、二分查找 | 哈希表会打散相近的键，排序让它们挨在一起 |
| 5 | 排行 | Top K 堆 | 只要前 K 名，不用全部排序 |

回头看，有几个设计决定影响了后面的每一步：

- **用编号代替名字**（里程碑 1）。BFS、Dijkstra 中的 `prev`、`dist`、`done` 都是用编号作下标的数组。如果图中存的是站名，每一步都要先查哈希表。
- **邻接表按读取的顺序追加**（里程碑 1）。BFS 的结果因此是确定的，`main.c` 输出相邻车站的顺序、状态图中每个车站的线路顺序，也都由它决定。
- **把「在哪条线上」放进顶点**（里程碑 3）。这一步之后，换乘不再是特殊情况，只是一条普通的边。里程碑 4 甚至不用改图，只换了一种比较代价的方法。

如果还想继续，可以试试这些扩展：支持环线（里程碑 1 的思考题 2）；每个换乘站有自己的换乘时间（里程碑 3 的思考题 1）；给出几条各有所长的路线（里程碑 4 的思考题 3）；或者给程序加一个图形界面，把路线画在地图上。

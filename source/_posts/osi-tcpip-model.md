> **本文目标**：理解网络为什么要分层，以及每一层负责什么；能对照 OSI 七层模型和 TCP/IP 模型；会用 tcpdump 抓包；能把一个真实的数据包拆成各层的头部和数据，理解封装与解封装。
>
> **前置知识**：会用 Linux 命令行（Linux 基础专栏第 1 章）。
>
> **实验环境**：Docker 中的 Ubuntu 24.04 容器（aarch64），IP 地址 172.17.0.3，通过网关 172.17.0.1 访问外网；tcpdump 4.99、tshark 4.2、curl 8.5。容器启动时加上了 `NET_ADMIN`、`NET_RAW` 等权限，用于抓包和本专栏后面搭建实验网络。

## 1. 为什么要分层

在浏览器中打开一个网页，背后要解决很多问题：

- 比特怎样变成线路上的电信号或光信号？
- 同一根网线上连着很多台机器，数据交给哪一台？
- 目标机器在世界的另一端，中间经过哪些路由器？
- 数据丢了、乱序了、重复了怎么办？
- 浏览器和服务器怎样约定请求和响应的格式？

如果用一个程序解决所有问题，它会极其复杂，而且换一种网线、换一个应用都要重写。**分层**把这些问题拆开：每一层只负责一件事，只使用下一层提供的服务，只为上一层提供服务。换网线只影响最下层；写一个新的应用，也不必关心数据是怎样穿过海底光缆的。

## 2. 两种模型对照

| OSI 七层 | TCP/IP 模型 | 职责 | 数据单元 | 常见协议 / 设备 |
|---|---|---|---|---|
| 应用层 | 应用层 | 为应用程序提供网络服务 | 消息 | HTTP、DNS、SMTP、SSH |
| 表示层 | 应用层 | 数据格式、加密、压缩 | | TLS |
| 会话层 | 应用层 | 建立和管理会话 | | |
| 传输层 | 传输层 | 进程到进程：端口、可靠传输 | 段（segment） | **TCP**、**UDP** |
| 网络层 | 网络层 | 主机到主机：IP 地址、路由 | 数据报（packet） | **IP**、ICMP；路由器 |
| 数据链路层 | 链路层 | 同一网络内相邻节点之间：MAC 地址 | 帧（frame） | 以太网、Wi-Fi、ARP；交换机 |
| 物理层 | 链路层 | 在介质上传输比特 | 比特 | 网线、光纤、无线电 |

**OSI** 是国际标准化组织提出的参考模型，概念清晰，但实际很少按它实现；**TCP/IP** 是互联网实际使用的模型，它把 OSI 上面三层合并为应用层，把下面两层合并为链路层。教学中常用两者的折中：**五层模型**（应用层、传输层、网络层、数据链路层、物理层），本专栏也采用这种说法。

每一层通过**协议**与对方的同一层「对话」：TCP 只和对方的 TCP 打交道，IP 只和路径上的 IP 打交道。实现上，每一层都在数据前面加上自己的**头部**（header），记录本层需要的信息。下面抓一个真实的包来看。

## 3. 抓包：curl 访问 example.com

**tcpdump** 是 Linux 上最常用的抓包工具，它能记录经过网卡的每一个包。在一个终端中开始抓包（只抓 80 端口，`-w` 保存到文件），同时用 curl 访问一个网页：

```bash
tcpdump -i eth0 -w http80.pcap "tcp port 80" &
curl -s -o page.html http://example.com/
kill %1
tcpdump -nn -r http80.pcap
```

（`-nn` 表示不把 IP 地址和端口转换成名字，`-r` 读取保存的文件。下面每行截掉了末尾的一部分。）

| 包 | 方向 | 内容 |

在这之前，curl 还先用 DNS 查询了 example.com 的 IP 地址（这里没有抓 DNS 的包），第 3.1 篇讲 DNS。

## 4. 拆开一个包

取出第 4 个包，也就是 HTTP 请求。`-XX` 以十六进制显示整个帧：

```bash
tcpdump -nn -r http80.pcap -XX
```

```

	0x0010:  007e b507 4000 4006 9928 ac11 0003 ac42  .~..@.@..(.....B
	0x0020:  93f3 bfcc 0050 668e d78a b02c 4073 8018  .....Pf....,@s..
	0x0030:  01f6 ecba 0000 0101 080a 2587 4566 cad1  ..........%.Ef..

```

一共 140 字节（0x8c）。右边的字符列中，从 0x0042 开始能看到 `GET / HTTP/1.1`，前面的 66 个字节就是各层的头部。按层拆开：

**以太网头（14 字节，0x00～0x0d）**

| 字节 | 值 | 含义 |
|---|---|---|
| 0～5 | `ca:64:49:52:b3:61` | 目的 MAC 地址 |
| 6～11 | `aa:b0:81:06:e4:db` | 源 MAC 地址（本机 eth0 的地址） |
| 12～13 | `0800` | 类型：里面装的是 IPv4 |

**IP 头（20 字节，0x0e～0x21）**

| 字节 | 值 | 含义 |
|---|---|---|
| `45` | 4 和 5 | 版本 4；头部长度 5 × 4 = 20 字节 |
| `007e` | 126 | 整个 IP 数据报的长度：20 + 32 + 74 |
| `4000` | | 标志「不要分片」（DF） |
| `40` | 64 | **TTL**，每经过一个路由器减 1 |
| `06` | 6 | 协议：里面装的是 TCP |
| `ac11 0003` | 172.17.0.3 | 源 IP 地址 |
| `ac42 93f3` | 172.66.147.243 | 目的 IP 地址 |

**TCP 头（32 字节，0x22～0x41）**

| 字节 | 值 | 含义 |
|---|---|---|
| `bfcc` | 49100 | 源端口（curl 随机使用的端口） |
| `0050` | 80 | 目的端口：HTTP |
| `668e d78a` | 1720637322 | 序号 |
| `b02c 4073` | 2955690099 | 确认号 |
| `80` | 8 | 头部长度 8 × 4 = 32 字节（20 字节固定部分 + 12 字节选项） |
| `18` | PSH、ACK | 标志位 |
| `01f6` | 502 | 窗口 |
| `0101 080a ...` | | 选项：两个空操作 + 时间戳 |

**HTTP 数据（74 字节，0x42～0x8b）**

```
GET / HTTP/1.1\r\n
Host: example.com\r\n
User-Agent: curl/8.5.0\r\n
Accept: */*\r\n
\r\n
```

14 + 20 + 32 + 74 = 140。用 tshark（Wireshark 的命令行版本）解析同一个包，得到的结果相同（只保留了一部分）：

```

Ethernet II, Src: aa:b0:81:06:e4:db (aa:b0:81:06:e4:db), Dst: ca:64:49:52:b3:61 (ca:64:49:52:b3:61)
    Type: IPv4 (0x0800)
Internet Protocol Version 4, Src: 172.17.0.3, Dst: 172.66.147.243
    .... 0101 = Header Length: 20 bytes (5)
    Total Length: 126
    Time to Live: 64
    Protocol: TCP (6)
Transmission Control Protocol, Src Port: 49100, Dst Port: 80, Seq: 1, Ack: 1, Len: 74
    1000 .... = Header Length: 32 bytes (8)
    Flags: 0x018 (PSH, ACK)
Hypertext Transfer Protocol
    GET / HTTP/1.1\r\n
```

几个值得注意的地方：

- **每一层都用一个字段说明上一层是什么**：以太网头的类型 `0800` 表示 IPv4，IP 头的协议号 6 表示 TCP，TCP 头的端口 80 表示 HTTP。接收方正是靠这些字段，一层一层地把数据交给正确的上层；
- **目的 MAC 不是 example.com 的**。`ip neigh` 显示这个 MAC 属于网关：

  ```
  172.17.0.1 dev eth0 lladdr ca:64:49:52:b3:61 REACHABLE
  ```

  MAC 地址只在**同一个网络内**有效，发往外网的包，链路层的目的地总是本网络的出口（网关）。IP 地址则从头到尾都是 example.com 的。这个区别是第 1.2 篇和第 1.4 篇的主题；
- 以太网帧的末尾其实还有 4 字节的校验和（FCS），网卡收到帧时检查并去掉了它，所以 tcpdump 看不到；
- 140 字节中有 66 字节是头部，**开销接近一半**。传送大块数据时，一个帧可以装 1448 字节的数据，头部的比例就小多了。

## 5. 封装与解封装

把上面的过程连起来：发送方从上往下，每一层在前面加上自己的头部（**封装**）；接收方从下往上，每一层拆掉自己的头部（**解封装**）；中间的路由器只拆到网络层，看完 IP 头决定往哪里转发，再换上新的以太网头。

这种结构带来了分层的好处：路由器不需要懂 HTTP，所以新的应用协议不需要升级路由器；TCP 不需要知道下面是网线还是 Wi-Fi；网卡也不需要知道上面跑的是什么程序。

本专栏后面的内容就按这个结构展开：第 1 章是链路层和网络层，第 2 章是传输层（TCP、UDP），第 3 章是应用层协议，第 4 章用 Socket 编写网络程序。**Socket 就是应用层和传输层之间的接口**：程序把数据交给 Socket，下面三层的封装都由内核完成。

## 6. 常见误区

1. **以为 OSI 七层是互联网的实际结构**：互联网用的是 TCP/IP 模型，OSI 主要用作讨论问题的参考。
2. **以为 MAC 地址可以跨网络通信**：MAC 地址只在一个网络内有效，每经过一个路由器就换一次；IP 地址才是端到端的。
3. **以为数据是一个整体发出去的**：一个请求要分成多个包，还伴随着握手、确认等控制包。
4. **抓包时不加过滤条件**：在繁忙的机器上会抓到大量无关的包。用 `"tcp port 80"`、`"host 1.2.3.4"` 这样的过滤表达式。
5. **用 tcpdump 抓 HTTPS 的内容**：只能看到 TLS 加密后的数据（第 3.3 篇）。

## 7. 小结

- 分层把网络通信的问题拆开，每层只负责一件事；OSI 七层是参考模型，TCP/IP 是实际使用的模型，教学中常用五层模型
- 链路层用 MAC 地址在同一网络内传送帧；网络层用 IP 地址在主机之间传送数据报；传输层用端口区分进程；应用层定义具体的消息格式
- 发送时逐层封装，接收时逐层解封装；每层的头部都有一个字段说明上一层是什么
- 实测：一个 140 字节的 HTTP 请求 = 14 字节以太网头 + 20 字节 IP 头 + 32 字节 TCP 头 + 74 字节数据；获取一个网页来回了 11 个包
- 目的 MAC 是网关的，目的 IP 是服务器的：MAC 逐跳更换，IP 端到端不变
- `tcpdump -i 网卡 -w 文件 "过滤条件"` 抓包，`-nn -r` 读取，`-XX` 显示十六进制

## 8. 练习

1. 第 6 个包是 HTTP 响应，tcpdump 显示它的 TCP 数据长度是 933 字节。这个帧一共有多少字节？其中 IP 数据报有多少字节？
2. 为什么 HTTP 请求包中的 TCP 头是 32 字节，而不是最小的 20 字节？
3. 用 tcpdump 抓一次 `ping -c 1 1.1.1.1`，ICMP 的包有多少字节？分别是哪几层的头部？

1. 头部的大小和请求包一样：14 + 20 + 32 = 66 字节，所以帧是 66 + 933 = **999** 字节，IP 数据报是 20 + 32 + 933 = **985** 字节。用 tshark 验证：

   ```bash
   tshark -r http80.pcap -Y "http.response" -T fields -e frame.len -e ip.len -e tcp.hdr_len -e tcp.len
   ```

   ```
   999	985	32	933
   ```

2. 多出的 12 字节是 TCP 的**选项**：两个 1 字节的空操作（NOP，用来对齐），加上 10 字节的**时间戳**选项。时间戳用于更准确地测量往返时间，以及防止序号回绕造成的错误，Linux 默认开启。握手的包中还有 MSS、SACK、窗口扩大等选项（第 2 章）。

3. ```bash
   tcpdump -i eth0 -w ping.pcap icmp &
   ping -c 1 1.1.1.1
   tcpdump -nn -e -r ping.pcap
   ```

   ```
   07:05:41.831154 aa:b0:81:06:e4:db > ca:64:49:52:b3:61, ethertype IPv4 (0x0800), length 98: 172.17.0.3 > 1.1.1.1: ICMP echo request, id 1, seq 1, length 64
   07:05:41.834973 ca:64:49:52:b3:61 > aa:b0:81:06:e4:db, ethertype IPv4 (0x0800), length 98: 1.1.1.1 > 172.17.0.3: ICMP echo reply, id 1, seq 1, length 64
   ```

   （`-e` 显示以太网头中的 MAC 地址。）每个帧 98 字节 = 14 字节以太网头 + 20 字节 IP 头 + 8 字节 ICMP 头 + 56 字节数据。ping 输出的第一行 `56(84) bytes` 说的就是：数据 56 字节，加上 ICMP 头和 IP 头共 84 字节。ICMP 直接装在 IP 中（IP 头的协议号是 1），**没有传输层**，所以 ping 没有端口号。第 1.4 篇会详细讲 ICMP。

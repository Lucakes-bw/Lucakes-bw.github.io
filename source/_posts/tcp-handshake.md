## 1. TCP 是什么

上一篇看到，UDP 只负责把数据报交给正确的端口，丢了、乱了、发得太快了都不管。**TCP**（Transmission Control Protocol）解决了所有这些问题，它提供的是：

- **面向连接**：通信之前，双方先「握手」，建立一个连接，交换必要的信息；
- **可靠**：数据不丢失、不重复、按顺序送达（第 2.3 篇）；
- **字节流**：应用写入的数据被看作一串连续的字节，没有消息边界（第 2.5 篇）；
- **流量控制和拥塞控制**：不会把接收方或网络压垮（第 2.4 篇）。

为此，TCP 的头部比 UDP 复杂得多：

| 字段 | 长度 | 作用 |
|---|---|---|
| 源端口、目的端口 | 各 2 字节 | 和 UDP 一样 |
| **序号**（seq） | 4 字节 | 本报文的数据中，第一个字节的编号 |
| **确认号**（ack） | 4 字节 | 期望收到对方的下一个字节的编号，即「这之前的都收到了」 |
| 头部长度 | 4 位 | 以 4 字节为单位，20～60 字节 |
| **标志位** | 9 位 | SYN（建立连接）、ACK（确认号有效）、FIN（关闭）、RST（重置）、PSH（尽快交给应用）等 |
| 窗口 | 2 字节 | 自己还能接收多少字节（第 2.4 篇） |
| 校验和 | 2 字节 | |
| 紧急指针 | 2 字节 | 很少使用 |
| 选项 | 0～40 字节 | MSS、窗口扩大、SACK、时间戳等 |

TCP 给传送的**每一个字节**编号，序号和确认号都是字节的编号。这是 TCP 可靠传输的基础。

## 2. 抓一个完整的连接

在 s 上用 nc 监听 8000 端口，c 连接它，发送一行 `hello`，然后关闭（`-N` 表示输入结束后关闭连接）：

```bash
ip netns exec s nc -l 8000 &
ip netns exec c bash -c "echo hello | nc -N 10.0.0.2 8000"
```

```
07:30:17.891593 IP 10.0.0.1.38576 > 10.0.0.2.8000: Flags [S], seq 616624040, win 64240, options [mss 1460,sackOK,TS val 861833511 ecr 0,nop,wscale 7], length 0
07:30:17.891648 IP 10.0.0.2.8000 > 10.0.0.1.38576: Flags [S.], seq 2611394274, ack 616624041, win 65160, options [mss 1460,sackOK,TS val 859037579 ecr 861833511,nop,wscale 7], length 0
07:30:17.891674 IP 10.0.0.1.38576 > 10.0.0.2.8000: Flags [.], ack 1, win 502, options [nop,nop,TS val 861833511 ecr 859037579], length 0
07:30:17.891742 IP 10.0.0.1.38576 > 10.0.0.2.8000: Flags [P.], seq 1:7, ack 1, win 502, options [nop,nop,TS val 861833511 ecr 859037579], length 6
07:30:17.891753 IP 10.0.0.2.8000 > 10.0.0.1.38576: Flags [.], ack 7, win 510, options [nop,nop,TS val 859037579 ecr 861833511], length 0

07:30:17.891826 IP 10.0.0.2.8000 > 10.0.0.1.38576: Flags [F.], seq 1, ack 8, win 510, options [nop,nop,TS val 859037579 ecr 861833511], length 0
```

tcpdump 的标志：`S` 是 SYN，`.` 是 ACK，`P` 是 PSH，`F` 是 FIN，`R` 是 RST。从第 3 个报文起，tcpdump 显示的是**相对序号**（减去了初始序号），`ack 1` 就是「初始序号 + 1」。加上 `-S` 可以看到真实的值。

## 3. 三次握手

前 3 个报文就是**三次握手**：

1. **SYN**：客户端发送 SYN，`seq 616624040` 是它随机选择的**初始序号**（ISN）；
2. **SYN+ACK**：服务器回复，`ack 616624041` = 客户端的 ISN + 1，表示收到了 SYN（**SYN 虽然不带数据，也占用一个序号**）；`seq 2611394274` 是服务器自己的 ISN；
3. **ACK**：客户端确认服务器的 SYN，`-S` 显示真实的确认号是 `ack 2611394275`，即服务器的 ISN + 1。

之后，客户端发送 6 字节的 `hello\n`，序号 1～6（`seq 1:7` 表示 [1, 7)），服务器回复 `ack 7`：「6 号以前都收到了，下一个要 7 号」。

**为什么要三次？** 握手要完成两件事：双方各自告诉对方自己的初始序号，并且确认对方收到了。客户端的 ISN 由第 1 次发出、第 2 次确认；服务器的 ISN 由第 2 次发出、第 3 次确认，确认和发出合并在第 2 次中，所以是三次。只有两次的话，服务器无法知道客户端是否收到了自己的 ISN；而且网络中滞留的一个很久以前的 SYN 突然到达时，服务器会错误地建立一个连接，三次握手中客户端可以对这个莫名其妙的 SYN+ACK 回复 RST。

**为什么初始序号是随机的？** 如果每个连接都从 0 开始，旧连接中迟到的报文可能被新连接误认为是自己的数据；随机的 ISN 也让攻击者难以伪造报文插入一个连接。

### 3.1 握手中的选项

SYN 和 SYN+ACK 中协商了几个选项：

| 选项 | 含义 |
|---|---|
| `mss 1460` | **最大报文段长度**：我能接收的一个报文中最多的数据字节数。1460 = MTU 1500 − IP 头 20 − TCP 头 20，这样 TCP 的报文就不会被分片（第 1.2 篇） |
| `sackOK` | 支持**选择确认**（SACK），丢包时可以告诉对方具体收到了哪些段（第 2.3 篇） |
| `TS val ... ecr ...` | **时间戳**，用于测量往返时间；第 1.1 篇看到的 32 字节 TCP 头，多出的 12 字节就是它 |
| `wscale 7` | **窗口扩大因子**：窗口字段只有 16 位，最大 65535；实际的窗口 = 窗口字段 × 2⁷。所以后面的 `win 502` 实际是 502 × 128 = 64256 字节（第 2.4 篇） |

这些选项只能在 SYN 中协商，连接建立后就不能更改了。

## 4. 关闭连接

TCP 是**全双工**的：两个方向的数据流相互独立，要分别关闭。一方调用 `close`（或者 `shutdown`），表示「我没有数据要发了」，发送 **FIN**；另一方确认后，仍然可以继续发送数据，直到它也发送 FIN。所以标准的关闭过程有四个报文，叫作**四次挥手**：

1. A → B：FIN
2. B → A：ACK
3. B → A：FIN（B 也处理完了）
4. A → B：ACK

但上面实际抓到的是 **3 个**：

```
07:30:17.891762 IP 10.0.0.1.38576 > 10.0.0.2.8000: Flags [F.], seq 7, ack 1, ...
07:30:17.891826 IP 10.0.0.2.8000 > 10.0.0.1.38576: Flags [F.], seq 1, ack 8, ...
07:30:17.891855 IP 10.0.0.1.38576 > 10.0.0.2.8000: Flags [.], ack 2, ...
```

服务器的 nc 收到 FIN 后（读到文件结束）立即关闭了自己的一端，内核还没来得及单独发出对客户端 FIN 的确认，就把确认（`ack 8`：FIN 也占一个序号）和自己的 FIN 合在了一个报文中。如果服务器收到 FIN 后还要处理一会儿、再发送一些数据才关闭，就会看到完整的 4 个报文。

## 5. 连接的状态

握手和挥手的过程中，连接在不同的**状态**之间转换。`ss -tan` 可以查看本机所有 TCP 连接的状态。写一个服务器，它收到客户端的 FIN 后先不关闭，等 5 秒再关闭：

```python
# hold.py：接受一个连接，收到对方的 FIN 后先不关闭，等 5 秒再关闭
import socket, time
srv = socket.socket(); srv.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
srv.bind(("10.0.0.2", 8000)); srv.listen()
conn, addr = srv.accept()
while conn.recv(1024):          # 读到 0 字节表示对方关闭了它的发送方向（收到了 FIN）
    pass
time.sleep(5)
conn.close()
time.sleep(3)
```

（为了简短，这里的服务器和客户端用 Python 写，套接字函数和 C 语言中的一一对应，第 4 章用 C 实现。）客户端连接后 1.5 秒关闭。在各个时刻分别查看双方的状态（`c:` 和 `s:` 表示在哪一方执行的 `ss`）：

```
--- 服务器监听
s: LISTEN 0      128         10.0.0.2:8000      0.0.0.0:*
--- 连接建立后
c: ESTAB     0      0           10.0.0.1:41300     10.0.0.2:8000
s: LISTEN 0      128         10.0.0.2:8000      0.0.0.0:*
s: ESTAB  0      0           10.0.0.2:8000     10.0.0.1:41300
--- 客户端 close 之后
c: FIN-WAIT-2 0      0           10.0.0.1:41300     10.0.0.2:8000
s: LISTEN     0      128         10.0.0.2:8000      0.0.0.0:*
s: CLOSE-WAIT 0      0           10.0.0.2:8000     10.0.0.1:41300
--- 服务器也 close 之后
c: TIME-WAIT 0      0           10.0.0.1:41300     10.0.0.2:8000
s: LISTEN 0      128         10.0.0.2:8000      0.0.0.0:*
```

（省略了第 2 节的 nc 留下的一个 TIME-WAIT，下面会用到它。）

| 状态 | 谁 | 含义 |
|---|---|---|
| LISTEN | 服务器 | 调用了 `listen`，等待连接 |
| SYN_SENT / SYN_RCVD | 客户端 / 服务器 | 握手进行中 |
| ESTABLISHED | 双方 | 连接已建立，可以传送数据 |
| FIN_WAIT_1 | 主动关闭方 | 发出了 FIN，等待确认 |
| FIN_WAIT_2 | 主动关闭方 | FIN 已被确认，等待对方的 FIN |
| CLOSE_WAIT | 被动关闭方 | 收到了 FIN，等待**本方程序**调用 `close` |
| LAST_ACK | 被动关闭方 | 发出了 FIN，等待最后的确认 |
| TIME_WAIT | 主动关闭方 | 等待一段时间后才真正关闭 |

**CLOSE_WAIT** 值得特别注意：它的意思是「对方已经关了，我还没关」。连接停在这个状态，原因只能是本方的程序没有调用 `close`。服务器上如果有大量的 CLOSE_WAIT，几乎可以肯定是程序有 bug，比如出错的分支忘了关闭连接，最终会耗尽文件描述符（《文件描述符与系统调用》）。

## 6. TIME_WAIT

主动关闭的一方在收到对方的 FIN 并回复 ACK 之后，不是立即关闭，而是进入 **TIME_WAIT**。`-o` 可以显示计时器：

```bash
ip netns exec c ss -tano state time-wait
```

```
0      0           10.0.0.1:41300     10.0.0.2:8000 timer:(timewait,59sec,0)
0      0           10.0.0.1:38576     10.0.0.2:8000 timer:(timewait,39sec,0)
```

刚进入 TIME_WAIT 的连接还剩 59 秒；第 2 节 nc 的那个连接已经过去了约 20 秒，还剩 39 秒。Linux 的 TIME_WAIT 固定为 **60 秒**。（标准中规定为 2MSL，MSL 是报文在网络中的最长生存时间。）

为什么要等？

1. **最后一个 ACK 可能丢失**。对方收不到它，会重发 FIN。如果这一方已经彻底关闭，就只能回复 RST，对方会以为连接出了错。在 TIME_WAIT 中，它还能再次回复 ACK；
2. **让旧连接的报文消失**。如果立即用同样的地址和端口建立一个新连接，旧连接中在网络里滞留的报文可能被新连接当作自己的数据。等待足够长的时间，这些报文都已经过期了。

TIME_WAIT 的代价是占用一个「源地址、源端口、目的地址、目的端口」的组合。客户端频繁地建立短连接，可能产生成千上万个 TIME_WAIT，耗尽可用的本地端口。解决方法通常是使用长连接（HTTP 的 keep-alive，第 3.2 篇），而不是去缩短 TIME_WAIT。服务器重启时常遇到的 `Address already in use`，则是因为它监听的端口上还有 TIME_WAIT 的连接，设置 `SO_REUSEADDR` 选项就能解决（上面的 `hold.py` 中就设置了）。

## 7. 握手失败的两种情况

### 7.1 SYN 没有回音

如果服务器根本收不到 SYN，或者收到了但不回复（被防火墙丢弃），客户端会重发 SYN。在 s 上用 iptables 丢弃所有发往 8000 端口的包，c 发起连接：

```bash
ip netns exec s iptables -A INPUT -p tcp --dport 8000 -j DROP
ip netns exec c nc -z -v 10.0.0.2 8000
```

```
nc: connect to 10.0.0.2 port 8000 (tcp) failed: Connection timed out
exit=1，用时 135.3 秒
```

在 s 上抓到的 SYN（相对于第一个 SYN 的时间）：

```
   0.0 秒  10.0.0.1.48282 > 10.0.0.2.8000: Flags [S], seq 3526769850, w
   1.0 秒  10.0.0.1.48282 > 10.0.0.2.8000: Flags [S], seq 3526769850, w
   2.1 秒  10.0.0.1.48282 > 10.0.0.2.8000: Flags [S], seq 3526769850, w
   3.1 秒  10.0.0.1.48282 > 10.0.0.2.8000: Flags [S], seq 3526769850, w
   4.1 秒  10.0.0.1.48282 > 10.0.0.2.8000: Flags [S], seq 3526769850, w
   5.1 秒  10.0.0.1.48282 > 10.0.0.2.8000: Flags [S], seq 3526769850, w
   7.2 秒  10.0.0.1.48282 > 10.0.0.2.8000: Flags [S], seq 3526769850, w
  11.2 秒  10.0.0.1.48282 > 10.0.0.2.8000: Flags [S], seq 3526769850, w
  19.6 秒  10.0.0.1.48282 > 10.0.0.2.8000: Flags [S], seq 3526769850, w
  36.0 秒  10.0.0.1.48282 > 10.0.0.2.8000: Flags [S], seq 3526769850, w
  68.2 秒  10.0.0.1.48282 > 10.0.0.2.8000: Flags [S], seq 3526769850, w
```

同一个 SYN（序号相同）一共发了 11 次：先每隔 1 秒重发 5 次，之后间隔依次翻倍（2、4、8、16、32 秒），最后一次之后又等了约 67 秒，connect 才以 `Connection timed out` 失败，前后共 135 秒。

间隔翻倍叫作**指数退避**：如果是网络拥塞造成的丢包，越来越慢地重试，可以避免让拥塞更严重。开头那几次 1 秒的固定间隔，来自这台机器的内核（6.8）的一个较新的参数 `net.ipv4.tcp_syn_linear_timeouts`，它的值是 4：先按初始的超时时间线性地重发几次，再开始指数退避，让短暂的丢包能更快地恢复。总的重发次数由它和 `net.ipv4.tcp_syn_retries`（6）共同决定，这里是 10 次。

所以，**连接一个丢弃 SYN 的地址，可能要等两分多钟才报错**。程序中通常要自己设置连接超时，而不是依赖系统的默认值。

### 7.2 RST：连接被拒绝

连接一个没有程序监听的端口：

```bash
ip netns exec c nc -z -v 10.0.0.2 8001
```

```
nc: connect to 10.0.0.2 port 8001 (tcp) failed: Connection refused
07:30:52.469515 IP 10.0.0.1.48394 > 10.0.0.2.8001: Flags [S], seq 3738224112, win 64240, options [mss 1460,sackOK,TS val 861868089 ecr 0,nop,wscale 7], length 0
07:30:52.469559 IP 10.0.0.2.8001 > 10.0.0.1.48394: Flags [R.], seq 0, ack 3738224113, win 0, length 0
```

服务器的内核立即回复 **RST**（重置），connect 马上失败，错误是 `Connection refused`。这和 7.1 节的区别很有用：**立即被拒绝，说明主机在、端口没开；等很久才超时，说明包被丢弃了，可能是主机不在或者被防火墙拦截**。

## 8. RST：异常终止

RST 也用于在连接建立后**异常地终止**它，不经过正常的挥手。一个例子：服务器接受连接后，没有读取客户端发来的数据就关闭了连接：

```python
# rstclose.py：接受连接后不读数据就关闭
import socket, time
srv = socket.socket(); srv.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
srv.bind(("10.0.0.2", 8000)); srv.listen()
conn, addr = srv.accept()
time.sleep(0.5)                  # 等客户端的数据到达，但不读取
conn.close()
```

客户端发送 12 字节后等待回复：

```
recv 出错： [Errno 104] Connection reset by peer
```

抓包（握手部分省略）：

```
IP 10.0.0.1.56162 > 10.0.0.2.8000: Flags [P.], seq 1:13, ack 1, win 502, ...
IP 10.0.0.2.8000 > 10.0.0.1.56162: Flags [.], ack 13, win 509, ...
IP 10.0.0.2.8000 > 10.0.0.1.56162: Flags [R.], seq 1, ack 13, win 509, ...
```

服务器的内核已经确认收到了这 12 字节（`ack 13`），但程序关闭时它们还在接收缓冲区中没有被读取。这说明客户端的请求根本没有被处理，所以内核不发 FIN（FIN 表示「正常结束」），而是发 **RST**，客户端的 `recv` 得到 `Connection reset by peer`。

`Connection reset by peer` 是网络编程中最常见的错误之一。常见的原因：对方程序崩溃或被杀死（内核替它关闭连接时，如果有未读数据就会发 RST）、对方在有未读数据时关闭、中间的防火墙或负载均衡器主动断开了长时间空闲的连接。

## 9. 常见误区

1. **以为 ACK 是应用程序收到数据后发的**：ACK 由内核发送，表示数据到了接收缓冲区，不代表程序读取或处理了。第 8 节中，数据已被确认，程序却从未读过它。
2. **以为挥手一定是 4 个报文**：ACK 和 FIN 可以合并，实测只有 3 个。
3. **大量 CLOSE_WAIT 时去调整内核参数**：CLOSE_WAIT 是本方程序没有 `close`，要修程序。
4. **想方设法消除 TIME_WAIT**：它有存在的理由。客户端端口不够用时，优先考虑长连接。
5. **把「连接超时」和「连接被拒绝」混为一谈**：一个是没有回音，一个是收到了 RST，原因完全不同。

## 10. 小结

- TCP 给每个字节编号：序号是本报文第一个字节的编号，确认号是期望收到的下一个字节的编号；SYN 和 FIN 各占一个序号
- 三次握手交换并确认双方的随机初始序号，同时协商 MSS、窗口扩大、SACK、时间戳等选项
- 关闭是两个方向分别进行的；标准是四次挥手，ACK 和 FIN 合并时只有三个报文（实测）
- 用 `ss -tan` 查看状态；CLOSE_WAIT 表示本方程序还没 close；主动关闭方进入 TIME_WAIT，Linux 上持续 60 秒
- 丢弃 SYN 时，客户端重发 SYN，先线性后指数退避，实测 135 秒后才报 `Connection timed out`
- 连接没有监听的端口，立即收到 RST（`Connection refused`）；有未读数据时关闭连接，发出 RST（`Connection reset by peer`）

## 11. 练习

1. 一个 TCP 连接中，客户端的初始序号是 1000，它发送了 3 个报文，数据分别是 100、200、300 字节，然后发送 FIN。这三个报文和 FIN 的序号分别是多少？服务器确认 FIN 时的确认号是多少？
2. 用 nc 让服务器先关闭连接（服务器端输入完后按 Ctrl+D），哪一方会进入 TIME_WAIT？
3. 服务器上 `ss -tan | grep -c CLOSE-WAIT` 的结果是 3000，并且还在不断增加。可能是什么原因？

<details>
<summary>点击查看答案</summary>

1. SYN 占一个序号，所以第一个数据报文的序号是 1001，三个报文的序号依次是 1001、1101、1301，数据最后一个字节是 1600；FIN 的序号是 1601；FIN 也占一个序号，服务器确认 FIN 时的确认号是 **1602**。

2. **服务器**。谁先发 FIN，谁就是主动关闭方，进入 TIME_WAIT，和它是客户端还是服务器无关。实测服务器发送 `bye` 后关闭，客户端读到后也关闭：

   ```bash
   ip netns exec s bash -c "echo bye | nc -N -l 8000" &
   ip netns exec c bash -c "nc 10.0.0.2 8000 </dev/null"
   ip netns exec s ss -tano state time-wait "( sport = :8000 )"
   ```

   ```
   0      0           10.0.0.2:8000     10.0.0.1:56750 timer:(timewait,59sec,0)
   ```

   客户端那边没有 TIME_WAIT。像 HTTP/1.0 这样由服务器主动关闭连接的协议，TIME_WAIT 会积累在服务器上。

3. 对方已经关闭了连接，而服务器程序没有调用 `close`。常见的情况：程序在处理请求的某个分支中（比如出错时）直接返回，忘了关闭连接；或者程序没有检测到 `read` 返回 0（对方关闭），一直在等待。CLOSE_WAIT 不会自己消失，会一直占用文件描述符，直到程序关闭它或者退出。应该检查程序的代码，而不是调整内核参数。

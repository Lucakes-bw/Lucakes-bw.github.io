> **本文目标**：会让程序崩溃时生成 core 文件，并用 GDB 分析它；会用观察点（watchpoint）找到修改了某个变量的代码；会用 GDB 连接到正在运行的进程；会用 Valgrind 检查内存错误和内存泄漏。
>
> **前置知识**：《开发环境与编程工具》中断点、单步、`bt` 等调试器的基本用法（本文开头只用一张表回顾）；《进程与系统监控》中的信号和退出码。
>
> **实验环境**：Ubuntu 24.04 容器（aarch64），GCC 13.3，GDB 15.1，Valgrind 3.22。为了让输出可以复现，文中的 GDB 会话用 `gdb -batch -ex 命令` 运行，显示时改写成交互的形式。

## 1. 回顾：GDB 常用命令

调试的程序要用 **`-g -O0`** 编译：`-g` 加入调试信息（《GCC 与 ELF 文件》中的 `.debug_*` 节），`-O0` 关闭优化，否则变量可能被优化掉，执行顺序也和源代码对不上。

| 命令 | 简写 | 作用 |
|---|---|---|
| `run [参数]` | `r` | 运行程序 |
| `break 函数名` / `break 文件:行号` | `b` | 设置断点 |
| `next` / `step` | `n` / `s` | 单步（不进入 / 进入函数） |
| `continue` | `c` | 继续运行到下一个断点 |
| `print 表达式` | `p` | 打印变量或表达式 |
| `backtrace` | `bt` | 调用栈 |
| `frame n` | `f n` | 切换到第 n 层 |
| `info locals` | | 所有局部变量 |
| `list` | `l` | 显示源代码 |
| `watch 表达式` | | 观察点：表达式的值改变时停下 |
| `quit` | `q` | 退出 |

这些命令的详细演示见《开发环境与编程工具》。本文关注三种在 Linux 上经常遇到、用断点和单步不好解决的情况。

## 2. core dump：崩溃之后再分析

服务器上的程序半夜崩溃了，第二天早上才发现，当时并没有在调试器中运行。这时就要靠 **core dump**：进程因为某些信号（如 SIGSEGV、SIGABRT）终止时，内核可以把它的内存和寄存器保存到一个 **core 文件**中，事后用 GDB 打开它，就像回到了崩溃的那一刻。

下面的程序统计几个学生的总分，其中 `dave` 不在表中：

```c
// crash.c
#include <stdio.h>
#include <string.h>

struct student {
    const char *name;
    int score;
};

static struct student table[] = {
    {"alice", 90}, {"bob", 72}, {"carol", 85},
};

static struct student *find(const char *name)
{
    for (size_t i = 0; i < sizeof table / sizeof table[0]; i++) {
        if (strcmp(table[i].name, name) == 0) {
            return &table[i];
        }
    }
    return NULL;                     // 没找到
}

static int total(const char **names, int n)
{
    int sum = 0;
    for (int i = 0; i < n; i++) {
        sum += find(names[i])->score;  // 没有检查返回值
    }
    return sum;
}

int main(void)
{
    const char *names[] = {"alice", "carol", "dave", "bob"};
    printf("total = %d\n", total(names, 4));
    return 0;
}
```

### 2.1 打开 core dump

是否生成 core 文件，由资源限制 `ulimit -c` 控制，它是 core 文件的最大大小：

```bash
gcc -g -O0 -Wall crash.c -o crash
(ulimit -c 0; ./crash; echo "exit=$?")
ls core*
```

```
Segmentation fault
exit=139
ls: cannot access 'core*': No such file or directory
```

限制为 0 时，只有一句 `Segmentation fault`，退出码 139 = 128 + 11（SIGSEGV），没有留下任何线索。去掉限制再运行：

```bash
ulimit -c unlimited
./crash
ls -l core
file core
```

```
Segmentation fault (core dumped)
-rw------- 1 lucky lucky 270336 Oct 24 02:09 core
core: ELF 64-bit LSB core file, ARM aarch64, version 1 (SYSV), SVR4-style, from './crash', real uid: 1001, effective uid: 1001, real gid: 1001, effective gid: 1001, execfn: './crash', platform: 'aarch64'
```

这次提示 `(core dumped)`，当前目录下出现了 `core` 文件。它也是 ELF 格式的，记录了崩溃的程序是 `./crash`。

`ulimit -c unlimited` 只对当前 Shell 和它启动的程序有效。core 文件保存在哪里、叫什么名字，由内核参数 `/proc/sys/kernel/core_pattern` 决定：

```bash
cat /proc/sys/kernel/core_pattern
```

```
core
```

本文的容器中它就是 `core`，表示保存在进程的当前目录中。**普通的 Ubuntu 电脑上情况不同**：`ulimit -c` 默认是 0，`core_pattern` 通常以 `|` 开头，表示把 core 交给一个程序处理（比如 Ubuntu 的错误报告工具 apport，或者 `systemd-coredump`）。如果系统使用 `systemd-coredump`，可以用 `coredumpctl list` 列出崩溃记录，`coredumpctl gdb` 直接用 GDB 打开最近的一个。

### 2.2 用 GDB 分析 core 文件

```bash
gdb ./crash core
```

```
Core was generated by `./crash'.
Program terminated with signal SIGSEGV, Segmentation fault.
#0  0x0000b388051509c4 in total (names=0xffffd4959e78, n=4) at crash.c:27
27	        sum += find(names[i])->score;  // 没有检查返回值
(gdb) bt
#0  0x0000b388051509c4 in total (names=0xffffd4959e78, n=4) at crash.c:27
#1  0x0000b38805150a40 in main () at crash.c:35
(gdb) info locals
i = 2
sum = 175
(gdb) p names[i]
$1 = 0xb38805150ad0 "dave"
```

GDB 一打开 core 文件，就告诉我们程序因为 SIGSEGV 终止，停在 `crash.c` 的第 27 行。更有用的是，**崩溃时所有变量的值都还在**：

- `i = 2`，正在处理第 3 个名字 `"dave"`；
- `sum = 175`，正好是 alice 和 carol 的分数之和，说明前两个都处理成功了。

看一下崩溃的那条指令：

```
(gdb) x/i $pc
=> 0xb388051509c4 <total+52>:	ldr	w0, [x0, #8]
(gdb) p $x0
$2 = 0
```

`ldr w0, [x0, #8]` 是从地址 `x0 + 8` 读取 4 个字节，也就是读取结构体中的 `score`（在 `name` 指针的 8 个字节后面），而 `x0` 是 0：`find("dave")` 返回了 `NULL`，`NULL->score` 访问了地址 8，导致段错误。

core 文件只是一张快照，不能让程序继续运行，也不能调用函数：

```
(gdb) p find(names[i])
You can't do that without a process to debug.
```

如果直接在 GDB 中运行程序，就可以调用函数来验证猜测：

```
(gdb) run
Program received signal SIGSEGV, Segmentation fault.
0x0000aaaaaaaa09c4 in total (names=0xfffffffffb78, n=4) at crash.c:27
27	        sum += find(names[i])->score;  // 没有检查返回值
(gdb) p find(names[i])
$1 = (struct student *) 0x0
(gdb) p find("bob")->score
$2 = 72
```

注意两次的地址不同：在 GDB 中运行时，GDB 默认关闭了地址空间布局随机化，地址变成了 `0xaaaaaaaa09c4` 这样整齐的值。

> **发布的程序没有 `-g` 怎么办？**常见做法是用 `-g` 编译，发布前用 `objcopy --only-keep-debug` 把调试信息单独保存成一个文件，再 strip 程序。拿到 core 文件后，配合保存的调试信息就能看到行号。Ubuntu 的 `-dbgsym` 软件包就是这样提供系统程序的调试信息的。

## 3. 观察点：谁改了我的变量

下面的程序中，账户的余额莫名其妙地变成了 0：

```c
// watch2.c
#include <stdio.h>

struct account {
    char name[8];
    int balance;
};

static void set_name(struct account *a, const char *name)
{
    int i;
    for (i = 0; name[i] != '\0'; i++) {   // 没有检查长度
        a->name[i] = name[i];
    }
    a->name[i] = '\0';
}

int main(int argc, char *argv[])
{
    struct account acc = {"", 100};
    printf("balance = %d\n", acc.balance);
    set_name(&acc, argc > 1 ? argv[1] : "lucky");
    printf("name = %s, balance = %d\n", acc.name, acc.balance);
    return 0;
}
```

```bash
gcc -g -O0 -Wall watch2.c -o watch2
./watch2
./watch2 lucky-bw
```

```
balance = 100
name = lucky, balance = 100
balance = 100
name = lucky-bw, balance = 0
```

名字是 `lucky` 时正常，换成 `lucky-bw` 余额就变成了 0，而代码中没有任何一行给 `balance` 赋值。在大程序中，这种「变量被不相干的代码改掉」的问题很难靠读代码找到。**观察点**（watchpoint）让 GDB 在一个变量的值改变时停下来：

```
(gdb) break 21
Breakpoint 1 at 0x91c: file watch2.c, line 21.
(gdb) run lucky-bw
Breakpoint 1, main (argc=2, argv=0xfffffffffd28) at watch2.c:21
21	    set_name(&acc, argc > 1 ? argv[1] : "lucky");
(gdb) watch acc.balance
Hardware watchpoint 2: acc.balance
(gdb) continue

Hardware watchpoint 2: acc.balance

Old value = 100
New value = 0
set_name (a=0xfffffffffb88, name=0xffffffffff2e "lucky-bw") at watch2.c:15
15	}
(gdb) bt
#0  set_name (a=0xfffffffffb88, name=0xffffffffff2e "lucky-bw") at watch2.c:15
#1  0x0000aaaaaaaa094c in main (argc=2, argv=0xfffffffffd28) at watch2.c:21
(gdb) p i
$1 = 8
(gdb) p sizeof(a->name)
$2 = 8
```

GDB 在 `balance` 从 100 变成 0 的那一刻停了下来。它显示的是**下一条要执行的语句**（第 15 行），所以修改发生在刚执行完的第 14 行：`a->name[i] = '\0'`，此时 `i = 8`。`lucky-bw` 正好 8 个字符，结尾的 `\0` 是第 9 个字节，写到了 `name[8]`，越过了数组，落在紧挨着的 `balance` 上。`balance` 是 100，在小端序的机器上，最低的字节在前面，这个字节被改成 0，100 就变成了 0。

几点说明：

- `watch` 要在变量**有效的范围内**设置，所以先在第 21 行停下；函数返回、局部变量失效后，观察点会被自动删除；
- `Hardware watchpoint` 表示使用 CPU 提供的调试寄存器实现，程序几乎全速运行，但数量有限（通常只有几个）；
- 我起初用的是 `strcpy(a->name, name)`，在这台 ARM 虚拟机上，硬件观察点**没有**捕获到 `strcpy` 中的那次写入（`strcpy` 一次写入多个字节）。执行 `set can-use-hw-watchpoints 0` 改用**软件观察点**后才捕获到：GDB 单步执行每一条指令，并检查值是否改变，所以要慢得多。观察点没有触发时，可以试试这个方法；
- `rwatch` 在变量被读取时停下，`awatch` 在读或写时都停下。

## 4. 连接到正在运行的进程

程序没有崩溃，而是卡住了：

```c
// hang.c
#include <stdio.h>

int main(void)
{
    long sum = 0;
    for (unsigned char i = 0; i < 300; i++) {   // 想把 0 到 299 加起来
        sum += i;
    }
    printf("sum = %ld\n", sum);
    return 0;
}
```

```bash
gcc -g -O0 hang.c -o hang
./hang &
ps -o pid,stat,%cpu,cmd -p $!
```

```
    PID STAT %CPU CMD
   5590 R    99.0 ./hang
```

状态是 `R`，CPU 占用 99%：它一直在计算，没有结束。`gdb -p PID` 可以连接（attach）到一个正在运行的进程：

```bash
gdb -p 5590
```

```
Could not attach to process.  If your uid matches the uid of the target
process, check the setting of /proc/sys/kernel/yama/ptrace_scope, or try
again as the root user.  For more details, see /etc/sysctl.d/10-ptrace.conf
ptrace: Inappropriate ioctl for device.
```

连接失败了，虽然这个进程就是我们自己启动的。原因是 Ubuntu 默认开启了一项安全限制：

```bash
cat /proc/sys/kernel/yama/ptrace_scope
```

```
1
```

`ptrace_scope` 为 1 时，普通用户只能调试**自己的子进程**（比如在 GDB 中用 `run` 启动的程序），不能连接到其他进程。否则，一个被入侵的程序就能读取同一用户下其他进程（比如浏览器）的内存。调试自己机器上的程序，用 `sudo` 即可：

```
$ sudo gdb -p 5590
main () at hang.c:7
7	        sum += i;
(gdb) bt
#0  main () at hang.c:7
(gdb) p i
$1 = 206 '\316'
(gdb) p sum
$2 = 96439242235
(gdb) next
6	    for (unsigned char i = 0; i < 300; i++) {   // 想把 0 到 299 加起来
(gdb) next
7	        sum += i;
(gdb) next
6	    for (unsigned char i = 0; i < 300; i++) {   // 想把 0 到 299 加起来
(gdb) p i
$3 = 207 '\317'
```

连接后进程被暂停，停在了循环中。`sum` 已经是 964 亿多，远远超过 0 到 299 的和 44850，说明循环已经转了很多圈。`i` 的类型是 `unsigned char`，最大只能到 255，再加 1 就回到 0，**永远不会达到 300**，所以 `i < 300` 永远成立。

退出 GDB 时，进程会恢复运行（GDB 会询问是否 detach）。

其实这个 bug 编译器能发现，只要加上 `-Wextra`：

```
hang.c:6:33: warning: comparison is always true due to limited range of data type [-Wtype-limits]
    6 |     for (unsigned char i = 0; i < 300; i++) {   // 想把 0 到 299 加起来
      |                                 ^
```

## 5. Valgrind：检查内存错误

下面的程序看起来运行正常：

```c
// leak.c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

static char *make_greeting(const char *name)
{
    char *s = malloc(strlen("Hello, ") + strlen(name));   // 少算了结尾的 \0
    strcpy(s, "Hello, ");
    strcat(s, name);
    return s;
}

int main(void)
{
    const char *names[] = {"alice", "bob", "carol"};
    for (int i = 0; i < 3; i++) {
        char *g = make_greeting(names[i]);
        puts(g);                                           // 用完没有 free
    }

    int *scores = malloc(3 * sizeof(int));
    scores[0] = 90;
    scores[1] = 72;                                        // 忘了给 scores[2] 赋值
    if (scores[2] > 60) {
        puts("pass");
    }
    free(scores);
    return 0;
}
```

```bash
gcc -g -O0 -Wall -Wextra leak.c -o leak
./leak
```

```
Hello, alice
Hello, bob
Hello, carol
```

没有警告，没有崩溃，输出也对，但其中有三个 bug。**Valgrind** 不需要重新编译，直接运行程序就能检查（用 `-g` 编译时，报告中会有行号）：

```bash
valgrind --leak-check=full ./leak
```

（`==5630==` 是进程号。）逐条看：

1. **Invalid write of size 1**：第 9 行的 `strcat` 写了 1 个字节到「一个 12 字节的内存块**后面 0 字节**」的位置，即紧挨着内存块的末尾，这个块是第 7 行 `malloc` 的。`"Hello, alice"` 有 12 个字符，加上 `\0` 要 13 个字节，只分配了 12 个，`\0` 写出了界。
2. **Invalid read of size 1**：`puts` 计算字符串长度时，读到了同一个位置。这是第 1 个错误的后果。
3. **Conditional jump or move depends on uninitialised value(s)**：第 24 行的 `if` 用到了未初始化的值 `scores[2]`。它的值是随机的，这次运行没有打印 `pass`，换个环境可能就会打印。
4. **definitely lost: 34 bytes in 3 blocks**：3 次 `make_greeting` 分配的内存（12 + 10 + 12 = 34 字节）没有释放，并且已经没有任何指针指向它们，再也无法释放了。

`total heap usage: 5 allocs` 中，除了 3 次 `make_greeting` 和 1 次 `scores`，还有 1 次是 `stdout` 自己分配的 4096 字节缓冲区，所以总共分配了 34 + 12 + 4096 = 4142 字节。

修复：`malloc` 时加 1；`puts(g)` 之后 `free(g)`；给 `scores[2]` 赋值，或者用 `calloc` 分配清零的内存。

### 5.1 Valgrind 和 AddressSanitizer

《开发环境与编程工具》中介绍过 **AddressSanitizer**（ASan），它在编译时加入检查代码。同一个程序用 ASan 编译：

```bash
gcc -g -fsanitize=address leak.c -o leak_asan
./leak_asan
```

```
==5650==ERROR: AddressSanitizer: heap-buffer-overflow on address 0x50200000001c at pc 0xe1e18e55fe88 bp 0xffffe09526a0 sp 0xffffe0951e80
WRITE of size 6 at 0x50200000001c thread T0
    #0 0xe1e18e55fe84 in strcat ../../../../src/libsanitizer/asan/asan_interceptors.cpp:515
    #1 0xc724f6770f54 in make_greeting /home/lucky/ch2/gdb/leak.c:9
    #2 0xc724f6771104 in main /home/lucky/ch2/gdb/leak.c:17
```

ASan 同样指出了第 9 行的越界写，并且**在第一个错误处就终止了程序**。两者的比较：

| | Valgrind | AddressSanitizer |
|---|---|---|
| 是否要重新编译 | 不需要 | 需要 `-fsanitize=address` |
| 速度 | 慢 | 较快 |
| 发现错误后 | 继续运行，报告所有错误 | 默认在第一个错误处终止 |
| 未初始化的值 | 能发现 | 不能（需要 clang 的 MemorySanitizer） |
| 栈上和全局数组越界 | 基本不能 | 能发现 |

用一个对 200 万个元素循环 20 遍的程序测量速度：直接运行 0.063 秒；在 Valgrind 中运行 1.042 秒，慢了约 16 倍（其中包括 Valgrind 自身的启动时间）；用 ASan 编译后运行 0.073 秒，只慢了约 20%。不同的程序差别很大，频繁分配内存的程序在两者下都会慢得更多。

两个工具可以互相补充：平时开发用 ASan，遇到 ASan 发现不了的问题（比如未初始化的值），或者手上只有编译好的程序时，用 Valgrind。**注意不能同时使用两者**。

## 6. 常见错误

1. **不加 `-g` 就调试**：GDB 只能显示地址，看不到行号和变量名。
2. **用 `-O2` 编译后调试**：变量显示 `<optimized out>`，单步执行时在源代码中跳来跳去。调试时用 `-O0`（或者 `-Og`）。
3. **程序崩溃了却没有 core 文件**：检查 `ulimit -c` 是否为 0，以及 `core_pattern` 把 core 交给了谁。
4. **core 文件和程序不匹配**：重新编译后，旧的 core 文件对应的是旧程序，GDB 显示的行号会错乱。分析 core 时要用崩溃时的那个可执行文件。
5. **`gdb -p` 失败**：不是自己的子进程，受 `ptrace_scope` 限制，用 `sudo`。
6. **观察点设置在变量的作用范围之外**：要先停在变量有效的地方，再 `watch`。
7. **Valgrind 和 ASan 一起用**：两者都要接管内存分配，不能同时使用。

## 7. 小结

- core dump 保存了进程崩溃时的内存和寄存器；`ulimit -c unlimited` 打开，`core_pattern` 决定保存位置；`gdb 程序 core` 打开后，`bt`、`info locals`、`p` 查看崩溃时的状态
- 观察点 `watch 变量` 在变量改变时停下，用于查找「谁改了这个变量」，典型的原因是数组越界写到了相邻的变量
- `gdb -p PID` 连接到正在运行的进程，查看卡住的程序在做什么；Ubuntu 的 `ptrace_scope` 限制普通用户只能调试子进程
- Valgrind 不用重新编译，能发现越界读写、未初始化的值、内存泄漏，但运行慢；ASan 更快，能发现栈上的越界，两者互相补充

3. **definitely lost**：内存块已经没有任何指针指向它，不可能再释放，是确定的泄漏。**still reachable**：程序结束时，内存块还有指针指向（比如全局变量），只是没有在退出前释放。这个程序中，`cache` 是全局变量，退出时仍然指向那块内存，所以报告的是 still reachable：

   ```
   ==5685==    definitely lost: 0 bytes in 0 blocks
   ==5685==    indirectly lost: 0 bytes in 0 blocks
   ==5685==      possibly lost: 0 bytes in 0 blocks
   ==5685==    still reachable: 100 bytes in 1 blocks
   ```

   这种情况通常无害，程序退出时操作系统会回收所有内存。真正要关注的是 definitely lost，尤其是在循环中反复发生的泄漏，会让长时间运行的程序占用的内存越来越多。

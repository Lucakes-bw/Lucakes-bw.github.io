> **本文目标**：理解传输层的作用和端口的概念；能读懂 UDP 头部；理解 UDP「不可靠、无连接」的具体含义：会丢包、会乱序、不会告诉发送方；学会用 netem 模拟网络中的丢包和延迟；知道 UDP 适用于哪些场合。
>
> **前置知识**：第 1 章的封装、IP 和 ICMP。
>
> **实验环境**：Ubuntu 24.04 容器。本章用两个网络命名空间搭建实验网络：客户端 c（10.0.0.1）和服务器 s（10.0.0.2），中间用一对 veth 直接相连（建立方法和第 1.4 篇相同）。

## 1. 传输层和端口

网络层的 IP 把数据报从一台主机送到另一台主机。但一台主机上同时运行着很多程序：浏览器、聊天软件、后台的更新程序……数据到了主机，应该交给哪个程序？这是**传输层**的职责，它用**端口号**（0～65535 的整数）区分同一台主机上的不同程序。

传输层最主要的两个协议：

| | UDP | TCP |
|---|---|---|
| 连接 | 无连接，直接发送 | 先建立连接（第 2.2 篇） |
| 可靠性 | 不保证送达、不保证顺序 | 保证按顺序、不丢失、不重复地送达（第 2.3 篇） |
| 数据边界 | 保留：发一个，收一个 | 字节流，没有边界（第 2.5 篇） |
| 流量和拥塞控制 | 没有 | 有（第 2.4 篇） |
| 头部 | 8 字节 | 20～60 字节 |
| 典型应用 | DNS、音视频通话、游戏、QUIC | 网页、文件传输、SSH、邮件 |

本篇讲 UDP，它简单得多，正好能看清「传输层至少要做什么」。

## 2. UDP 头部

Bash 可以通过特殊的路径 `/dev/udp/主机/端口` 发送 UDP 数据报：每次重定向写入，就发出一个数据报。在 s 上用 `nc -u -l 9000` 监听 9000 端口，同时抓包；在 c 上分别向 9000 端口和没有程序监听的 9001 端口发送一行文字：

```bash
ip netns exec s nc -u -l -k 9000 &
ip netns exec s tcpdump -i eth0 -nn -U -w udp1.pcap "udp or icmp" &
ip netns exec c bash -c "echo hello > /dev/udp/10.0.0.2/9000"
ip netns exec c bash -c "echo nobody > /dev/udp/10.0.0.2/9001"
```

s 上的 nc 输出了 `hello`。抓到的包：

```
07:25:35.164833 IP 10.0.0.1.46842 > 10.0.0.2.9000: UDP, length 6
07:25:35.168871 IP 10.0.0.1.56029 > 10.0.0.2.9001: UDP, length 7
07:25:35.168910 IP 10.0.0.2 > 10.0.0.1: ICMP 10.0.0.2 udp port 9001 unreachable, length 43
```

第一个数据报的十六进制（只看最后一行）：

```
	0x0020:  0002 b6fa 2328 000e 1422 6865 6c6c 6f0a  ....#(..."hello.
```

从 `b6fa` 开始的 8 个字节就是 UDP 头部，后面是数据 `hello\n`：

| 字段 | 长度 | 值 | 含义 |
|---|---|---|---|
| 源端口 | 2 字节 | `b6fa` = 46842 | bash 随机使用的端口 |
| 目的端口 | 2 字节 | `2328` = 9000 | |
| 长度 | 2 字节 | `000e` = 14 | 头部 8 + 数据 6 |
| 校验和 | 2 字节 | `1422` | 检查头部和数据在传输中是否出错 |

就这些。和 IP 相比，UDP 只多做了两件事：用**端口**把数据交给正确的程序，用**校验和**发现损坏的数据（发现了就直接丢弃，不会通知谁）。

第二个数据报发往 9001 端口，s 上没有程序监听，于是 s 的内核回复了一个 **ICMP 端口不可达**（和第 1.4 篇 traceroute 最后一跳的回复是同一种消息）。但发送方的 bash 并不会知道这件事：数据报已经发出去了，它不等待任何回复。

## 3. 用 netem 模拟糟糕的网络

实验网络中的两台主机直接相连，不会丢包。Linux 的 **netem**（网络模拟器）可以人为地在网卡上加入延迟、抖动、丢包、乱序、重复：

```bash
ip netns exec c tc qdisc add dev eth0 root netem delay 20ms 10ms loss 10%
ip netns exec c ping -c 5 -i 0.2 10.0.0.2
```

```
5 packets transmitted, 4 received, 20% packet loss, time 814ms
rtt min/avg/max/mdev = 13.835/21.779/30.230/5.997 ms
```

`delay 20ms 10ms` 表示每个包延迟 20 ms ± 10 ms，`loss 10%` 表示随机丢弃 10% 的包。规则加在 c 的 eth0 上，只影响 c 发出的包。ping 的延迟在 14～30 ms 之间变化，5 个丢了 1 个。本章后面会反复使用它，`tc qdisc del dev eth0 root` 删除规则。

### 3.1 丢包和乱序

在这样的网络上，c 连续发出 1000 个数据报，内容是编号 1～1000：

```bash
ip netns exec c bash -c 'for i in $(seq 1 1000); do echo $i > /dev/udp/10.0.0.2/9000; done'
```

在 s 上抓包，按到达的顺序取出编号，统计：

```
发送 1000 个，收到 891 个，丢失 109 个
乱序到达 852 个
前 30 个到达的编号： 2 3 21 7 41 20 15 114 130 48 49 149 92 45 62 113 36 210 12 136 106 188 126 187 212 102 56 277 268 189
```

- **丢失了 109 个**，约 10%，和 netem 的设置一致。UDP 不会重发，丢了就是丢了；
- **顺序完全乱了**：第 3 个到达的是 21 号，第 8 个到达的是 114 号。发送很快（1000 个用了不到 1 秒），每个包又随机延迟 10～30 ms，后发的包经常先到。「乱序」在这里指比前面已经到达的某个编号更小，1000 个中有 852 个是这样；
- 接收方无法知道丢了哪些、原来的顺序是什么，**除非应用程序自己在数据中加上编号**，就像这个实验做的那样。

这就是「不可靠」的含义：UDP 只是尽力把每个数据报发出去，送没送到、什么顺序到，它都不管。

## 4. 没有流量控制

如果接收方处理得比发送方慢呢？让 s 上的 nc 暂停（用《进程与系统监控》中的 `kill -STOP`），不再读取数据，然后 c 一口气发出 5000 个 1000 字节的数据报（用几行 Python 发送，C 语言的写法在第 4.2 篇）：

```bash
#!/bin/bash
cd /lab
ip netns exec s nc -u -l 9000 > recv2.txt & N=$!          # ip netns exec 用 exec 运行 nc，$! 就是 nc 的 PID
sleep 0.5
kill -STOP $N                                              # 让接收方暂停，不再读取
ip netns exec s nstat -n
ip netns exec c python3 /lab/udpsend.py 5000
ip netns exec s nstat | grep -i udp
ip netns exec s ss -uanm "sport = :9000" | tail -2
kill -CONT $N; sleep 1; kill $N
echo "nc 实际收到的数据报：$(grep -o "x\{993\}" recv2.txt | wc -l) 个"
```

```python
# udpsend.py
import socket, sys
n = int(sys.argv[1])
s = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
s.connect(("10.0.0.2", 9000))
for i in range(1, n + 1):
    s.send(("%06d" % i).encode() + b"x" * 993)   # 每个数据报 1000 字节
print("发送了", n, "个数据报，每个 1000 字节")
```

```
发送了 5000 个数据报，每个 1000 字节
UdpInErrors                     4907               0.0
UdpRcvbufErrors                 4907               0.0
UNCONN 214272 0            0.0.0.0:9000      0.0.0.0:*
	 skmem:(r214272,rb212992,t0,tb212992,f2816,w0,o0,bl0,d4907)
nc 实际收到的数据报：93 个
```

（`nstat -n` 把计数器清零，之后的 `nstat` 显示这段时间内的变化。）

- 发送方顺利地发完了 5000 个，**没有收到任何错误**；
- 接收方的**接收缓冲区**（`rb212992`，约 208 KB）很快就满了（`r214272`），之后到达的数据报全部被丢弃，计数器 `UdpRcvbufErrors` 记录了 4907 个，`ss` 中的 `d4907` 也是这个数；
- nc 恢复运行后，只读到了缓冲区中的 93 个。每个数据报的数据是 1000 字节，但内核为它分配的内存要多得多（大约 2.3 KB），所以 208 KB 的缓冲区只装下了 93 个。

UDP 没有**流量控制**：发送方不知道接收方能处理多快，接收方也没有办法让发送方慢下来。TCP 有，第 2.4 篇会做同样的实验对比。

## 5. 为什么还要用 UDP

UDP 不可靠，却被大量使用，因为在很多场合，TCP 的可靠性反而是负担：

- **DNS 查询**：一问一答，各一个数据报就够了。用 TCP 要先花一个往返时间建立连接；丢了就重新问一次，由应用自己处理（第 3.1 篇）；
- **音视频通话、直播、游戏**：一个 200 ms 前的语音包，重发过来已经没用了，宁可丢掉，也不要因为等待重发而让后面的数据都卡住；
- **QUIC / HTTP/3**：在 UDP 之上自己实现可靠传输和拥塞控制，避开了 TCP 的一些限制（第 3.4 篇）；
- **广播和组播**：TCP 只能一对一，UDP 可以一对多（第 1.2 篇看到的很多 IPv6 包就是组播）。

使用 UDP 的应用，往往要自己处理编号、确认、重发、限速这些问题，相当于把 TCP 的一部分功能按自己的需要重新实现一遍。

## 6. 常见误区

1. **以为 UDP 发送成功就代表对方收到了**：`send` 成功只说明数据报交给了本机的内核。
2. **以为在局域网中 UDP 不会丢包**：接收方处理不过来时，缓冲区溢出同样会丢包，就像第 4 节那样。
3. **以为 UDP 的数据报会按顺序到达**：路径不同、延迟变化时都会乱序。
4. **发送过大的 UDP 数据报**：超过 MTU 会被 IP 分片，任何一片丢失整个数据报就没了。一般控制在 1472 字节（以太网）以内，在互联网上更保守一些。
5. **把 ICMP 端口不可达当作 UDP 的确认机制**：它只在端口没有程序监听时才会出现，而且可能被防火墙拦截。

## 7. 小结

- 传输层用端口号区分同一台主机上的程序；UDP 头部只有 8 字节：源端口、目的端口、长度、校验和
- 发往没有程序监听的 UDP 端口，对方回复 ICMP 端口不可达，但发送方的应用通常不会知道
- netem 可以模拟延迟、抖动、丢包：`tc qdisc add dev eth0 root netem delay 20ms 10ms loss 10%`
- 实测 10% 丢包、±10 ms 抖动的网络中，1000 个数据报收到 891 个，顺序严重错乱
- UDP 没有流量控制：接收方暂停时，5000 个数据报只留下了 93 个，4907 个被丢弃（`UdpRcvbufErrors`），发送方毫不知情
- UDP 适合一问一答、实时性优先、组播等场合，可靠性由应用自己决定

## 8. 练习

1. 一个 UDP 数据报中有 1472 字节的数据，加上各层头部后，以太网帧是多少字节？
2. 在 netem 中用 `delay 20ms`（不加抖动）重复第 3.1 节的实验，还会乱序吗？
3. 增大接收缓冲区能解决第 4 节的问题吗？

<details>
<summary>点击查看答案</summary>

1. 14（以太网头）+ 20（IP 头）+ 8（UDP 头）+ 1472 = **1514** 字节，正好是 MTU 1500 加上以太网头。这是不分片时 UDP 能装的最多数据（第 1.2 篇 ping 的 1472 也是这样算出来的，只是把 UDP 头换成了 ICMP 头，两者都是 8 字节）。

2. 不会。把规则改成 `delay 20ms loss 10%` 后重复实验：

   ```
   收到 895 个，乱序 0 个
   ```

   每个包都延迟同样的 20 ms，先发的总是先到，所以不会乱序，只会丢包。乱序来自延迟的**变化**：真实的网络中，不同的包可能走不同的路径、在路由器中排队的时间不同，就会出现这种变化。

3. 只能缓解，不能解决。更大的缓冲区能吸收短时间的突发流量，接收方偶尔慢一下不至于丢包；但如果发送方持续地比接收方快，再大的缓冲区也会被填满。真正的解决方法是让发送方知道接收方的处理能力并且慢下来，也就是流量控制，这正是 TCP 提供的。

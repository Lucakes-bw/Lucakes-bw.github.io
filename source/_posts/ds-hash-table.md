> **本文目标**：理解哈希函数和冲突；会实现链地址法的哈希表（含扩容）和线性探测的开放寻址法；理解负载因子对性能的影响；知道好的哈希函数的重要性；会根据需求选择哈希表或其他查找结构。
>
> **前置知识**：《单链表》、《二分查找》、《二叉搜索树》。

## 1. 思路

到目前为止，查找最快的方法是二分查找和平衡树，O(log n)。还能更快吗？

如果键是 0 到 999 之间的整数，可以直接用一个长度为 1000 的数组，`table[key]` 就是要找的值，O(1)。但现实中的键往往是字符串、很大的整数，不可能为每个可能的键都准备一个位置。

**哈希表**的做法是：用一个**哈希函数**把任意的键转换成一个整数，再对数组长度取余，得到它在数组中的位置（叫作**桶**）。查找时用同样的方法算出位置，直接去那里找。

问题是，不同的键可能被映射到同一个位置，这叫**冲突**。比如数组长度是 7，15 和 8 除以 7 的余数都是 1。处理冲突有两种主要的方法：**链地址法**和**开放寻址法**。

## 2. 哈希函数

好的哈希函数要把键**均匀地**分散到所有的桶中。看两个字符串的哈希函数：

```c
uint32_t hashBad(const char* s)                 // 把字符的编码加起来：很差
{
    uint32_t h = 0;
    while (*s) h += (unsigned char)*s++;
    return h;
}

uint32_t hashFNV(const char* s)                 // FNV-1a：每个字符都会打乱所有的位
{
    uint32_t h = 2166136261u;
    while (*s) {
        h ^= (unsigned char)*s++;
        h *= 16777619u;
    }
    return h;
}
```

第一个函数把所有字符的编码加起来，看似合理，但问题很大：`"ab"` 和 `"ba"` 的哈希值相同；而且字符串不长时，和的范围很小。FNV-1a 每处理一个字符，都先异或再乘以一个大质数，让每个字符都影响结果的所有位。

用 10 万个形如 `"user12345"` 的键（第 3 节的哈希表，最终有 131072 个桶）实测：

```
字符编码相加 桶 131072 个，用到 136 个，最长的链 5520，平均每次查找比较 1806.6 次，查找 100000 次 827.9 ms
FNV-1a       桶 131072 个，用到 69008 个，最长的链 7，平均每次查找比较 1.4 次，查找 100000 次 3.6 ms
```

「字符编码相加」的哈希值只有 136 种：这些键都由 `user` 加上最多 5 位数字组成，编码之和的范围非常窄。13 万个桶只用到了 136 个，最长的链有 5520 个元素，查找退化成了链表的顺序查找，**慢了 230 倍**。而 FNV-1a 用到了一半以上的桶，平均每次查找只比较 1.4 次。

**哈希表的性能完全取决于哈希函数**。实际中应该使用经过检验的哈希函数（FNV、MurmurHash、xxHash 等），不要自己随便设计。

## 3. 链地址法

每个桶是一个链表，哈希值相同的元素放在同一个链表中：

```c
typedef struct Entry {
    char* key;
    int value;
    struct Entry* next;
} Entry;

typedef struct {
    Entry** buckets;
    size_t nbuckets;
    size_t size;
    uint32_t (*hash)(const char*);
} HashMap;

void hmPut(HashMap* m, const char* key, int value)
{
    size_t b = m->hash(key) % m->nbuckets;     // 算出在哪个桶
    for (Entry* e = m->buckets[b]; e; e = e->next) {
        if (strcmp(e->key, key) == 0) { e->value = value; return; }   // 已存在：更新
    }
    Entry* e = malloc(sizeof(Entry));
    if (e == NULL) exit(1);
    e->key = malloc(strlen(key) + 1);
    if (e->key == NULL) exit(1);
    strcpy(e->key, key);
    e->value = value;
    e->next = m->buckets[b];                    // 插到这个桶的链表头部
    m->buckets[b] = e;
    if (++m->size > m->nbuckets) hmRehash(m);   // 负载因子超过 1 就扩容
}

int* hmGet(const HashMap* m, const char* key, long long* probes)
{
    size_t b = m->hash(key) % m->nbuckets;
    for (Entry* e = m->buckets[b]; e; e = e->next) {
        if (probes) ++*probes;
        if (strcmp(e->key, key) == 0) return &e->value;
    }
    return NULL;
}
```

（`probes` 用来统计比较的次数，实际使用时可以去掉。键要复制一份保存，不能只保存调用者传入的指针，因为调用者的字符串可能会被修改或释放。）

### 3.1 负载因子和扩容

**负载因子** α = 元素个数 / 桶的个数，也就是链表的平均长度。查找的平均代价是 O(1 + α)。α 越大，链表越长，查找越慢。

所以元素增多时要**扩容**：桶的个数翻倍，然后把**所有元素重新分配**到新的桶中（因为桶的个数变了，`hash % nbuckets` 的结果也变了）：

```c
static void hmRehash(HashMap* m)                // 桶的个数翻倍，所有元素重新分配
{
    size_t nb = m->nbuckets * 2;
    Entry** nbk = calloc(nb, sizeof(Entry*));
    if (nbk == NULL) exit(1);
    for (size_t i = 0; i < m->nbuckets; ++i) {
        Entry* e = m->buckets[i];
        while (e) {
            Entry* next = e->next;
            size_t b = m->hash(e->key) % nb;
            e->next = nbk[b];
            nbk[b] = e;
            e = next;
        }
    }
    free(m->buckets);
    m->buckets = nbk;
    m->nbuckets = nb;
}
```

扩容一次是 O(n)，但和《顺序表》一样，因为每次翻倍，均摊到每次插入上是 O(1)。

```c
HashMap ages = hmCreate(4, hashFNV);
hmPut(&ages, "alice", 30); hmPut(&ages, "bob", 25); hmPut(&ages, "carol", 35);
hmPut(&ages, "dave", 28); hmPut(&ages, "eve", 22); hmPut(&ages, "bob", 26);
```

```
bob = 26，frank 不存在，元素 5 个，桶 8 个
```

插入第 5 个元素时，负载因子超过 1，桶从 4 个扩容到 8 个。第二次插入 `bob` 更新了它的值。程序用 ASan 和 `leaks` 检查过，没有错误和泄漏。

## 4. 开放寻址法

开放寻址法不使用链表，所有元素都直接存放在数组中。发生冲突时，按某种规则去找**下一个空位**。最简单的是**线性探测**：被占了就看下一个位置。

```c
int isInsert(IntSet* s, int key)
{
    size_t i = mix((unsigned)key) % s->cap;
    while (s->slots[i] != -1) {
        if (s->slots[i] == key) return 0;
        i = (i + 1) % s->cap;                   // 被占了：看下一个位置
    }
    s->slots[i] = key;
    s->size++;
    return 1;
}

int isContains(const IntSet* s, int key, long long* probes)
{
    size_t i = mix((unsigned)key) % s->cap;
    for (;;) {
        ++*probes;
        if (s->slots[i] == -1) return 0;        // 遇到空位：不存在
        if (s->slots[i] == key) return 1;
        i = (i + 1) % s->cap;
    }
}
```

（这是一个存放非负整数的集合，`-1` 表示空位；`mix` 是一个打乱整数各个位的哈希函数。）查找时如果遇到空位，就可以确定要找的键不存在：如果它存在，插入时一定会放在这个空位或者更前面的位置。

线性探测的问题是**聚集**：连续被占用的位置会形成一段，落在这一段中的任何键都要一直探测到这一段的末尾，而新的元素又会让这一段变得更长。在演示中，12、23、34 的哈希值都是 1，已经形成了一段聚集，再插入 45 或 13 看看：

### 4.1 实测：负载因子的影响

在容量为 2²⁰（约 105 万）的表中，填充到不同的负载因子，分别统计查找存在的键（从所有键中随机抽取）和不存在的键的平均探测次数：

```
线性探测 负载因子 0.50：查找成功平均探测 1.51 次，查找失败平均探测 2.48 次
线性探测 负载因子 0.70：查找成功平均探测 2.17 次，查找失败平均探测 5.98 次
线性探测 负载因子 0.90：查找成功平均探测 5.53 次，查找失败平均探测 49.94 次
线性探测 负载因子 0.95：查找成功平均探测 10.43 次，查找失败平均探测 190.98 次
线性探测 负载因子 0.99：查找成功平均探测 47.06 次，查找失败平均探测 4290.42 次
```

这和 Knuth 给出的理论公式基本吻合（负载因子越接近 1，随机波动越大）：查找成功约为 ½(1 + 1/(1−α))，查找失败约为 ½(1 + 1/(1−α)²)。α = 0.9 时，公式给出 5.5 和 50.5 次，实测是 5.53 和 49.94 次。

负载因子接近 1 时，探测次数急剧上升：α = 0.99 时，一次失败的查找要探测 4000 多次。所以**开放寻址法的负载因子通常控制在 0.5 到 0.75 之间**，超过就扩容。

（我第一次测量时，只查找了最先插入的 10 万个键，结果「查找成功」在所有负载因子下都是 1.05 次。原因是这些键插入时表还很空，它们几乎都在自己的哈希位置上。改为在所有键中随机抽取后，才得到了上面和理论一致的结果。测量时的抽样方法同样重要。）

### 4.2 两种方法的比较

| | 链地址法 | 开放寻址法 |
|---|---|---|
| 存储 | 数组 + 链表节点 | 只有数组 |
| 负载因子 | 可以大于 1 | 必须小于 1，通常 ≤ 0.75 |
| 缓存友好 | 否，节点分散 | 是，探测的位置连续 |
| 删除 | 简单，从链表中删除 | 复杂，不能直接清空（练习 3） |
| 实现 | C++ 的 `std::unordered_map`、Java 的 `HashMap` | Python 的 `dict`、Rust 的 `HashMap` |

## 5. 哈希表和其他查找结构

| | 有序数组 + 二分 | 平衡二叉搜索树 | 哈希表 |
|---|---|---|---|
| 查找 | O(log n) | O(log n) | 平均 O(1)，最坏 O(n) |
| 插入、删除 | O(n) | O(log n) | 平均 O(1) |
| 有序遍历、范围查询 | 支持 | 支持 | **不支持** |
| 最小值、最大值 | O(1) | O(log n) | O(n) |

哈希表的查找最快，但它是**无序**的：不能按顺序遍历，不能查找「所有在 100 到 200 之间的键」，也不能快速找到最小的键。需要这些操作时，用平衡树（C++ 的 `std::map`）。另外，哈希表的最坏情况是 O(n)：如果哈希函数不好，或者有人故意构造大量冲突的键（**哈希洪水攻击**），性能会急剧下降，所以很多语言的哈希表会使用带随机种子的哈希函数。

《STL 容器》中实测过：在 10 万个元素中查找 10 万次，`unordered_set` 用了 1.4 毫秒，`set` 用了 7.7 毫秒，有序 `vector` 的二分查找用了 2.3 毫秒，而顺序查找用了 2 秒。

## 6. 常见错误

1. **使用糟糕的哈希函数**：大量冲突，实测慢了 230 倍。
2. **不扩容**：负载因子越来越大，链表越来越长，或者线性探测时探测次数急剧增加。
3. **扩容时只复制数组，不重新计算位置**：桶的个数变了，元素的位置也要变。
4. **只保存键的指针，不复制键**：调用者修改或释放了字符串，哈希表中的键就失效了。
5. **开放寻址法删除时直接把位置清空**：会切断后面元素的探测链，导致查找不到它们。
6. **需要有序遍历时使用哈希表**：哈希表是无序的。

## 7. 小结

- 哈希表用哈希函数算出键的位置，平均 O(1) 查找、插入、删除
- 不同的键映射到同一个位置叫冲突；链地址法用链表串起冲突的元素，开放寻址法去找下一个空位
- 哈希函数决定了性能：实测糟糕的哈希函数让 13 万个桶只用了 136 个，查找慢了 230 倍
- 负载因子过大时要扩容（翻倍并重新分配所有元素），均摊 O(1)；线性探测的负载因子通常不超过 0.75，实测和理论公式基本吻合
- 哈希表无序，不支持范围查询；需要有序时用平衡树

## 8. 练习

1. 给定一个整数数组和一个目标值，判断数组中是否有两个数之和等于目标值，要求 O(n)。
2. 用 `key % m` 作为哈希函数时，为什么 m 通常取质数，而不是 2 的幂？（提示：考虑所有的键都是偶数，或者都是 1000 的倍数的情况。）
3. 在线性探测的哈希表中，删除一个元素时为什么不能直接把它的位置标记为空？应该怎么做？

1. 遍历数组，对每个数 x，检查 `target - x` 是否已经在哈希集合中，然后把 x 放入集合：

   ```c
   int twoSum(const int* a, int n, int target, int* x, int* y)   // 有没有两个数之和等于 target
   {
       IntSet seen = {malloc(2 * n * sizeof(int)), (size_t)2 * n, 0};
       memset(seen.slots, -1, 2 * n * sizeof(int));
       long long dummy = 0;
       int found = 0;
       for (int i = 0; i < n && !found; ++i) {
           int need = target - a[i];
           if (need >= 0 && isContains(&seen, need, &dummy)) { *x = need; *y = a[i]; found = 1; }
           isInsert(&seen, a[i]);
       }
       free(seen.slots);
       return found;
   }
   ```

   对 `{8, 3, 11, 7, 2, 15}` 和目标 9，找到 7 + 2 = 9；目标 100 时没有。容量取 2n，负载因子不超过 0.5。（这里的 `IntSet` 只能存放非负整数。）两两比较是 O(n²)；排序后用两个指针是 O(n log n)；哈希表是 O(n)。

2. 如果 m 是 2 的幂，`key % m` 只取决于 key 的二进制最低几位，高位完全被忽略了。如果所有的键都是偶数，最低位都是 0，一半的桶永远用不到；如果键都是 1024 的倍数，而 m = 1024，所有的键都落在 0 号桶。m 取质数时，key 的所有位都会影响余数，分布更均匀。（如果哈希函数本身已经充分打乱了所有的位，比如本文的 FNV-1a 和 `mix`，用 2 的幂也没有问题，而且可以用位运算 `h & (m - 1)` 代替取余，更快。）

3. 查找时遇到空位就停止。如果直接清空被删除的位置，那么插入时因为它被占用而放到了后面的元素，就再也找不到了（查找到这个空位就停止了）。正确的做法是放一个特殊的「墓碑」标记：查找时把它当作被占用，继续往后找；插入时可以把新元素放在墓碑的位置。墓碑太多时，重新建一张表来清理它们。

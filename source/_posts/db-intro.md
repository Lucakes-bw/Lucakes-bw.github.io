> **本文目标**：理解数据库解决了哪些「直接用文件」解决不了的问题；理解关系模型中的表、行、列、主键；会启动 MySQL，用命令行客户端连接；会建库、建表、插入和查询；理解 MySQL 的客户端/服务器结构；会创建用户并授予权限。
>
> **前置知识**：会用 Linux 命令行和 Docker（Linux 基础专栏）。了解 TCP 连接有助于理解第 4 节（计算机网络专栏）。
>
> **实验环境**：Docker 中的 MySQL 8.4.13 官方镜像（基于 Oracle Linux 9，aarch64，2 个 CPU 核），字符集 utf8mb4。本专栏所有的 SQL 都在这个数据库中执行。

## 1. 为什么需要数据库

程序要保存数据，最直接的办法是写文件：文本文件、CSV、JSON。数据少、只有一个程序读写时，这样完全够用。但是很快就会遇到问题。

先看一个实验。文件 `count.txt` 中保存一个计数，两个进程**同时**各给它加 1000 次，每次「读出数字，加 1，写回去」：

```bash
echo 0 > count.txt
inc() { for i in $(seq 1000); do n=$(cat count.txt); echo $((n + 1)) > count.txt; done; }
inc & inc & wait
cat count.txt
```

结果应该是 2000。运行三次：

```
5
5
22
```

不仅是「少加了几次」，计数几乎被清零了。原因有两个：

- 两个进程可能读到同一个值，各自加 1 后写回，两次加法只生效了一次（《线程同步》中的「丢失更新」）；
- 更糟的是，`echo ... > count.txt` 会先把文件**截断**为空，再写入新的数字。另一个进程恰好在这个间隙读取，读到的是空字符串，`$((n + 1))` 算出 1，计数就回到了 1。

同样的事交给 MySQL：表 `counter` 中有一行 `n = 0`，两个客户端同时各执行 1000 次 `UPDATE counter SET n = n + 1`：

```
2000
2000
2000
```

三次都是 2000。数据库保证每一条 `UPDATE` 都是一个不可分割的整体，两个客户端的修改不会互相覆盖，也不会有人读到「写了一半」的数据。

这只是数据库解决的问题之一。和直接读写文件相比，数据库还提供：

| 问题 | 直接用文件 | 数据库 |
|---|---|---|
| 多个程序同时读写 | 自己加锁，很容易出错 | 事务和锁（第 4 章） |
| 写到一半断电、进程崩溃 | 文件可能损坏，只剩一半 | 崩溃后自动恢复到一致的状态（4.4 篇） |
| 在大量数据中查找 | 从头扫描整个文件 | 索引，百万行中找一行只要几次磁盘读取（第 3 章） |
| 数据的格式和约束 | 程序自己检查 | 类型、主键、唯一、外键等约束由数据库检查（1.2 篇） |
| 查询方式 | 每种查询写一段代码 | 用 SQL 描述「要什么」，数据库决定「怎么找」 |
| 权限 | 只有文件权限 | 精确到库、表、列、操作的权限（第 6 节） |

**数据库**（database）就是按一定结构组织、长期保存的数据集合；管理它的软件叫**数据库管理系统**（DBMS），例如 MySQL、PostgreSQL、SQLite、Oracle。平时说「数据库」，通常两者都指。

## 2. 关系模型

MySQL 是**关系型数据库**：数据保存在一张张**表**（table）中，表就像一个二维表格：

- 每一**列**（column）有一个名字和一个类型，例如 `price DECIMAL(10, 2)`；
- 每一**行**（row）是一条记录，例如一件商品；
- 通常有一列（或几列）能唯一确定一行，叫作**主键**（primary key），例如商品编号 `id`。两行的主键不能相同。

表和表之间通过列的值建立联系，例如订单表中的 `product_id` 列保存商品的 `id`，表示这笔订单买的是哪件商品（1.4 篇的多表查询，第 2 章的表设计）。

操作关系型数据库的语言是 **SQL**（Structured Query Language）。几乎所有关系型数据库都使用 SQL，基本语法相同，各家有一些扩展。SQL 的语句大致分为几类：

| 类别 | 作用 | 语句 |
|---|---|---|
| DDL（数据定义） | 创建、修改、删除库和表 | `CREATE`、`ALTER`、`DROP` |
| DML（数据操作） | 增加、修改、删除行 | `INSERT`、`UPDATE`、`DELETE` |
| DQL（数据查询） | 查询 | `SELECT` |
| DCL（数据控制） | 用户和权限 | `CREATE USER`、`GRANT`、`REVOKE` |

除了关系型数据库，还有 Redis（键值）、MongoDB（文档）等 **NoSQL** 数据库，它们放弃了部分关系模型的特性，换取特定场景下的性能或灵活性。本专栏只讲 MySQL。

## 3. 启动 MySQL

用 Docker 启动 MySQL 8.4（长期支持版），root 密码设为 `lab`：

```bash
docker run -d --name mysql84 -e MYSQL_ROOT_PASSWORD=lab mysql:8.4
```

第一次启动要初始化数据目录，大约需要十几秒。之后进入容器，用命令行客户端 `mysql` 连接：

```bash
docker exec -it -e LANG=C.UTF-8 mysql84 mysql -uroot -p
```

`-e LANG=C.UTF-8` 不能省略：这个镜像中没有设置语言环境，客户端会默认使用 latin1 字符集和服务器通信，中文虽然看起来正常，存进数据库的却是错误的字节。下一篇第 4 节会重现这个问题。

输入密码后看到 `mysql>` 提示符，就可以输入 SQL 了。每条语句以分号 `;` 结束，可以跨多行；关键字不区分大小写，习惯上写成大写。

> 为了不必每次输入密码，可以把用户名和密码写在 `~/.my.cnf` 中（`[client]` 段的 `user=root`、`password=lab`，再加上 `default-character-set=utf8mb4`），客户端会自动读取。这只适合实验环境。

先看看服务器的版本和几个默认设置：

```sql
SELECT version(), @@character_set_server, @@transaction_isolation, @@innodb_page_size;
```

```
+-----------+------------------------+-------------------------+--------------------+
| version() | @@character_set_server | @@transaction_isolation | @@innodb_page_size |
+-----------+------------------------+-------------------------+--------------------+
| 8.4.13    | utf8mb4                | REPEATABLE-READ         |              16384 |
+-----------+------------------------+-------------------------+--------------------+
```

`@@` 开头的是服务器的系统变量。默认字符集是 `utf8mb4`（1.2 篇），默认的事务隔离级别是「可重复读」（4.2 篇），InnoDB 的页大小是 16 KB（3.1 篇）。这几个值后面都会遇到。

## 4. 第一次使用

### 4.1 建库、建表、插入、查询

```sql
SHOW DATABASES;
```

```
+--------------------+
| Database           |
+--------------------+
| information_schema |
| mysql              |
| performance_schema |
| sys                |
+--------------------+
4 rows in set (0.01 sec)
```

这四个是 MySQL 自带的系统库：`mysql` 保存用户、权限等，`information_schema` 和 `performance_schema` 提供库表结构和运行状态的信息，`sys` 是基于它们的一组方便查看的视图。

创建一个网店的数据库 `shop`，在其中创建商品表 `product`：

```sql
CREATE DATABASE shop;
USE shop;
CREATE TABLE product (
    id    INT PRIMARY KEY,
    name  VARCHAR(50),
    price DECIMAL(10, 2),
    stock INT
);
```

```
Query OK, 1 row affected (0.00 sec)
Database changed
Query OK, 0 rows affected (0.00 sec)
```

`USE shop` 选择了当前数据库，之后的表名都在 `shop` 中查找。表有四列：编号（整数，主键）、名称（最多 50 个字符的字符串）、价格（共 10 位、其中 2 位小数的定点数）、库存（整数）。类型的细节在下一篇。

插入三行，第二条语句一次插入了两行：

```sql
INSERT INTO product VALUES (1, '机械键盘', 299.00, 50);
INSERT INTO product VALUES (2, '无线鼠标', 89.90, 200), (3, '显示器', 1299.00, 15);
```

```
Query OK, 1 row affected (0.00 sec)

Query OK, 2 rows affected (0.00 sec)
Records: 2  Duplicates: 0  Warnings: 0
```

查询全部行和列（`*` 表示所有的列）：

```sql
SELECT * FROM product;
```

```
+----+----------+---------+-------+
| id | name     | price   | stock |
+----+----------+---------+-------+
|  1 | 机械键盘 |  299.00 |    50 |
|  2 | 无线鼠标 |   89.90 |   200 |
|  3 | 显示器   | 1299.00 |    15 |
+----+----------+---------+-------+
3 rows in set (0.00 sec)
```

> 命令行客户端按字符数对齐表格，中文在终端中占两个字符宽，表格会错位。本专栏展示的结果都按显示宽度重新对齐过，内容没有改动。

只要价格低于 300 的商品的名称和价格：

```sql
SELECT name, price FROM product WHERE price < 300;
```

```
+----------+--------+
| name     | price  |
+----------+--------+
| 机械键盘 | 299.00 |
| 无线鼠标 |  89.90 |
+----------+--------+
2 rows in set (0.00 sec)
```

注意 SQL 的写法：只说明**要什么**（哪些列、满足什么条件），没有说**怎么找**（从头扫描，还是用索引）。怎么找由数据库的优化器决定，这是 SQL 和自己写循环读文件的根本区别。

主键不能重复，再插入一个 `id` 为 1 的商品：

```sql
INSERT INTO product VALUES (1, '耳机', 199.00, 30);
```

```
ERROR 1062 (23000): Duplicate entry '1' for key 'product.PRIMARY'
```

数据库拒绝了这次插入。这就是「约束由数据库检查」：不管哪个程序、哪段代码插入数据，都不可能出现两件编号相同的商品。

查看库中的表和表的结构：

```sql
SHOW TABLES;
DESC product;
```

```
+----------------+
| Tables_in_shop |
+----------------+
| product        |
+----------------+

+-------+---------------+------+-----+---------+-------+
| Field | Type          | Null | Key | Default | Extra |
+-------+---------------+------+-----+---------+-------+
| id    | int           | NO   | PRI | NULL    |       |
| name  | varchar(50)   | YES  |     | NULL    |       |
| price | decimal(10,2) | YES  |     | NULL    |       |
| stock | int           | YES  |     | NULL    |       |
+-------+---------------+------+-----+---------+-------+
```

`Null` 列表示这一列能否为空：主键自动是 `NOT NULL`，其他列默认允许为空。`Key` 中的 `PRI` 表示主键。

### 4.2 表在磁盘上是什么

MySQL 的数据保存在**数据目录**中（`SHOW VARIABLES LIKE 'datadir'` 查看，这里是 `/var/lib/mysql/`）。每个库是其中的一个子目录：

```bash
ls -la /var/lib/mysql/shop/
```

```
-rw-r----- 1 mysql mysql 114688 Oct 25 10:15 product.ibd
```

表 `product` 就是一个文件 `product.ibd`，114688 字节，正好是 7 个 16 KB 的页。只有 3 行数据，文件却有 112 KB：表的数据、索引和管理信息都按页存放，即使是空表也要预先分配几个页。3.1 篇会打开这个文件，看看页里面有什么。

数据目录中还有其他文件：`#innodb_redo` 目录中是 redo 日志，`undo_001`、`undo_002` 是 undo 日志，`binlog.000001` 等是二进制日志。它们是事务和崩溃恢复的基础（4.4 篇）。

**不要直接修改、复制或删除数据目录中的文件。** 数据库运行时，很多数据还在内存中没有写回文件；直接复制得到的文件很可能是不一致的。备份要用专门的方法（5.2 篇）。

## 5. 客户端和服务器

`mysql` 命令并不是数据库本身，它只是一个**客户端**。真正管理数据的是**服务器**进程 `mysqld`，它在容器中是 1 号进程：

```bash
grep -E "^(Pid|Threads|VmRSS)" /proc/1/status
```

```
Pid:	1
VmRSS:	  485312 kB
Threads:	37
```

一个刚启动、几乎没有数据的 `mysqld` 就有 37 个线程，占用约 474 MB 内存，大部分是 InnoDB 的缓冲池（缓存数据页的内存，默认 128 MB）和各种后台线程。

客户端和服务器之间通过连接通信。客户端中执行 `status`（或 `\s`）可以看到连接方式：

```
Connection:		Localhost via UNIX socket
UNIX socket:		/var/run/mysqld/mysqld.sock
```

在同一台机器上，默认用 **Unix 域套接字**（一个特殊的文件，和网络套接字的用法相同，但不经过网络协议栈）。指定 `-h 127.0.0.1` 就改用 TCP：

```
Connection:		127.0.0.1 via TCP/IP
TCP port:		3306
```

MySQL 的默认端口是 **3306**（另外 33060 是 X 协议的端口）。所以 MySQL 服务器本质上就是一个 TCP 服务器，和计算机网络专栏 4.4 篇的 epoll 服务器是同一类程序，只是协议换成了 MySQL 自己的二进制协议。

从实验网络的容器中用 nc 连接 3306 端口，什么都不发送，看看服务器发来了什么：

```bash
timeout 2 nc 172.17.0.4 3306 | head -c 96 | od -A d -t x1z -w16
```

```
0000000 4a 00 00 00 0a 38 2e 34 2e 31 33 00 1e 00 00 00  >J....8.4.13.....<
0000016 46 33 6f 47 63 66 7e 7e 00 ff ff ff 02 00 ff df  >F3oGcf~~........<
0000032 15 00 00 00 00 00 00 00 00 00 00 2a 23 0b 05 61  >...........*#..a<
0000048 77 7a 60 04 71 7a 73 00 63 61 63 68 69 6e 67 5f  >wz`.qzs.caching_<
0000064 73 68 61 32 5f 70 61 73 73 77 6f 72 64 00        >sha2_password.<
```

和 HTTP 不同，MySQL 协议是**服务器先说话**：连接建立后，服务器立即发出一个「握手包」：

| 字节 | 内容 | 含义 |
|---|---|---|
| `4a 00 00` | 74 | 包的长度（3 字节，小端序） |
| `00` | 0 | 包的序号 |
| `0a` | 10 | 协议版本 |
| `38 2e 34 2e 31 33 00` | `8.4.13` | 服务器版本，以 `\0` 结尾 |
| `1e 00 00 00` | 30 | 这个连接的编号 |
| `46 33 6f 47 …` | 随机字节 | 用于密码认证的随机数（salt） |
| 末尾 | `caching_sha2_password` | 认证方式 |

客户端收到后，用服务器给的随机数和密码计算出一个值发回去（密码本身不在网络上传输），认证通过后才能发送 SQL。之后每条 SQL 也是这样一个「长度 + 序号 + 内容」的包，查询结果同样分成多个包发回。这正是计算机网络专栏《TCP 的常见问题》中说的「在字节流上划分消息」：MySQL 用每个包开头的长度字段划分。

把数据库端口直接暴露到公网是很危险的：任何人都能连上来尝试密码。生产环境中 3306 端口通常只对应用服务器开放。

## 6. 用户和权限

一直用 root 是不好的习惯：root 可以做任何事，包括删除所有的库。应用程序应该使用一个只有必要权限的用户。创建一个只能查询 `shop` 库的用户 `reader`：

```sql
CREATE USER 'reader'@'%' IDENTIFIED BY 'read123';
GRANT SELECT ON shop.* TO 'reader'@'%';
SHOW GRANTS FOR 'reader'@'%';
```

```
+------------------------------------------+
| Grants for reader@%                      |
+------------------------------------------+
| GRANT USAGE ON *.* TO `reader`@`%`       |
| GRANT SELECT ON `shop`.* TO `reader`@`%` |
+------------------------------------------+
```

MySQL 的用户由「用户名@主机」两部分组成，`%` 表示允许从任何主机连接；写成 `'reader'@'10.0.0.%'` 就只允许从这个网段连接。`USAGE` 表示「没有任何权限」，只能登录；`shop.*` 表示 `shop` 库中的所有表。

用 `reader` 登录，查询可以，删除不行：

```sql
SELECT name FROM product WHERE id = 2;
DELETE FROM product WHERE id = 2;
```

```
+----------+
| name     |
+----------+
| 无线鼠标 |
+----------+
1 row in set (0.00 sec)

ERROR 1142 (42000): DELETE command denied to user 'reader'@'127.0.0.1' for table 'product'
```

常用的权限有 `SELECT`、`INSERT`、`UPDATE`、`DELETE`（读写数据），`CREATE`、`ALTER`、`DROP`（改表结构），`ALL PRIVILEGES`（全部）。用 `REVOKE` 收回权限，`DROP USER` 删除用户。

## 7. 常见错误

- **忘记分号**：客户端显示 `->` 并继续等待输入，以为语句还没写完。补上 `;` 回车即可；
- **没有选择数据库**：`ERROR 1046 (3D000): No database selected`，先 `USE 库名`，或者写成 `库名.表名`；
- **字符串用了双引号或者没加引号**：SQL 标准中字符串用**单引号**，MySQL 默认也接受双引号，但其他数据库中双引号表示列名，养成用单引号的习惯；
- **在 SQL 中把 `=` 写成 `==`**：SQL 的比较就是一个 `=`；
- **直接操作数据目录中的文件**：复制、删除 `.ibd` 文件会让数据库损坏或者数据不一致；
- **应用程序用 root 连接**：一旦程序有 SQL 注入漏洞（5.1 篇），攻击者就拥有了整个数据库。

## 8. 小结

- 数据库解决了直接用文件时的并发、崩溃、查找、约束、权限等问题。实测两个进程同时给文件中的计数加 1000 次，结果是 5；交给 MySQL 是 2000
- 关系模型：数据保存在表中，每列有名字和类型，主键唯一确定一行
- SQL 描述「要什么」，由数据库决定「怎么找」；语句分为 DDL、DML、DQL、DCL
- 每个表是数据目录中的一个 `.ibd` 文件，按 16 KB 的页存放
- MySQL 是客户端/服务器结构，服务器 `mysqld` 监听 3306 端口，本机默认用 Unix 域套接字；连接建立后服务器先发出握手包
- 应用程序应该使用只有必要权限的用户

## 9. 练习

1. 在第 1 节的实验中，如果把计数改成用 `flock` 加锁（`flock count.txt -c '...'`）后再「读、加 1、写」，结果是多少？
2. `SELECT * FROM product WHERE name = '显示器';` 和 `SELECT * FROM product WHERE price = '299';` 能查到结果吗？
3. 用 `reader` 用户执行 `SHOW DATABASES;` 能看到哪些库？

<details>
<summary>点击查看答案</summary>

1. 把 `inc` 中的循环体改成在锁的保护下执行：

   ```bash
   inc() { for i in $(seq 1000); do flock count.txt -c 'n=$(cat count.txt); echo $((n + 1)) > count.txt'; done; }
   ```

   运行三次，结果都是 2000。`flock` 让两个进程的「读、加 1、写」互斥执行，不会互相打断。但这要求**所有**访问这个文件的程序都遵守同样的加锁规则（`flock` 是建议锁，不加锁的程序照样可以读写），而且每次修改要启动一个新的进程、加锁、读写整个文件，速度很慢。数据库把这些都做好了。
2. 都能查到。第一条是普通的字符串比较。第二条中 `price` 是数字类型，`'299'` 是字符串，MySQL 会把字符串**隐式转换**成数字再比较，所以查到了机械键盘。隐式转换看起来方便，但在有索引的列上可能让索引失效（3.4 篇），应该让比较的两边类型一致。
3. 只能看到 `information_schema`、`performance_schema` 和 `shop`。用户看不到自己没有任何权限的库（`mysql`、`sys` 等）；`information_schema` 和 `performance_schema` 对所有用户可见，但其中只显示有权限的对象的信息。

</details>
